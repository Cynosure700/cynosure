# 工具调用终端展示设计文档

## 1. 背景与目标

当前 cynosure 在 TUI 中只展示本轮工具调用总数和最终回答，不展示每个工具的具体调用流程。现有状态栏会显示 `本轮工具 N`，但用户无法在终端内看到“准备调用哪个工具、参数是什么、是否执行完成、执行摘要/失败原因”等过程信息。

本设计目标是在不影响现有 Agent 循环、工具执行、历史持久化、上下文压缩和工具审计日志的前提下，参考 Claude Code 的终端交互形式，在 TUI 会话流中增加可见的工具调用过程展示。

## 2. 当前实现梳理

- TUI 事件通道由 `EventWriter.Event` 写入，事件结构包含 `Name`、`Content` 和 `Data`，位置在 `internal/tui/events.go:5`、`internal/tui/events.go:25`。
- TUI 主循环只处理 `assistant_delta`、`reasoning_delta`、`assistant`、`meta`、`error`、`done` 等事件，位置在 `internal/tui/app.go:180`。
- 目前用户发送消息后，TUI 调用 `runtime.RespondToConversation`，位置在 `internal/tui/app.go:249`。
- Runtime 在每轮模型返回工具调用后执行工具：先运行 PreToolUse hook，再执行工具，再运行 PostToolUse hook，位置在 `internal/agent/runtime/conversation_flow.go:162`。
- 工具执行完成后，`ToolCallCount` 增加并通过 `emitMeta` 下发工具总数，位置在 `internal/agent/runtime/conversation_flow.go:174`、`internal/agent/runtime/conversation_flow.go:180`。
- 工具结果已写入模型历史，并追加到 `~/.cynosure/task_outputs/{session_id}/tools.md`，但该日志不会自动注入 TUI 展示，位置在 `internal/agent/runtime/hooks/tool.go:45`、`internal/agent/runtime/hooks/tool.go:59`。
- TUI 展示消息类型目前只有 user、assistant、thinking、system、error 等，渲染入口在 `internal/tui/app.go:534`。

因此，最佳切入点是在 runtime 执行工具前后额外发送 TUI 事件，TUI 仅消费这些事件并渲染为轻量的“工具过程卡片”。这样不会改变模型上下文、工具结果内容、工具审计日志和最终回复逻辑。

## 3. 范围

### 3.1 本次纳入范围

1. 在终端会话流中展示工具调用生命周期：
   - 准备调用：工具名 + 参数摘要。
   - 调用中：显示运行状态。
   - 调用完成：显示成功/失败状态 + 结果摘要。
2. 支持内置工具、MCP 工具和 `spawn_subagent`。
3. 参数和结果只做摘要展示，避免大结果刷屏。
4. 展示内容只影响 TUI，不改变模型历史和持久化格式。
5. 保持 `/resume` 历史恢复的现有行为，不强制回放历史工具过程。

### 3.2 本次不纳入范围

1. 不做工具结果全文展开/折叠交互。
2. 不新增配置项开关，默认展示轻量流程。
3. 不改变 `task_outputs` 的审计日志格式。
4. 不改变 LLM 请求结构和工具调用协议。
5. 不做 Web UI 或非 TUI 模式适配。

## 4. 可选方案与取舍

### 方案 A：Runtime 新增 tool 事件，TUI 渲染工具过程卡片（推荐）

在 runtime 工具执行前后发送 `tool_call_start` 和 `tool_call_done` 事件。TUI 新增 `tool` 类型消息，以工具调用 ID 合并更新同一张卡片。

优点：
- 与现有 `assistant_delta`、`reasoning_delta`、`meta` 事件模型一致。
- 不改变模型上下文和持久化结构。
- 易于测试：runtime 测事件，TUI 测渲染。
- 可复用现有 `ToolUseContext` 中的工具名、raw args、outcome 和 audit。

缺点：
- 需要新增少量事件协议和 TUI 消息字段。

### 方案 B：复用 system 消息直接追加文本

工具执行前后直接在 TUI 中追加 system 消息，例如“正在调用 bash...”。

优点：
- 改动最小。

缺点：
- 无法自然更新同一个工具调用的状态，会产生多条零散消息。
- 样式和语义与系统提示混在一起，后续维护困难。
- 不利于未来支持折叠、耗时、参数美化等能力。

### 方案 C：读取 tools.md 并实时展示

继续依赖 `~/.cynosure/task_outputs/{session_id}/tools.md`，TUI 通过文件追加日志展示工具过程。

优点：
- 利用现有审计日志。

缺点：
- 只能在工具完成后展示，无法显示“正在调用”。
- 文件轮询或回调会引入额外复杂度。
- 容易把审计日志和交互 UI 强耦合。

结论：选择方案 A。

## 5. 推荐设计

### 5.1 事件协议

新增两个运行期事件：

```text
tool_call_start
tool_call_done
```

事件 `Data` 使用 map，字段如下：

```text
tool_call_id   string  工具调用 ID，来自模型返回的 tool call ID
tool_name      string  工具名，例如 bash/read_file/mcp__xxx__yyy
raw_args       string  原始 JSON 参数
args_preview   string  参数摘要，限制长度后用于 UI 展示
status         string  running/success/rejected
result_preview string  结果摘要，完成后展示，限制长度
audit_summary  string  审计摘要，可选
```

`tool_call_start` 在 PreToolUse hook 成功后、真正执行工具前发送；`tool_call_done` 在 PostToolUse hook 成功后、`ToolCallCount` 增加前后发送均可。推荐放在 PostToolUse hook 成功后、`ToolCallCount++` 前，这样 UI 可以先更新工具卡片，再由 meta 更新计数。

### 5.2 Runtime 改动

在 `RespondToConversation` 工具循环中增加两个小函数：

```text
emitToolCallStart(state, toolCtx)
emitToolCallDone(state, toolCtx)
```

调用顺序建议为：

1. 构造 `ToolUseContext`。
2. 执行 `RunPreToolUse`。
3. 发送 `tool_call_start`。
4. 执行工具。
5. 如 `todo_write` 成功，更新 todos。
6. 执行 `RunPostToolUse`。
7. 发送 `tool_call_done`。
8. `ToolCallCount++` 并发送 `meta`。

这样不会改变现有工具执行顺序，也不会在 hook 失败时展示不完整工具卡片。若工具执行本身失败，现有逻辑会把失败转成 `Outcome.Status = rejected`，仍可通过 `tool_call_done` 展示失败原因。

### 5.3 TUI 数据结构

扩展 TUI 的 `Message`：

```text
Role             string
Content          string
ReasoningContent string
ToolCall         *ToolCallView
```

新增 `ToolCallView`：

```text
ID            string
Name          string
ArgsPreview   string
Status        string
ResultPreview string
```

保留现有 `Content` 和 `ReasoningContent` 字段，避免影响 user/assistant/system/error 消息。

### 5.4 TUI 更新逻辑

TUI 在事件处理处增加：

- `tool_call_start`：追加一条 `Role = "tool"` 的消息，状态为 `running`。
- `tool_call_done`：按 `tool_call_id` 从后向前查找最近的工具消息并更新状态与结果摘要；找不到时追加一条完成态工具消息，避免事件丢失导致 UI 无显示。

渲染规则：

```text
⏺ Bash(command: go test ./...)
  ⎿ running...

✓ Bash
  ⎿ success · ok  ./internal/tui  0.42s
```

其中：

- `running` 使用柔和颜色，避免抢占 assistant 输出。
- `success` 使用绿色/薄荷色。
- `rejected` 或其他失败状态使用珊瑚色。
- 参数和结果摘要均硬截断，避免破坏终端布局。

### 5.5 摘要与安全

参数摘要：

1. 尝试解析 raw JSON。
2. 如果是 `bash`，优先展示 `command` 字段。
3. 如果是文件类工具，优先展示 `file_path` / `path`。
4. 其他工具展示压缩后的单行 JSON。
5. 最大长度建议 160 字符。

结果摘要：

1. 使用 `Outcome.Result` 或 `Audit.OutcomeSummary`。
2. 去除首尾空白，压缩多行到最多 3 行。
3. 最大长度建议 300 字符。
4. 不展示完整大结果；完整结果仍以现有 `~/.cynosure/task_outputs` 和 `read_persisted_output` 机制处理。

安全边界：

- 不额外读取文件。
- 不绕过现有 workspace 安全限制。
- 不把 UI 摘要写回模型上下文。
- 不改变工具执行结果结构。

### 5.6 历史恢复

本次不改变历史持久化模型。`/resume` 仍按现有逻辑只恢复 user、assistant、system、error 消息；历史工具过程不回放。原因是当前存储中的 tool 消息面向模型上下文，直接回放容易把大结果带入 TUI，且会改变现有恢复体验。

后续如果需要回放，可单独设计从 `tools.md` 或结构化 tool event history 中恢复轻量摘要。

## 6. 测试计划

1. Runtime 单测：
   - 有工具调用时按顺序收到 `tool_call_start`、`tool_call_done`、`meta`。
   - 工具执行失败时 `tool_call_done.status = rejected`，并包含失败摘要。
   - 没有工具调用时不产生工具事件。
2. TUI 单测：
   - `tool_call_start` 会追加工具消息。
   - `tool_call_done` 会更新同一工具消息，而不是追加重复消息。
   - 找不到 start 消息时，done 事件会追加完成态工具消息。
   - 渲染中包含工具名、参数摘要、状态和结果摘要。
3. 回归测试：
   - `go test ./internal/agent/runtime ./internal/tui ./internal/agent/runtime/hooks`。
   - 如时间允许，执行 `go test ./...`。

## 7. 兼容性与风险控制

- 对模型无感：新增事件只发送给 TUI writer，不进入 OpenAI messages。
- 对工具无感：不修改 `agenttools.Dispatch` 和 MCP 调用实现。
- 对持久化无感：不修改 `storage.Message` 的 JSON 结构，不修改 `tools.md` 格式。
- 对现有 UI 低侵入：只新增 `tool` 角色渲染分支，不改 user/assistant/system/error 的渲染路径。
- 对大输出友好：UI 只展示摘要，避免影响终端性能。

主要风险：

1. 工具参数中包含多行或超长 JSON，可能影响布局。通过单行化和长度限制规避。
2. 并行工具调用时事件交错。当前 runtime 是顺序执行工具；TUI 仍按 `tool_call_id` 更新，保留未来兼容空间。
3. 工具事件和 assistant 流式内容交错。现有逻辑在工具调用轮不会提前刷 assistant content，新增工具卡片不会干扰最终回答。

## 8. 实施步骤

1. 在 runtime 中新增工具事件构造和摘要函数。
2. 在工具执行循环中发送 start/done 事件。
3. 在 TUI 中新增 `ToolCallView`、事件处理和工具消息更新函数。
4. 在 TUI 渲染中新增 tool 角色样式。
5. 补充 runtime 和 TUI 单测。
6. 执行回归测试，确保现有功能不受影响。

## 9. 验收标准

1. 当 Agent 调用工具时，终端能实时显示工具名、参数摘要、运行状态和完成摘要。
2. 成功与失败状态可区分。
3. 工具结果大时不会刷屏，只显示摘要。
4. 原有最终回答、思考展示、状态栏工具计数、上下文计数仍正常。
5. 工具执行、审计日志、历史持久化和上下文压缩行为保持不变。
6. 相关单测通过。

- 未包含 TBD/TODO 占位内容。
- 设计范围聚焦于 TUI 工具调用过程展示，未引入无关重构。
- 推荐方案不改变模型上下文、工具协议或持久化格式，满足“不影响现有功能”。
