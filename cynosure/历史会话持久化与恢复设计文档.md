# 历史会话持久化与 `/resume` 恢复设计文档

## 1. 背景与目标

当前 `cynosure` 已迁移到本地 TUI。TUI 启动时会在 `local.Bootstrap` 中创建新的 `Conversation` 与新的 `SessionID`，见 `internal/local/bootstrap.go:85`、`internal/local/bootstrap.go:86`；本地 `Store` 中的展示历史、模型历史、摘要缓存与大工具输出当前主要保存在进程内 map，见 `internal/local/store.go:13`。因此进程退出后，历史会话无法恢复。

本次改造目标：

1. 将历史对话持久化到 `~/.cynosure/session/{session_id}/history`。
2. 将模型历史对话持久化到 `~/.cynosure/session/{session_id}/model_history`。
3. 保持现有对话逻辑与压缩逻辑一致：
   - 历史对话用于展示用户与 agent 的交互历史。
   - 模型历史对话用于保存压缩后的上下文，并作为真正传给 LLM 的上下文基线。
4. 新增 TUI `/resume` 功能：直接展示当前目录下的历史会话列表，由用户自主选择恢复目标。
5. 恢复前仍校验当前用户所在项目是否与历史会话所属项目一致；不一致时提示用户移动到历史会话所在目录下，不自动切换目录。

说明：本文档统一按本地隐藏目录约定使用 `~/.cynosure/session`。

## 2. 现状梳理

### 2.1 TUI 启动与会话创建

启动链路为 `main.go` -> `internal/cli.Run` -> `local.Bootstrap` -> `tui.Run`。CLI 目前只支持默认 TUI、`tui`、`help` 和 `--cwd`，见 `internal/cli/root.go:23`、`internal/cli/root.go:58`。

`local.Bootstrap` 每次启动都会创建新会话：

- 本地用户在 `internal/local/bootstrap.go:85` 创建。
- TUI 会话在 `internal/local/bootstrap.go:86` 创建，`SessionID` 使用 `idgen.UUID()`。
- 会话随后通过 `store.CreateConversation` 放入本地 store，见 `internal/local/bootstrap.go:87`。

### 2.2 展示历史与模型历史

runtime 每轮对话开始时会加载两份历史：

- 展示历史：`RespondToConversation` 调用 `loadConversationMessages`，见 `internal/agent/runtime/conversation_flow.go:78`。
- 模型历史：`RespondToConversation` 调用 `loadModelHistory`，见 `internal/agent/runtime/conversation_flow.go:82`。

当前模型历史的语义已经满足需求：`loadModelHistory` 优先从 store 加载 `conversation_model_histories`，不存在时回退展示历史，见 `internal/agent/runtime/context_compression.go:13`、`internal/agent/runtime/context_compression.go:17`。

### 2.3 压缩逻辑

每轮 LLM 请求前，runtime 使用 `compressContextBeforeLLM` 对 `state.ModelHistory` 的 clone 执行压缩，见 `internal/agent/runtime/conversation_flow.go:106`、`internal/agent/runtime/context_compression.go:28`。压缩结果只作为本轮 request history，不直接修改展示历史。

会话结束时，runtime 会将本轮最后一次 request history 加上最终 assistant 消息作为 `finalModelHistory` 保存，见 `internal/agent/runtime/conversation_flow.go:151`、`internal/agent/runtime/conversation_flow.go:153`。因此只要本地 store 的 `UpsertConversationModelHistory` 改为落盘，现有压缩逻辑无需改变。

### 2.4 TUI 展示

TUI 当前只展示 `Model.messages` 中的进程内消息，见 `internal/tui/app.go:35`、`internal/tui/app.go:253`、`internal/tui/app.go:278`。启动时不会从 store 加载历史。现有 slash command 只有 `/help`、`/clear`、`/cwd`、`/skills`、`/mcp`，见 `internal/tui/app.go:162`。

## 3. 方案对比

### 方案 A：继续只用内存 store，额外导出/导入

- 优点：改动少。
- 缺点：需要用户显式导出/导入，无法满足固定路径自动存储；模型历史也难以稳定复用。
- 结论：不采用。

### 方案 B：在 `local.Store` 中增加 session 文件持久化（推荐）

- 做法：保留 runtime 和压缩 pipeline 不变，只扩展本地 store 的读写实现，把展示历史与模型历史同步写入 `~/.cynosure/session`。
- 优点：对 runtime 侵入最小；现有 `SetConversationHistory`、`ListMessagesByConversation`、`GetConversationModelHistory`、`UpsertConversationModelHistory` 语义不变；测试边界清晰。
- 缺点：需要定义文件格式、原子写和 resume 加载流程。
- 结论：采用。

### 方案 C：引入 SQLite 或恢复旧 DB 存储

- 优点：查询能力强，可自然支持 session 列表与索引。
- 缺点：超出本次需求；TUI 迁移已移除外部持久化依赖，引入 DB 会增加复杂度。
- 结论：不采用。

## 4. 总体设计

采用方案 B：在 `internal/local` 新增轻量级 session 目录存储能力，并由 TUI `/resume` 触发当前项目历史会话列表与选择恢复流程。

```text
~/.cynosure/session/
  └── {session_id}/
        ├── history
        └── model_history

local.Bootstrap
  └── local.NewStoreWithMemory
        ├── MarkdownMemoryStore         # 现有记忆系统，保持不变
        └── SessionHistoryStore         # 新增：展示历史/模型历史文件持久化

TUI /resume
  ├── 扫描 ~/.cynosure/session/*/history
  ├── 过滤 workspace_root == 当前 CWD 的历史会话
  ├── 在 TUI 中展示候选列表
  ├── 用户输入序号选择会话
  ├── 恢复前再次校验 workspace_root == 当前 CWD
  ├── 加载展示历史到 local.Store
  ├── 加载模型历史到 local.Store
  ├── 替换当前 TUI conversation
  └── 将历史渲染到 viewport
```

## 5. 文件路径与格式

### 5.1 路径

新增路径解析函数，建议放在 `internal/config/local_config.go` 或新文件中：

```go
func CynosureSessionDir() (string, error) {
    home, err := os.UserHomeDir()
    if err != nil { ... }
    return filepath.Join(home, ".cynosure", "session"), nil
}
```

启动时确保根目录存在：`os.MkdirAll(~/.cynosure/session, 0o755)`。每个会话单独使用一个子目录：`~/.cynosure/session/{session_id}/`。

目录与文件严格使用：

- 会话目录：`{session_id}/`
- 展示历史：`{session_id}/history`
- 模型历史：`{session_id}/model_history`

`session_id` 只允许 `[A-Za-z0-9._-]`，拒绝 `/`、`\`、空白和 `..`，避免路径穿越。

### 5.2 文件格式

`history` 与 `model_history` 都使用 JSON，且不加扩展名。使用包装结构保存恢复所需元数据：

```json
{
  "version": 1,
  "session_id": "041581e7-c3e7-46c8-afe7-7cdcc671e80e",
  "conversation_id": "conv_xxx",
  "user_id": "local-user",
  "workspace_root": "/abs/path/to/project",
  "title": "TUI 会话",
  "created_at": "2026-06-12T10:00:00Z",
  "updated_at": "2026-06-12T10:10:00Z",
  "messages": []
}
```

`messages` 直接复用现有 `[]storage.Message` JSON 结构，保持与 `storage.EncodeConversationHistory` / `DecodeConversationHistory` 的消息字段兼容，见 `internal/agent/storage/conversation_history.go:10`、`internal/agent/storage/models.go:67`。

设计选择：不额外创建 `meta` 文件，项目过滤与校验所需的 `workspace_root` 内嵌在两份历史文件中；扫描 `/resume` 候选列表和恢复时均以 `{session_id}/history` 的元信息为准。

### 5.3 原子写

每次写入采用临时文件 + rename：

1. 确保 `~/.cynosure/session/{session_id}/` 存在。
2. 写入 `{target}.tmp-{pid}`。
3. `fsync` 文件。
4. `os.Rename(tmp, target)`。
5. 尽量 `fsync` 父目录。

这样可以避免进程中断时留下半截 JSON。

## 6. Store 改造

### 6.1 新增组件

建议在 `internal/local/session_history_store.go` 新增内部组件：

```go
type SessionHistoryStore struct {
    dir string
}

type SessionHistoryDocument struct {
    Version        int               `json:"version"`
    SessionID      string            `json:"session_id"`
    ConversationID string            `json:"conversation_id"`
    UserID         string            `json:"user_id"`
    WorkspaceRoot  string            `json:"workspace_root"`
    Title          string            `json:"title"`
    CreatedAt      time.Time         `json:"created_at"`
    UpdatedAt      time.Time         `json:"updated_at"`
    Messages       []storage.Message `json:"messages"`
}
```

方法建议：

- `SaveHistory(ctx, conversation, messages)`：写 `{session_id}/history`。
- `LoadHistory(ctx, sessionID)`：读 `{session_id}/history`。
- `SaveModelHistory(ctx, conversation, messages)`：写 `{session_id}/model_history`。
- `LoadModelHistory(ctx, sessionID)`：读 `{session_id}/model_history`。
- `ListSessions(ctx, workspaceRoot)`：扫描 `~/.cynosure/session/*/history`，仅返回 `workspace_root` 与当前项目一致的候选会话。
- `ValidateSessionID(sessionID)`：校验文件名安全。

### 6.2 集成到 `local.Store`

`Store` 增加字段：

```go
sessionHistory *SessionHistoryStore
```

`NewStoreWithMemory(workspaceRoot)` 中初始化 session store。现有 `MarkdownMemoryStore` 保持使用 workspace root，不与 `~/.cynosure/session` 混用。

写入策略：

- `CreateConversation`：继续写入内存 map；不需要立即写空文件，避免创建无内容会话。
- `SetConversationHistory`：继续更新 `messages/cache`，随后将完整展示历史写入 `{session_id}/history`。该方法是最终 assistant 消息落地入口，见 `internal/local/store.go:111`、`internal/agent/runtime/hooks/stop.go:9`。
- `UpsertConversationModelHistory`：继续更新 `modelHistory`，随后写入 `{session_id}/model_history`，见 `internal/local/store.go:308`。
- `ListMessagesByConversation`：优先读内存；如果内存为空且 conversation 有 session_id，则尝试从 `{session_id}/history` 加载并回填内存。
- `GetConversationModelHistory`：优先读内存；如果内存为空且 conversation 有 session_id，则尝试从 `{session_id}/model_history` 加载并回填内存。
- `ListResumableSessions(ctx, currentWorkspace)`：调用 session store 扫描当前目录下可恢复的历史会话，供 TUI `/resume` 展示。

错误处理：

- 写文件失败应返回错误，避免用户误以为会话已持久化。
- 读文件不存在时按现有语义返回空历史或 `ok=false`。
- JSON 损坏时返回明确错误，用于 `/resume` 展示。

## 7. `/resume` 设计

### 7.1 命令形式

在 TUI slash command 中新增：

```text
/resume
```

`/help` 更新为包含 `/resume`。

`/resume` 不接收参数。执行后直接扫描并展示当前目录下的历史会话候选列表，用户再通过输入序号自主选择要恢复的会话。这样避免用户手动复制 `session_id`，也避免误恢复其他项目的会话。

### 7.2 恢复流程

恢复只能在未生成状态下进行；如果 `m.running == true`，提示先中断当前生成。

流程：

1. 扫描 `~/.cynosure/session/*/history`。
2. 对每个 history 文件读取元信息，并规范化路径：
   - 对当前 `m.session.CWD` 取 `filepath.Abs` + `filepath.Clean`，可用时再 `filepath.EvalSymlinks`。
   - 对历史文件中的 `workspace_root` 执行同样规范化。
3. 只展示 `workspace_root` 与当前 `m.session.CWD` 一致的历史会话；其他项目的会话不进入候选列表。
4. 如果当前目录没有历史会话，提示：`当前目录暂无可恢复的历史会话`。
5. 如果存在候选会话，在 TUI 中展示带序号的列表，建议字段：序号、更新时间、标题、消息数、session_id。
6. TUI 进入 `resume selecting` 状态。用户下一次输入数字时，按序号选择会话；输入 `/cancel` 或 `/clear` 时退出选择状态。
7. 用户选择后，再次校验所选会话的 `workspace_root` 与当前 `m.session.CWD` 一致：
   - 一致：继续恢复。
   - 不一致：不恢复，提示：`历史会话属于 <workspace_root>，请 cd 到该目录或使用 --cwd <workspace_root> 后再执行 /resume`。
8. 构造 `storage.Conversation`：
   - `ID` 使用文件中的 `conversation_id`；如果为空则生成新 `conv_` 并在内存中建立映射。
   - `SessionID` 使用所选会话的 `session_id`。
   - `UserID` 使用当前本地用户。
   - `Title/CreatedAt/UpdatedAt` 使用文件元信息。
9. 调用 store 的恢复方法，把展示历史写入 `messages/cache`，把模型历史写入 `modelHistory`。
10. 替换 `m.session.Conversation` 为恢复后的 conversation。
11. 将展示历史转换为 TUI `Message` 并刷新 viewport。

### 7.3 TUI 展示规则

实时对话中 TUI 当前只展示 user 与 assistant 消息，不逐条展示 tool 消息；恢复历史时保持一致：

- `role == "user"`：展示为 user。
- `role == "assistant"`：展示为 assistant。
- `role == "tool"`：默认不展示，避免大工具结果刷屏。
- 其他 role：可展示为 system/error，或忽略。

注意：文件中的展示历史仍保存完整 `[]storage.Message`，包括 tool 消息；只是 TUI 渲染时过滤。这样既保留现有 runtime 历史语义，也保证用户看到的是用户-agent 交互。

## 8. 对话与压缩逻辑保持一致

本设计不修改 runtime 主流程：

1. 用户输入仍由 `tui.Model.respond` 调用 `runtime.RespondToConversation`，见 `internal/tui/app.go:145`、`internal/tui/app.go:150`。
2. runtime 仍先加载展示历史和模型历史，见 `internal/agent/runtime/conversation_flow.go:78`、`internal/agent/runtime/conversation_flow.go:82`。
3. 每轮 LLM 前仍通过 `compressContextBeforeLLM` 压缩模型历史副本，见 `internal/agent/runtime/conversation_flow.go:106`。
4. 会话结束仍写展示历史和最终模型历史，见 `internal/agent/runtime/conversation_flow.go:151`、`internal/agent/runtime/conversation_flow.go:153`。

因此，改造后的行为是：

- TUI 展示：来自 `{session_id}/history`。
- LLM 上下文：来自 `{session_id}/model_history`；缺失时仍按现有逻辑回退 `{session_id}/history`。
- 压缩策略、摘要策略、tool result 压缩策略不变。

## 9. 边界条件

1. **当前目录无历史会话**：`/resume` 提示当前目录暂无可恢复的历史会话。
2. **模型历史文件不存在**：允许恢复展示历史；后续 LLM 使用现有 `loadModelHistory` fallback 逻辑从展示历史开始。
3. **项目目录不一致**：拒绝恢复，并提示历史会话所在目录。
4. **历史 JSON 损坏**：拒绝恢复，提示文件解析失败。
5. **当前正在生成**：拒绝恢复，提示先 `Ctrl+C` 中断。
6. **session_id 非法**：拒绝恢复，避免路径穿越。
7. **选择序号非法**：提示用户输入列表中的有效序号，保持 `resume selecting` 状态。
8. **写入失败**：当前轮对话返回错误，TUI 展示错误，避免静默丢历史。

## 12. 验收标准

1. 完成一轮 TUI 对话后，存在 `~/.cynosure/session/{session_id}/history`。
2. 完成一轮 TUI 对话且压缩/模型历史收尾执行后，存在 `~/.cynosure/session/{session_id}/model_history`。
3. 退出 TUI 后重新启动，在同一项目目录执行 `/resume` 可看到当前目录下的历史会话列表，并可通过序号选择恢复。
4. 恢复后继续提问时，LLM 使用 `{session_id}/model_history` 中的模型历史作为上下文基线。
5. 在不同项目目录执行 `/resume` 不展示其他项目的历史会话；若恢复过程中发现项目不一致，不会恢复，并提示用户移动到历史会话所在目录。
6. 现有上下文压缩、模型历史 fallback、工具调用流程不发生语义变化。
7. `go test ./...` 通过。
