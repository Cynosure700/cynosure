# 模型回答兜底机制设计文档

## 1. 背景

当前主 Agent 的回答链路在 `internal/agent/runtime/conversation_flow.go` 中完成：每轮请求前压缩 `state.ModelHistory`，调用 `runModelRoundWithRecovery` 处理输出截断与 413 上下文溢出，最终在非 `tool_calls` 时进入 Stop 钩子、追加最终 assistant、落库并触发记忆收尾。

子 Agent 的链路在 `internal/agent/runtime/subagent.go` 中完成：`runSubagentLoop` 使用 fresh message list，按子 Agent 类型设置工具集与最大轮数，每轮请求前执行子 Agent 四层压缩。当前当循环达到最大轮数后直接返回 `subagent exceeded max rounds`，父 Agent 得到的是工具错误而不是子 Agent 已完成工作的总结。

本需求优化两个边界场景：

1. 最终回答的 `content` 为空时，追加一条“请输出最终可见答案”类提示，并重试一次。
2. 子 Agent 达到最大轮数时，追加一条“请基于历史会话进行总结输出”类提示，让子 Agent 产出历史总结，避免向父 Agent 返回误导性的执行错误。

## 2. 目标

1. 主 Agent 只在“最终回复”为空时触发一次兜底重试，不影响工具调用轮、截断续写、413 压缩、记忆提取和历史落库策略。
2. 子 Agent 只在达到最大轮数后触发一次总结兜底，基于已有子 Agent 历史输出可见总结。
3. 兜底提示作为运行时内部提示进入模型历史，不作为用户消息展示到 TUI。
4. 不新增用户配置项，不改变现有最大轮数、超时、压缩阈值、工具审批、子 Agent 类型和工具集策略。

## 3. 非目标

1. 不改变模型 SDK、流式事件协议或 TUI 展示协议。
2. 不扩大主 Agent 或子 Agent 的工具权限。
3. 不把空回答兜底做成无限重试或多阶段反思。
4. 不改变 `fallbackAssistantContent` 的现有含义；兜底失败后仍允许现有 `(no response)` 兜底生效。

## 4. 方案对比

### 4.1 推荐方案：运行时隐式追问

在运行时检测边界场景，并向 `state.ModelHistory` 追加一条内部 `user` 消息后重试。该消息不写入展示历史 `state.History`，因此用户界面不会显示自救提示。

优点：

1. 改动面集中在 `conversation_flow.go` 与 `subagent.go`。
2. 复用现有压缩、截断续写、413 恢复、日志和模型调用逻辑。
3. 不污染用户可见历史，同时下一次 LLM 请求能看到补救提示。

缺点：

1. 模型历史会包含一条内部补救提示，但这符合“真实发送给模型的消息线”语义。

### 4.2 备选方案：在系统提示词中长期加入规则

在系统提示词中要求模型永远输出最终可见答案、子 Agent 达到边界时总结。

优点：实现简单。

缺点：无法精准识别运行时边界；会增加每轮提示词负担；对“达到最大轮数”这类 runtime 状态没有可靠感知。不推荐。

### 4.3 备选方案：返回固定本地文案

当空回答或子 Agent 超轮时，由本地代码直接返回固定文案。

优点：不增加一次模型调用。

缺点：无法基于历史会话总结，也不能回答用户问题；容易产生没有信息量的错误兜底。不推荐。

## 5. 详细设计

### 5.1 主 Agent 空最终回答重试

在 `RespondToConversation` 中增加一个本轮局部布尔值，例如 `retriedEmptyFinalAnswer := false`。

每次模型返回后，维持现有顺序：

1. `runModelRoundWithRecovery` 仍先处理截断续写与 413 恢复。
2. 仍累计 `ReasoningContent`。
3. 仍先判断工具调用轮。

只在以下条件同时成立时触发空最终回答重试：

1. `finishReason != "tool_calls"`。
2. `len(msg.ToolCalls) == 0`。
3. `strings.TrimSpace(msg.Content) == ""`。
4. `retriedEmptyFinalAnswer == false`。

触发后：

1. 设置 `retriedEmptyFinalAnswer = true`。
2. 向 `state.ModelHistory` 追加一条内部 `user` 消息，内容为：

```text
请输出最终可见答案。不要调用工具，不要复述内部过程，直接基于当前上下文回答用户的问题；如果无法完成，也要清楚说明原因和下一步建议。
```

3. `continue` 进入下一轮。下一轮仍会先执行现有上下文压缩，再构造请求。

若重试后仍为空，则不再重试，继续走现有 Stop 钩子和 `fallbackAssistantContent` 兜底，保证策略上限明确。

### 5.2 子 Agent 最大轮数总结兜底

在 `runSubagentLoop` 的 `for round := 1; round <= maxRounds; round++` 结束后，不再直接返回 `subagent exceeded max rounds`。改为追加一次内部总结提示并发起一次总结请求。

总结提示内容为：

```text
请基于历史会话进行总结输出。不要继续调用工具，直接总结已完成的观察、关键结论、仍未解决的问题，以及建议父 Agent 下一步如何处理。
```

总结请求的关键约束：

1. 使用当前 `state.ModelHistory` 作为历史基线，先追加内部 `user` 总结提示。
2. 发起请求前仍调用 `compressSubagentContextBeforeLLM`，保持子 Agent 四层压缩策略不变。
3. 请求的 `Tools` 设置为 `nil` 或空列表，防止模型继续工具循环。
4. `MaxTokens` 使用现有 `defaultMaxTokens`，并继续通过 `runModelRoundWithRecovery` 复用截断续写与 413 恢复。
5. 如果总结请求成功，即使内容为空，也把该消息返回给 `runSubagent`，由现有 `fallbackAssistantContent` 处理最终工具结果。
6. 如果总结请求失败，返回带原始语义的错误，例如 `subagent exceeded max rounds and summary fallback failed: ...`。

该兜底不改变 `defaultSubagentMaxRounds = 300`、`exploreSubagentMaxRounds = 50`、`subAgentTurnTimeout = 1 * time.Hour`，也不改变子 Agent 在正常轮次内的工具审批和压缩行为。

### 5.3 辅助函数

为避免在主流程和子 Agent 中散落硬编码，新增小型 helper，位置可放在 `conversation_flow.go` 或同包新文件中：

```go
const emptyFinalAnswerRetryPrompt = `请输出最终可见答案。不要调用工具，不要复述内部过程，直接基于当前上下文回答用户的问题；如果无法完成，也要清楚说明原因和下一步建议。`

const subagentMaxRoundsSummaryPrompt = `请基于历史会话进行总结输出。不要继续调用工具，直接总结已完成的观察、关键结论、仍未解决的问题，以及建议父 Agent 下一步如何处理。`

func appendInternalUserPrompt(state *LoopState, content string) {
	state.ModelHistory = append(state.ModelHistory, storage.Message{
		ID:             state.NextMessageID(),
		ConversationID: state.Conversation.ID,
		UserID:         state.User.ID,
		Role:           "user",
		Content:        content,
	})
}
```

该 helper 只追加到 `ModelHistory`，不追加到 `History`。原因是这类提示属于运行时控制消息，不是用户真实输入；同时 `ModelHistory` 本来就是“真实发送给模型的消息线”，需要记录该提示以保证下一次请求上下文完整。

## 6. 数据流

### 6.1 主 Agent

```text
LLM 返回非工具最终消息
  -> content 为空且本轮未重试
  -> ModelHistory 追加内部 user 兜底提示
  -> continue
  -> 现有压缩链
  -> LLM 再请求一次
  -> 正常 Stop / 落库 / 记忆收尾
```

### 6.2 子 Agent

```text
达到 maxRounds
  -> ModelHistory 追加内部 user 总结提示
  -> 子 Agent 四层压缩
  -> 无工具总结请求
  -> 返回总结消息给 runSubagent
  -> 父 Agent 收到 Subagent completed + Summary
```

## 7. 测试策略

### 7.1 主 Agent 空最终回答

新增或调整 runtime 单测：

1. 第一轮返回 `finishReason=stop` 且 `Content=""`，第二轮返回 `Content="final answer"`。
2. 断言 `RespondToConversation` 返回 `final answer`。
3. 断言 LLM 被调用两次。
4. 断言第二次请求包含内部提示 `请输出最终可见答案`。
5. 断言展示历史中没有这条内部提示。

补充边界用例：

1. 工具调用轮 `Content=""` 且 `finishReason=tool_calls` 时不触发空最终回答重试。
2. 重试一次后仍为空时不第三次调用，继续返回现有 `(no response)` 兜底。

### 7.2 子 Agent 最大轮数总结

新增或调整 runtime 单测：

1. 使用较小 `maxRounds` 调用 `runSubagentLoop`，让模型每轮都返回工具调用直到达到上限。
2. 上限结束后，断言额外发起一次总结请求。
3. 断言总结请求包含 `请基于历史会话进行总结输出`。
4. 断言总结请求的 `Tools` 为空，避免继续工具调用。
5. 断言 `runSubagent` 返回 `Subagent completed.\n\nSummary:\n...`，而不是 `subagent exceeded max rounds`。

## 8. 风险与缓解

1. 风险：空回答重试误伤工具调用轮。缓解：仅在非 `tool_calls` 且没有工具调用时触发。
2. 风险：内部提示污染 TUI 展示历史。缓解：只写 `state.ModelHistory`，不写 `state.History`。
3. 风险：子 Agent 总结兜底继续调用工具导致循环。缓解：总结请求 `Tools` 为空。
4. 风险：兜底请求绕过现有压缩或截断恢复。缓解：继续复用 `compressSubagentContextBeforeLLM` 与 `runModelRoundWithRecovery`。
5. 风险：重试次数失控。缓解：主 Agent 空回答只重试一次；子 Agent 超轮只总结一次。

## 9. 实施范围

预计修改文件：

1. `internal/agent/runtime/conversation_flow.go`：主 Agent 空最终回答一次重试；补充提示词常量或调用 helper。
2. `internal/agent/runtime/subagent.go`：子 Agent 达到最大轮数后的总结兜底。
3. `internal/agent/runtime/runtime_test.go`：补充主 Agent 与子 Agent 的单元测试。

不需要修改：

1. `assets/system_prompt.md` 与 `internal/agent/prompt.go`：本需求是运行时边界处理，不是长期身份/工具规则。
2. 压缩策略实现和阈值。
3. TUI 事件协议。
4. 配置文件与 allowlist。

## 10. 自检

1. 本设计覆盖了两个需求点：空最终回答重试一次、子 Agent 最大轮数总结输出。
2. 所有兜底都有明确触发条件和次数上限。
3. 设计不改变既有压缩、截断续写、413 恢复、工具审批、记忆提取、历史落库和 TUI 展示策略。
4. 提示词放在运行时代码中，符合该需求的动态边界处理属性。
5. 未引入配置项、工具权限变化或新的长期系统提示词规则。
