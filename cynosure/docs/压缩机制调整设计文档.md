# 压缩机制调整设计文档

## 一、背景与目标

当前 Cynosure 的上下文压缩分两条路径：

- **主动压缩（proactive）**：在每轮 LLM 调用**之前**运行五层策略链
  （`ToolResultCompression → MessageWindowCompression → RecentToolResultRetention
  → ConversationMemory → FullHistorySummarization`），把 `state.ModelHistory`
  压到 token 预算之内。
- **被动压缩（reactive）**：仅当主模型请求返回 HTTP 413（上下文溢出）时，带外调用
  一次 `ReactiveCompactStrategy`（摘要"除最后一条外的全部历史" + 保留 token 预算内
  的近期尾部），且当前实现用 `!compacted` 保证**一轮只压一次**。

本次调整围绕四个需求，对压缩的**时机**与**被动压缩策略**做定向改造，其余能力保持不变：

1. **ReactiveCompact 提示词更激进**：摘要更紧凑。
2. **413 统一触发 ReactiveCompact**：主模型 413 **和** 摘要 LLM 调用自身上下文超限，
   都触发 ReactiveCompact。
3. **压缩时机调整**：主动压缩改为在**每轮回复后、记忆提取前**执行；此外，在**进入对话
   循环前**先执行一次压缩（避免用户第一句就因历史过大而卡住）。
4. **ReactiveCompact 策略重写**：依次从**最旧的对话轮**开始剥离，每次剥离剩余对话轮的
   **20%**（至少 1 个对话轮），对新剥离的部分做摘要，重组后的消息 =
   `系统提示词 + system-reminder + 对话轮摘要 + 未摘要的消息`。

### 非目标（明确不改动）

- 五层策略链本身的算法与阈值不变。
- 子 Agent 四层压缩链（`NewSubagentCompressor`）不变。
- 记忆提取 / 会话记忆 / 断点机制不变。
- Token 估算器（`DefaultTokenEstimator`）、`llm.IsContextOverflow`（413 判定）不变。
- 逐字展示历史 `state.History` 永不被压缩污染的既有契约不变。

## 二、核心概念：什么是"一个对话轮"（conversation turn）

需求 4 中"对话轮"定义为：**从用户发送信息的第一条（真实 `user` 消息）开始，到模型最终
回复为止**的一整段消息。落到 `state.ModelHistory` 的消息序列上，一个对话轮 = 从一条
**真实用户 `user` 消息**开始，直到下一条真实用户 `user` 消息之前的所有消息，含：

- 该用户消息；
- assistant 回复（含 `tool_calls`）；
- tool 结果消息；
- 循环内部注入的 `user` 提示（如空回复重试 `emptyFinalAnswerRetryPrompt`、续写提示等——
  它们不是真实用户输入，归入当前轮，不单独成轮）。

### 轮边界识别规则

由于内部注入的 `user` 消息（`appendInternalUserPrompt`）与真实用户输入都是 `role=user`，
需要区分。识别策略：

- **首个 `user` 消息**始终是一轮的起点。
- 后续 `user` 消息中，`Content` 以 `<system-reminder>` 包裹的（内部注入的续写/重试提示等，
  如 `emptyFinalAnswerRetryPrompt` 经 `wrapSystemReminder` 注入）**不作为新轮起点**，归入
  当前轮；其余 `user` 消息作为新轮起点。
- 若历史以 `system` / `<conversation-summary>` 开头（上一次压缩产物），这些前缀消息不属于
  任何"对话轮"，在剥离时被视为已固定的"摘要头"单独处理（见第五节）。

> **边界稳健性说明**：进入 `ModelHistory` 的内部注入 `user` 消息主要是
> `emptyFinalAnswerRetryPrompt`（已用 `<system-reminder>` 包裹，识别为非新轮）。子 Agent 的
> `subagentMaxRoundsSummaryPrompt` 未加该包裹，会被识别为一个新轮起点；但它总是最新一条
> 消息，而剥离是**从最旧轮开始**，因此永远不会被误剥，不影响正确性。`truncationResumePrompt`
> 与 todo 提醒只追加到 `state.Messages`（发送态），不进入 `state.ModelHistory`，不影响轮切分。
> 即便个别注入消息导致轮数统计有 ±1 偏差，"每次剥离剩余 20%、至少 1 轮、最旧优先"的语义
> 仍然成立，不会剥错或漏剥最旧内容。

> 说明：ReactiveCompact 作用于 `state.ModelHistory`（真实模型线），其中的 system 提示词与
> system-reminder 是通过 `buildOpenAIMessagesWithReminder` 在发送时才拼到最前的，不在
> `ModelHistory` 内。因此轮切分只需在 `ModelHistory` 上按上述规则进行。

## 三、压缩时机调整（需求 3）

### 现状

`RespondToConversation` 的 for 循环**顶部**调用 `compressContextBeforeLLM`，即每轮"调 LLM
之前"压缩。记忆提取发生在：

- 中间 tool_calls 轮结束：`maybeUpdateSessionMemoryMidLoop`；
- 最终回复轮结束：`scheduleMemoryWork`（其中 `extractMemories` + 会话记忆更新）。

### 目标时机

保持"每个 LLM round 结束都压缩一次"的语义，但把执行点从"下一轮开头"前移到"本轮结尾、
记忆提取之前"，并新增"进入循环前一次"：

1. **进入对话循环前（pre-pass）**：在 `state` 构建完成、`for` 循环开始**之前**，执行一次
   主动压缩，把 `state.ModelHistory` 压到预算内并写回。这样即便用户第一句话面对的历史
   已经很大，也不会在第一轮就 413/卡住。
2. **每轮回复后、记忆提取前**：
   - **中间 tool_calls 轮**：`executeToolCallBatch` 返回后、
     `maybeUpdateSessionMemoryMidLoop` 之前，执行主动压缩并写回 `state.ModelHistory`。
   - **最终回复轮**：拿到最终 assistant 并 `append` 进 `state.ModelHistory` 后、
     `scheduleMemoryWork` 之前，执行主动压缩并写回 `state.ModelHistory`。

### 执行点迁移示意

```
进入循环前：  compressContextBeforeLLM(pre-pass) → 写回 ModelHistory
for {
    // 循环顶部不再压缩（原 compressContextBeforeLLM 调用移除）
    重算 token 用量 / emitMeta
    调 LLM（runModelRoundWithRecovery）
    if 最终回复:
        追加最终 assistant 到 ModelHistory
        >>> compressContextBeforeLLM(本轮结尾) → 写回 ModelHistory   // 记忆提取前
        scheduleMemoryWork(...)   // 记忆提取
        return
    追加 assistant + 执行工具（tool 结果进 ModelHistory）
    >>> compressContextBeforeLLM(本轮结尾) → 写回 ModelHistory        // 记忆提取前
    maybeUpdateSessionMemoryMidLoop(...)   // 记忆提取
}
```

### 关键约束

- **记忆提取用的 `state.ModelHistory` 与最终落库一致**：压缩发生在记忆提取之前，因此
  记忆提取拿到的是"本轮压缩后的真实消息线"。这符合现有"记忆提取数据源 = 压缩后的
  ModelHistory"的设计（`scheduleMemoryWork` 注释已述）。
- **发送态与内存态一致**：每次压缩后重建 `state.Messages =
  buildOpenAIMessagesWithReminder(...)`，保证下一轮发送的就是压缩后的历史。
- **token 用量估算**：`state.LastContextTokens` 的计算点保持在"调 LLM 之前"（循环顶部
  重算），因为此时 `ModelHistory` 已是上一轮结尾压缩后的结果，估算依然准确。
- **仅作用于主 Agent 循环**：本节的时机迁移（pre-pass + 记忆提取前压缩）只改
  `RespondToConversation`（主 Agent）。子 Agent（`runSubagentLoop`）没有记忆提取，其
  主动压缩仍在循环顶部执行，保持不变，避免不必要的范围扩散。（reactive 策略重写与 413
  循环因共用代码路径会自然覆盖子 Agent，见第四节场景 C。）

## 四、413 统一触发 ReactiveCompact（需求 2）

### 场景 A：主模型请求 413

`runModelRoundWithRecovery` 现有分支保留，但去掉"只压一次"的 `!compacted` 限制：

- 每次捕获 `llm.IsContextOverflow(err)` → 调用一次 `reactiveCompact`（累进剥离，见第五节）
  → 从压缩后历史重建请求并重试。
- 若再次 413 → 再触发一次 `reactiveCompact`（继续多剥离一批），如此**循环**，直到：
  - 请求成功；或
  - `ModelHistory` 已剥到只剩最少 1 个对话轮仍 413 → 返回错误交由上层兜底（现有边界）。
- 为防御异常（例如剥无可剥仍持续 413），增加一个保护上限（如最多 `N` 次 reactive 循环，
  `N` 取一个足够大的常量，例如与最大轮数同量级），超限则返回错误。

### 场景 B：摘要 LLM 调用自身 413

这是新增覆盖点。ReactiveCompact 内部调用摘要 LLM（`summarizeHistoryForContext`）对
"新剥离的最旧轮"做摘要时，摘要请求本身可能因输入过大而 413。处理方式为**统一循环**（与
用户确认一致）：

- 摘要调用返回 `IsContextOverflow` → **不放弃摘要**，而是"再剥离 20% 最旧轮"以缩小本次
  摘要输入，然后重试摘要；
- 循环直到摘要成功，或已剥到只剩最少 1 轮仍无法摘要 → 返回错误交由上层兜底。

> 统一性：无论 413 来自"主模型请求"还是"摘要调用"，最终动作都是"再剥离 20% 最旧对话轮
> → 重摘要 → 重试"，形成单一收敛循环。

### 场景 C：子 Agent 的 413

子 Agent 与主 Agent 共用 `runModelRoundWithRecovery → reactiveCompact` 路径（见
`subagent.go`），因此本次对 reactive 循环的改造同样作用于子 Agent。累进状态
`reactiveState` 挂在各自的 `LoopState` 上（父/子相互独立），子 Agent 的一次运行内自成一套
累进游标，进入时重置，不与父 Agent 串扰。子 Agent 的**主动**压缩链仍是四层
（`NewSubagentCompressor`，不含会话记忆），不受本次时机迁移之外的改动。

## 五、ReactiveCompact 策略重写（需求 4）

### 5.1 现状

`ReactiveCompactStrategy.Apply` 一次性摘要"除最后一条消息外的全部历史"，并按 token 预算
从尾部回填近期消息，丢弃 reasoning_content。它无状态、一次成型。

### 5.2 目标行为：按对话轮渐进剥离

改为**有状态的累进剥离**：

1. 把当前 `RequestHistory` 按第二节规则切分为对话轮列表 `turns`（外加可能存在的"摘要头"
   前缀，即上一次压缩产生的 `system` + `<conversation-summary>` 两条消息）。
2. 计算本次新剥离轮数：`strip = ceil(len(剩余未剥离轮) × 20%)`，且 `strip >= 1`。
   从**最旧**的未剥离轮开始取 `strip` 个作为"本次新剥离轮"。
3. **重摘要（合并摘要）**：把"已有摘要文本 + 本次新剥离轮的原始消息"一起作为输入，调用
   摘要 LLM（使用第六节的激进 prompt）生成**一段新的整合摘要**，替换旧摘要。
   （用户确认：合并方式为"重摘要"，即旧摘要与新剥离内容一起喂给摘要器，产出连贯的单段
   摘要，而非简单拼接。）
4. **重组历史**：
   ```
   系统提示词 + system-reminder   （由 buildOpenAIMessagesWithReminder 在发送时拼接）
   + <conversation-summary> 合并摘要 </conversation-summary>
   + 未剥离的对话轮消息（逐字保留，经 repairToolCallBoundaries 修复配对）
   ```
   即 `RequestHistory = buildSummaryHistory(合并摘要, 未剥离轮消息)`。
5. 对保留的消息执行 `dropReasoningContent`（续写不需要 reasoning_content，回收空间）。
6. **摘要 413 处理**：步骤 3 若摘要调用 413，则回到步骤 2 增大 `strip`（多剥一批 20%）后
   重试摘要，直到成功或只剩 1 轮。
7. **收敛边界**：若未剥离轮已只剩 1 轮仍需继续（外层再次 413），本策略无法进一步剥离，
   返回原样交由上层兜底。

### 5.3 累进状态的承载

渐进剥离需要跨多次 413 记住"已剥离到第几轮 / 当前摘要文本"。设计：

- 在 `compression.Request` 增加两个字段（仅 ReactiveCompact 使用）：
  - `ReactiveState *ReactiveCompactState`：包含 `StrippedTurns int`（已剥离的对话轮数）
    与 `Summary string`（当前累积摘要）。
- 在运行时侧 `LoopState` 持有一个 `reactiveState`，每次 `reactiveCompact` 调用时传入、
  用策略产出的新状态写回。
  - **新一轮真实用户输入到来时重置** `reactiveState`（新的一轮对话从"未剥离"重新开始
    累进），避免旧状态串轮。
  - 或者更简单：`reactiveState` 生命周期与单次 `RespondToConversation` 调用绑定，进入
    时清空。（本设计采用与单次 turn 绑定的方案。）

> 备选（更无状态）：每次都从头按"累计剥离比例"（`已剥离轮数 = ceil(总轮数 × 累计比例)`）
> 重新切分并对全部已剥离轮重摘要。用户已选择"渐进剥离 + 合并摘要（推荐）"，故采用 5.2 的
> 增量剥离 + 重摘要方案，避免每次都重摘全部已剥离内容导致输入膨胀。

### 5.4 复用与保留

- 复用 `buildSummaryHistory`、`repairToolCallBoundaries`、`dropReasoningContent`。
- 保留"`system` 摘要前导 + `<conversation-summary>` 用户消息"的两条消息结构
  （`summarySystemPreamble`）。
- 移除旧的"按 token 预算回填尾部"逻辑（`selectReactiveTail`），因为新策略以"对话轮"为
  剥离单位，保留的就是"未剥离的完整轮"，不再需要 token 预算尾部裁剪。

## 六、激进摘要 Prompt（需求 1）

### 现状

摘要统一使用 `assets/prompts/context_summary.md`（通用结构化简报，五个小节）。

### 改造

- 新增 `assets/prompts/reactive_compact_summary.md`：在通用摘要基础上强调**极度精简**——
  只保留续写任务所必需的最小事实（文件路径、函数名、命令、关键报错/结论、明确的待办），
  删除过程性叙述、寒暄、重复表述，目标 token 更小（对齐 `reactiveSummaryTargetTokens`
  的激进预算）。仍保留"遇到 `<persisted-output>` / `[Earlier result compacted]` 标记要
  说明可重取/需重跑"的规则。
- `FunctionalPrompts` 增加字段 `ReactiveCompactSummary string`，在
  `functional_prompts.go` 的加载表与 `withDefaults` 中登记 `reactive_compact_summary`。
- `assets/embed.go` 用 `//go:embed prompts/*.md` glob 加载，无需改动。
- 摘要器：`summarizeHistoryForContext` 增加"选择哪个 system prompt"的能力。方案是在
  `compression.SummaryRequest` 增加一个标记（如 `Aggressive bool` 或 `PromptKind`），
  由 ReactiveCompact 传入 `true`，摘要器据此选用 `ReactiveCompactSummary`；
  FullHistorySummarization 仍用通用 `ContextSummary`。

## 八、边界与失败处理

- **只剩 1 轮仍 413**：ReactiveCompact 无法继续剥离，返回原样；`runModelRoundWithRecovery`
  在 reactive 循环达到保护上限或剥无可剥后，返回错误交由上层（现有边界）处理。
- **摘要 LLM 不可用 / 返回空**：`summarizeHistoryForContext` 已有空摘要报错；ReactiveCompact
  透传错误，主动压缩链的 FullHistorySummarization 兜底逻辑不受影响。
- **`RequestHistory < 2`**：无可剥离/摘要内容，直接返回（现有短路保留）。
- **累进状态串轮**：`reactiveState` 与单次 `RespondToConversation` 绑定，进入时重置，避免
  跨 turn 携带旧的已剥离游标。
- **pre-pass 出错**：与循环内压缩一致，出错则 `return err`（与现有 `compressContextBeforeLLM`
  错误处理一致）。

## 九、测试计划

### 保持通过（回归）
- `context_compression_test.go`：压缩不污染 `state.History` / `ModelHistory` 写回幂等——
  时机迁移后仍成立。
- `compression/*_test.go`：五层策略链既有单测不受影响。

### 新增单测
1. **轮切分**：真实 user / 内部注入 `<system-reminder>` user / tool 结果混排，验证轮边界
   识别正确（内部注入不新起一轮）。
2. **渐进剥离比例**：给定 N 轮，验证首次剥离 `ceil(N×20%)` 且 ≥1，后续每次对剩余轮再取
   20%，最终收敛到最少 1 轮。
3. **重组结构**：剥离后 `RequestHistory` = `system 前导 + <conversation-summary> + 未剥离
   轮消息`，且未剥离轮的 tool_calls 配对完整、reasoning_content 被清除。
4. **合并（重）摘要**：验证第二次剥离时，摘要器输入包含"旧摘要 + 新剥离轮"，产出替换旧摘要。
5. **主模型 413 累进循环**：注入连续 413 的假 LLM，验证每次 413 都触发一次更深的剥离，直到
   成功或收敛边界；去掉 `!compacted` 后不再"只压一次"。
6. **摘要调用 413**：摘要 LLM 前几次返回 413、随输入缩小后成功，验证"再剥离 20% 重试摘要"
   的统一循环，且最终摘要成功。
7. **时机顺序**：验证 pre-pass 在进入循环前执行；每轮压缩在记忆提取（`maybeUpdateSessionMemoryMidLoop`
   / `scheduleMemoryWork`）**之前**执行。
8. **激进 prompt 选择**：ReactiveCompact 走 `ReactiveCompactSummary`，FullHistory 走
   `ContextSummary`。
