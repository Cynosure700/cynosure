# 压缩机制调整设计文档

## 一、背景与目标

当前 Cynosure 的上下文压缩分两条路径：

- **主动压缩（proactive）**：在每轮 LLM 调用**之前**运行五层策略链
  （`ToolResultCompression → MessageWindowCompression → RecentToolResultRetention
  → ConversationMemory → FullHistorySummarization`），把 `state.ModelHistory`
  压到 token 预算之内。
- **被动压缩（reactive）**：当前实现仅当主模型请求返回 HTTP 413（上下文溢出）时，带外调用
  一次 `ReactiveCompactStrategy`（摘要"除最后一条外的全部历史" + 保留 token 预算内
  的近期尾部），且用 `!compacted` 保证**一轮只压一次**。注意：主动压缩链里
  `FullHistorySummarizationStrategy` 的摘要 LLM 调用若自身 413，当前会直接向上抛错、
  中断本轮，**不会**触发 reactive。

本次调整围绕三个需求，对**被动压缩策略**做定向改造，其余能力（含压缩时机）保持不变：

1. **ReactiveCompact 提示词更激进**：摘要更紧凑。
2. **413 触发 ReactiveCompact**：**主模型请求 413** 与 **主动压缩链中
   `FullHistorySummarizationStrategy` 的摘要调用 413**，两者都触发 ReactiveCompact。
   ReactiveCompact 自身摘要调用若再发生 413，则**直接返回错误**（不再收缩重试）。
3. **ReactiveCompact 策略重写**：ReactiveCompact 是一次「单次压缩」，其内部依次从**最旧的
   对话轮**开始剥离，每次剥离剩余对话轮的 **20%**（至少 1 个对话轮）。**每次剥离后检查
   token 阈值：一旦重组后的历史回到上下文预算内，就停止继续剥离并成功返回**；**最多剥离
   3 次**——若 3 次后（或已无更多对话轮可剥）仍超出上下文预算，则**返回错误**。重组后的
   消息 = `系统提示词 + system-reminder + 对话轮摘要 + 未摘要的消息`。

> **压缩时机不变**：主动压缩仍在**每次请求前**（主 Agent / 子 Agent 各自 for 循环顶部）
> 执行 `compressContextBeforeLLM`，写回 `state.ModelHistory`。本次不改动压缩时机。

### 非目标（明确不改动）

- 五层策略链本身的算法与阈值不变。
- 子 Agent 四层**主动**压缩链（`NewSubagentCompressor`）不变；仅其 **reactive 压缩策略**
  与主 Agent 对齐（见第四节场景 C）。
- 记忆提取 / 会话记忆 / 断点机制不变。
- Token 估算器（`DefaultTokenEstimator`）、`llm.IsContextOverflow`（413 判定）不变。
- 逐字展示历史 `state.History` 永不被压缩污染的既有契约不变。

## 二、核心概念：什么是"一个对话轮"（conversation turn）

需求 4 中"对话轮"定义为：**从用户发送信息的第一条（真实 `user` 消息）开始，到模型最终
回复为止**的一整段消息。落到 `state.ModelHistory` 的消息序列上，一个对话轮 = 从一条
**真实用户 `user` 消息**开始，直到下一条真实用户 `user` 消息之前的所有消息，含：

- 该用户消息；
- assistant 回复（含 `tool_calls`）；
- tool 结果消息；
- 循环内部注入的 `user` 提示（如空回复重试 `emptyFinalAnswerRetryPrompt`、续写提示等——
  它们不是真实用户输入，归入当前轮，不单独成轮）。

### 轮边界识别规则

由于内部注入的 `user` 消息（`appendInternalUserPrompt`）与真实用户输入都是 `role=user`，
需要区分。识别策略：

- **首个 `user` 消息**始终是一轮的起点。
- 后续 `user` 消息中，`Content` 以 `<system-reminder>` 包裹的（内部注入的续写/重试提示等，
  如 `emptyFinalAnswerRetryPrompt` 经 `wrapSystemReminder` 注入）**不作为新轮起点**，归入
  当前轮；其余 `user` 消息作为新轮起点。
- 若历史以 `system` / `<conversation-summary>` 开头（上一次压缩产物），这些前缀消息不属于
  任何"对话轮"，在剥离时被视为已固定的"摘要头"单独处理（见第五节）。

> **边界稳健性说明**：进入 `ModelHistory` 的内部注入 `user` 消息主要是
> `emptyFinalAnswerRetryPrompt`（已用 `<system-reminder>` 包裹，识别为非新轮）。子 Agent 的
> `subagentMaxRoundsSummaryPrompt` 未加该包裹，会被识别为一个新轮起点；但它总是最新一条
> 消息，而剥离是**从最旧轮开始**，因此永远不会被误剥，不影响正确性。`truncationResumePrompt`
> 与 todo 提醒只追加到 `state.Messages`（发送态），不进入 `state.ModelHistory`，不影响轮切分。
> 即便个别注入消息导致轮数统计有 ±1 偏差，"每次剥离剩余 20%、至少 1 轮、最旧优先"的语义
> 仍然成立，不会剥错或漏剥最旧内容。

> 说明：ReactiveCompact 作用于 `state.ModelHistory`（真实模型线），其中的 system 提示词与
> system-reminder 是通过 `buildOpenAIMessagesWithReminder` 在发送时才拼到最前的，不在
> `ModelHistory` 内。因此轮切分只需在 `ModelHistory` 上按上述规则进行。

## 三、压缩时机（保持不变）

本次**不改动主动压缩的时机**。主动压缩仍在每次请求前执行，与现状一致：

- 主 Agent：`RespondToConversation` 的 for 循环**顶部**调用 `compressContextBeforeLLM`，
  把 `state.ModelHistory` 压到预算内并写回，随后据此重建 `state.Messages`、重算
  `state.LastContextTokens` 并发起 LLM 请求。
- 子 Agent：`runSubagentLoop` 的 for 循环顶部调用 `compressSubagentContextBeforeLLM`
  （四层链，不含会话记忆），语义相同。

记忆提取时机也不变（中间 tool_calls 轮的 `maybeUpdateSessionMemoryMidLoop`、最终回复轮的
`scheduleMemoryWork`），其数据源仍为压缩后的 `state.ModelHistory`。

本次仅新增/调整**被动压缩（reactive）**的触发与策略（见第四、五节），主动压缩流程原样保留。

## 四、413 触发 ReactiveCompact（需求 2）

ReactiveCompact 有两个触发来源。它是一次「单次压缩」：一次调用内部完成最多 3 次剥离，
满足 token 阈值即提前成功返回；若 3 次后（或已无更多对话轮可剥）仍超出上下文预算，则
**返回错误**。ReactiveCompact 内部的摘要 LLM 调用若自身失败（含 413），也**直接返回错误**，
不做收缩重试。

### 场景 A：主模型请求 413

`runModelRoundWithRecovery` 保留"只压一次"的 `!compacted` 单发语义：

- 捕获 `llm.IsContextOverflow(err)` 且尚未压缩过（`!compacted`）→ 调用**一次**
  `reactiveCompact`（其内部完成最多 3 次剥离，见第五节）。
  - 若 `reactiveCompact` 返回错误（内部摘要失败，或 3 次剥离后仍超预算）→ 直接返回错误
    交由上层兜底。
  - 否则置位 `compacted` → 从压缩后历史重建请求并**重试一次**。
- 若压缩后重试仍 413 → 因 `compacted` 已置位，不再重复触发 reactive，直接返回错误交由
  上层兜底（现有边界）。
- ReactiveCompact 的"最多 3 次剥离 + 满足预算即停 + 超限报错"完全在其单次调用内收敛，
  外层无需循环。

### 场景 B：主动压缩链 `FullHistorySummarizationStrategy` 摘要调用 413

这是本次**新增**的触发来源。主动压缩（每轮结尾）执行到兜底层
`FullHistorySummarizationStrategy` 时，会调用摘要 LLM 对历史做摘要；该摘要请求本身可能因
输入过大而 413。改造前它会直接抛错中断本轮；改造后：

- `compressContextBeforeLLM` 捕获到压缩过程返回 `llm.IsContextOverflow` 时 → 转而调用一次
  `reactiveCompact`（单次压缩，内部最多剥离 3 次），用剥离后的结果作为本轮压缩产物。
- 若 `reactiveCompact` 返回错误（内部摘要 413，或 3 次剥离后仍超预算）→ 返回错误交由上层
  兜底。

> 实现要点：`FullHistorySummarizationStrategy` 的摘要错误需能被 `llm.IsContextOverflow`
> 识别。当前 `summarizeHistoryForContext` 透传底层 LLM 客户端错误（`*llm.APIError`），
> `IsContextOverflow` 可直接判定，无需改动 413 判定逻辑；压缩链把该错误原样上抛即可。

### ReactiveCompact 自身摘要 413 的处理

ReactiveCompact 在对"新剥离的最旧轮"做摘要时，其摘要 LLM 调用若自身返回 413（或任何错误）：

- **直接返回错误**（不"收缩本次摘要输入后重试"，也不吞掉错误）。
- 该错误上抛：
  - 若来自场景 A（主模型 413 后的 reactive）→ `runModelRoundWithRecovery` 收到错误后返回，
    交上层兜底。
  - 若来自场景 B（FullHistory 413 后的 reactive）→ `compressContextBeforeLLM` 返回错误，
    交上层兜底。

### 场景 C：子 Agent 的 reactive 压缩

子 Agent 与主 Agent 共用 `runModelRoundWithRecovery → reactiveCompact` 路径（见
`subagent.go`），因此**新的 reactive 策略（单次压缩、按对话轮渐进剥离、激进摘要 prompt）
对子 Agent 同样生效**，满足"子 Agent 压缩策略与主 Agent 一致"。ReactiveCompact 无跨调用
状态（3 次剥离与预算判定都在单次调用内完成），父/子天然隔离，互不串扰。

**子 Agent 的主动压缩时机不变**：仍在 `runSubagentLoop` 循环顶部执行，且仍用四层
`NewSubagentCompressor`（不含 ConversationMemory，保留"不注入父会话记忆"的既有契约）。
子 Agent 主动压缩链走到 `FullHistorySummarizationStrategy` 摘要 413 时，同样按场景 B 转
reactive（因 `compressSubagentContextBeforeLLM` 复用相同的 413→reactive 处理）。

## 五、ReactiveCompact 策略重写（需求 3）

### 5.1 现状

`ReactiveCompactStrategy.Apply` 一次性摘要"除最后一条消息外的全部历史"，并按 token 预算
从尾部回填近期消息，丢弃 reasoning_content。它无状态、一次成型。

### 5.2 目标行为：单次压缩内部按对话轮渐进剥离

ReactiveCompactStrategy.Apply 是一次「单次压缩」，其内部循环最多 `reactiveMaxStrips`（3）次：

1. 计算预算 `budget = Estimator.ContextTokenBudget()`；`summary` 初始化为空。
2. 进入循环（最多 3 次），每次迭代：
   1. 把当前 `RequestHistory` 按第二节规则切分为对话轮列表 `turns`（开头的 `system` /
      `<conversation-summary>` 前缀不计入对话轮，会被本次重摘要重新整合）。
   2. 若 `len(turns) <= 1`（无内容或只剩 1 轮）→ **跳出循环**，由下方统一按 token 阈值
      判定成功/报错。
   3. 计算本次剥离轮数：`strip = ceil(len(turns) × 20%)`，且 `1 <= strip <= len(turns)-1`
      （至少剥 1 轮、至少留 1 轮）。从**最旧**端取 `strip` 个作为"本次新剥离轮"。
   4. **重摘要（合并摘要）**：把"已有 `summary`（若非空，作为 `<conversation-summary>`
      前置消息）+ 本次新剥离轮的原始消息"一起作为输入，调用摘要 LLM（使用第六节的激进
      prompt、`Aggressive=true`）生成一段新的整合摘要，更新 `summary`。
      - 摘要调用自身失败（含 413）→ **直接返回错误**，不做收缩重试。
   5. **重组历史**：`RequestHistory = buildSummaryHistory(summary, 未剥离轮消息)`，其中未
      剥离轮经 `repairToolCallBoundaries` 修复 tool_call 配对、并 `dropReasoningContent`
      丢弃 reasoning_content。发送时由 `buildOpenAIMessagesWithReminder` 在最前拼上系统
      提示词 + system-reminder，最终形态：
      ```
      系统提示词 + system-reminder
      + <conversation-summary> 合并摘要 </conversation-summary>
      + 未剥离的对话轮消息
      ```
   6. **token 阈值检查**：若
      `EstimateRequestTokens(SystemPrompt, RequestHistory, Tools) <= budget` → **成功返回**
      （返回 nil）。
3. 循环结束（已达 3 次，或第 2 步无更多对话轮可剥）后，再做一次 token 阈值检查：
   - 若仍 `> budget` → **返回错误**（`still over context budget after 3 strips`）；
   - 否则返回 nil（成功）。

> 关键点：只有"满足 token 阈值"才算成功；"3 次剥离后仍超预算"或"无更多对话轮可剥且仍
> 超预算"都返回错误。摘要 LLM 调用自身失败同样返回错误。

### 5.3 无跨调用状态

由于 ReactiveCompact 是「单次压缩」——3 次剥离、预算判定、摘要累积都在一次 `Apply` 调用内
完成——**不再需要跨调用的累进状态**。因此：

- 移除 `compression.Request.ReactiveState` 字段与 `ReactiveCompactState` 类型。
- 移除 `LoopState.ReactiveState` 字段及 `hooks` 包对 `compression` 的相应依赖。
- `runModelRoundWithRecovery` 恢复 `!compacted` 单发语义：一个回合内最多触发一次
  `reactiveCompact`。

### 5.4 复用与保留

- 复用 `buildSummaryHistory`、`repairToolCallBoundaries`、`dropReasoningContent`。
- 保留"`system` 摘要前导 + `<conversation-summary>` 用户消息"的两条消息结构
  （`summarySystemPreamble`）。
- 移除旧的"按 token 预算回填尾部"逻辑（`selectReactiveTail`），因为新策略以"对话轮"为
  剥离单位，保留的就是"未剥离的完整轮"，不再需要 token 预算尾部裁剪。

## 六、激进摘要 Prompt（需求 1）

### 现状

摘要统一使用 `assets/prompts/context_summary.md`（通用结构化简报，五个小节）。

### 改造

- 新增 `assets/prompts/reactive_compact_summary.md`：在通用摘要基础上强调**极度精简**——
  只保留续写任务所必需的最小事实（文件路径、函数名、命令、关键报错/结论、明确的待办），
  删除过程性叙述、寒暄、重复表述，目标 token 更小（对齐 `reactiveSummaryTargetTokens`
  的激进预算）。仍保留"遇到 `<persisted-output>` / `[Earlier result compacted]` 标记要
  说明可重取/需重跑"的规则。
- `FunctionalPrompts` 增加字段 `ReactiveCompactSummary string`，在
  `functional_prompts.go` 的加载表与 `withDefaults` 中登记 `reactive_compact_summary`。
- `assets/embed.go` 用 `//go:embed prompts/*.md` glob 加载，无需改动。
- 摘要器：`summarizeHistoryForContext` 增加"选择哪个 system prompt"的能力。方案是在
  `compression.SummaryRequest` 增加一个标记（如 `Aggressive bool` 或 `PromptKind`），
  由 ReactiveCompact 传入 `true`，摘要器据此选用 `ReactiveCompactSummary`；
  FullHistorySummarization 仍用通用 `ContextSummary`。

## 八、边界与失败处理

- **3 次剥离后仍超预算**：ReactiveCompact **返回错误**（`still over context budget after
  3 strips`）。场景 A 的 `runModelRoundWithRecovery` / 场景 B 的 `compressContextBeforeLLM`
  收到错误后交由上层（现有边界）兜底。
- **无更多对话轮可剥（只剩 1 轮）且仍超预算**：同样返回错误，交上层兜底。
- **剥离后已回到预算内**：成功返回（返回 nil），结果为
  `系统提示词 + system-reminder + 对话轮摘要 + 未摘要消息`。
- **ReactiveCompact 摘要调用失败（含 413）**：直接返回错误（不收缩重试），交上层兜底。
- **FullHistory 摘要 413 转 reactive**：主动压缩链的摘要调用 413 被 `IsContextOverflow`
  识别后转 `reactiveCompact`；reactive 成功（回到预算内）则压缩视为完成，reactive 返回
  错误（3 次后仍超预算，或自身摘要失败）则整体返回错误。
- **每轮结尾压缩出错**：出错则 `return err`（若为 FullHistory 413 则先转
  reactive 再按上述处理）。

## 九、测试计划

### 保持通过（回归）
- `context_compression_test.go`：压缩不污染 `state.History` / `ModelHistory` 写回幂等——
  压缩时机不变，仍成立。
- `compression/*_test.go`：五层策略链既有单测不受影响。

### 新增单测
1. **轮切分**：真实 user / 内部注入 `<system-reminder>` user / summary 前缀混排，验证轮边界
   识别正确（内部注入不新起一轮、前缀不计入对话轮）。
2. **满足预算即停**：小历史剥一次后即回到预算内，验证摘要器只被调用 1 次。
3. **最多 3 次后仍超预算则报错**：构造始终超预算的大历史，验证摘要器恰好被调用 3 次、
   `Apply` 返回错误。
4. **重摘要**：验证第二次剥离时摘要器输入包含上一次的 `<conversation-summary>`。
5. **重组结构 / reasoning 清除**：未剥离轮 tool_calls 配对完整、reasoning_content 被清除。
6. **摘要自身失败直接返回错误**：摘要调用返回错误时 `Apply` 返回错误且摘要只被调用 1 次
