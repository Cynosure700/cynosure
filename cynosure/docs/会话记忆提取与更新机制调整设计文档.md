# 会话记忆提取与更新机制调整 设计文档

日期：2026-06-19
范围：`cynosure/internal/agent/runtime`、`cynosure/internal/agent/runtime/compression`

## 0. 名词约定

- **会话记忆（session memory）**：即 `storage.ConversationMemory`，按会话维度随对话增量维护的"当前会话主干信息"。由 `updateConversationMemory`（`conversation_memory.go`）生成/更新，落盘到 `sessions/<id>.md`。**不注入系统提示词**，仅在上下文压缩触发"全量摘要替代"时被 `ConversationMemoryStrategy` 用作 compact_history 的替代品。
- **长期记忆（long-term memory）**：`extractMemories` 抽取的 4 类记忆（preference/feedback/project/reference）。**本次不改**。
- **compact_history**：`FullHistorySummarizationStrategy` 产出的"摘要 + 最近若干条消息"上下文。
- **断点（breakpoint）**：一次会话记忆更新所"折叠"进 session memory 的最后一条消息（其 message ID）。断点之后的消息即"未被 session memory 记忆到"的未压缩消息。
- **模型线（model line / ModelHistory）**：实际喂给压缩管线/模型的历史。它从上一轮持久化的"已压缩请求历史"加载（`loadModelHistory` → `GetConversationModelHistory`），并在循环中与 `History` 同步追加真实消息；与全量、逐字的 `History` 不同，模型线可能已带压缩产物（摘要/记忆前言、占位、被裁消息）。

> 本次仅调整 **会话记忆** 的提取/更新时机与 `ConversationMemoryStrategy` 的尾部组成；长期记忆 `extractMemories` 与定时去重 `maybeRunConsolidation` 保持现状（仍在每轮结束异步执行），其余压缩策略一律不动。

## 1. 背景与现状

### 1.1 会话记忆当前如何工作

- **提取/更新**：每轮对话**自然结束**时（`conversation_flow.go:168` 的非 `tool_calls` 分支），`scheduleMemoryWork` 在异步 goroutine 内**无条件**调用 `updateConversationMemory`：读取已有会话记忆 + 渲染本轮对话，调 LLM 重写"完整会话记忆列表"，再 `ReplaceConversationMemories` 整表替换。
- **注入替代**：压缩管线中 `ConversationMemoryStrategy`（`compression.go:84` 注册，在 `FullHistorySummarizationStrategy` 之前）在如下条件全部满足时，用会话记忆**替代** compact_history：
  - 当前请求 token `before > ContextTokenBudget()`（超预算）；
  - `len(RequestHistory) >= 2`；
  - 会话记忆条数 `>= conversationMemoryMinCount(5)`；
  - 会话记忆文本估算 token 落在 `[conversationMemoryMinTokens(10K), conversationMemoryMaxTokens(40K)]`。
  - 满足后组成：`[system 前言] + [user <conversation-memory>] + selectRecentTail(按 token 预算挑选) + lastMessage`。

### 1.2 模型线的折叠关系（断点设计的关键前提）

- `compressContextBeforeLLM` 对 `state.ModelHistory` 的**克隆**跑压缩，结果存入 `lastRequestHistory`；`state.ModelHistory` 本身保持真实消息、不被压缩改写。
- 轮末持久化的模型线 = `lastRequestHistory`（**已压缩**）+ 最终 assistant。即一旦某轮触发了 `ConversationMemoryStrategy`，持久化的模型线就坍缩成 `[前言, 记忆块, 未折叠尾部, assistant]`——被折叠的旧消息已被记忆块取代，不再以真实消息形式存在。
- 因此**断点必须"含端点"地保留**（tail 从断点消息本身开始），让断点消息作为锚点持续存在于模型线中，下一轮仍能按 ID 定位；否则断点会随首次折叠被自身丢弃，后续轮次找不到锚点。

### 1.3 现状的问题（对应需求）

1. 会话记忆从第 1 轮起就无条件提取，小会话也产生 LLM 调用，浪费且过早。
2. 仅在"轮次自然结束"提取一次，无法在"长工具链尚未结束但上下文已大幅增长"时及时刷新会话记忆。
3. `ConversationMemoryStrategy` 的尾部用 `selectRecentTail`（按 token 预算动态挑选），**不能精确对应"未被 session memory 记忆到的消息"**；需求要求尾部恰为"最近的未压缩消息"。

## 2. 目标（对应需求 1–3）

1. **初次提取门槛**：上下文达到 **10K tokens** 时，才触发会话记忆的**初次**提取。
2. **更新触发条件**：满足以下任一组合即触发会话记忆更新（评估点放在 **agent 循环每个 round 结束后**，详见决策 D1）：
   - 条件(1)：`token 增长 >= 5000` **且** 自上次更新以来`工具调用 >= 3 次`；（用于"长工具链中途刷新"）
   - 条件(2)：`token 增长 >= 5000` **且** 最后一个 assistant 消息**无工具调用**（即该轮对话自然结束）。
3. **替代组成 = 系统提示 + session memory + 未压缩消息**：当会话记忆满足替代 compact_history 时，最终上下文为 **系统提示 + session memory + 断点之后的未压缩消息**（即未被 session memory 记忆到的信息），而非固定"最近 5 条"。这需要为每次 session memory 更新记录**断点**，并处理多种边界情况（见 §3.6）。

### 决策（已与用户确认 / 本次明确）

- **D1（评估点）**：在 agent 主循环**每个 round 结束后**评估触发条件，而非仅在轮次自然结束（`scheduleMemoryWork`）时。否则条件(1)的"工具调用 >= 3"在轮末恒无意义（轮末最后一个 assistant 必然无工具调用，条件(2)恒成立）。
- **D2（范围）**：仅改"会话记忆"的提取/更新时机与 `ConversationMemoryStrategy` 尾部组成。长期记忆 `extractMemories`、定时去重 `maybeRunConsolidation` **不变**。
- **D3（断点存储位置）**：断点存于 **Service 内存态**（随 `sessionMemoryProgress`，按 `conversationID` 索引），并在每轮压缩前注入到 `compression.Request`，由 `ConversationMemoryStrategy` 读取。**不引入存储层/接口持久化改动**，与现有 `injectedMemories` 内存态同模式。进程重启后断点丢失 → 该会话首次再遇压缩时**优雅降级**为 `FullHistorySummarizationStrategy`（摘要 + 最近 5 条，无数据丢失），待下一次 session memory 更新重建断点后恢复"记忆替代"。
- **D4（断点含端点）**：tail 从断点消息**本身**开始（`[index:]`），断点消息作为锚点保留，保证跨轮可定位（理由见 §1.2）。代价仅为 1 条已折叠消息的轻微冗余。

## 3. 总体设计

### 3.1 会话记忆进度跟踪（Service 内存态）

新增 Service 字段（与现有 `injectedMemories` 同风格，进程内、按 `conversationID` 索引、最坏情况重建无正确性影响）：

```go
// runtime.go
type Service struct {
    // ...existing...
    sessionMemoryMu       sync.Mutex
    sessionMemoryProgress map[string]*sessionMemoryProgress // key=conversationID
}

// 会话记忆触发进度：记录上次更新时的上下文基线、自上次以来的工具调用数，
// 以及上次成功折叠进 session memory 的断点（最后一条已折叠消息的 ID）。
type sessionMemoryProgress struct {
    extracted          bool   // 是否已完成初次提取（决定走 10K 门槛还是增量条件）
    baselineTokens     int    // 上次更新时的上下文 token（增长基线）
    toolCallsSinceBase int    // 自上次更新以来累计工具调用次数
    updating           bool   // 是否有一次会话记忆更新正在进行（单航班守卫）
    breakpointID       string // 需求3：上次成功折叠的断点消息 ID（含端点保留）
}
```

辅助方法：

```go
// 获取/创建会话进度；首次创建时根据已有会话记忆判定 extracted，避免重启后对老会话重新走 10K 门槛。
func (s *Service) sessionMemoryProgressFor(ctx, conversationID) *sessionMemoryProgress
```
- 首次创建：`existing := s.Store.ListConversationMemories(ctx, conversationID)`，`extracted = len(existing) > 0`；`breakpointID = ""`（重启后断点未知，由 §3.6 的降级分支处理）。

### 3.2 触发评估（核心逻辑）

```go
const (
    sessionMemoryInitialTokens = 10 * 1024 // 需求1：初次提取门槛
    sessionMemoryTokenGrowth   = 5000      // 需求2：token 增长阈值
    sessionMemoryToolCallsMin  = 3         // 需求2 条件(1)：工具调用阈值
)

// shouldUpdate 在持有 sessionMemoryMu 的前提下判定是否应更新会话记忆，
// 并在判定为"是"时就地重置基线（baselineTokens、toolCallsSinceBase）。
// turnEnded=true 表示这是轮次自然结束的评估（条件2），false 表示 round 中途评估（条件1）。
func (p *sessionMemoryProgress) shouldUpdate(currentTokens int, turnEnded bool) bool {
    // 压缩后 token 可能回落到基线以下；将基线下移到当前值，使"增长"始终从最近低点起算。
    if currentTokens < p.baselineTokens {
        p.baselineTokens = currentTokens
    }
    if !p.extracted {
        if currentTokens >= sessionMemoryInitialTokens { // 需求1
            return true
        }
        return false
    }
    growth := currentTokens - p.baselineTokens
    if growth < sessionMemoryTokenGrowth {
        return false
    }
    // 需求2：turnEnded（条件2）token 增长达标即可；round 中途（条件1）还需工具调用 >= 3。
    if !turnEnded && p.toolCallsSinceBase < sessionMemoryToolCallsMin {
        return false
    }
    return true
}
```

说明：
- 触发判定与"重置基线/置 extracted/置断点"分离：`shouldUpdate` 只判定；真正重置在**更新成功后**由调用方在锁内提交（见 §3.3 / §3.6），避免失败时误推进基线或断点。
- "token" 取 `state.LastContextTokens`（`compression.DefaultTokenEstimator` 估算的整轮请求 token，与 meta 下发值一致）。
- 工具调用计数 `toolCallsSinceBase` 跨轮累计，由主循环在每轮执行工具后累加 `len(msg.ToolCalls)`。

### 3.3 主循环接入（`conversation_flow.go`）

仅在 `s.EnableMemory && memoryOn` 时参与。

**(a) round 中途评估（条件1 / 初次提取）** —— tool_calls 分支 for-body 末尾（`state.ToolCallCount++` / `emitMeta` 之后）：

```go
if memoryOn {
    s.maybeUpdateSessionMemoryMidLoop(ctx, conversation, user, state, len(msg.ToolCalls))
}
```

`maybeUpdateSessionMemoryMidLoop`（持 `sessionMemoryMu`）：
1. 取/建进度态，`p.toolCallsSinceBase += roundToolCalls`；
2. 若 `p.updating` 为真（上一次更新仍在跑）→ 直接返回（不重复触发、不动基线/断点）；
3. 否则 `if p.shouldUpdate(state.LastContextTokens, false)`：
   - 捕获快照 `snap := cloneMessages(state.History)`、`bpID := lastMessageID(snap)`、`baseTokens := state.LastContextTokens`；置 `p.updating = true`；
   - **异步** goroutine 执行 `updateConversationMemory(snap)`（独立 `context.WithTimeout(background, MemoryWorkTimeout)`，best-effort）：
     - 成功 → 持锁提交：`p.baselineTokens = baseTokens; p.toolCallsSinceBase = 0; p.extracted = true; p.breakpointID = bpID`；
     - 失败/无产出 → 仅记录告警，**不**提交（基线/断点不变，下轮可重试）；
     - finally：持锁 `p.updating = false`。

> 中途更新**不**接管/释放会话锁：主循环仍持锁并续期；store 内部 `sync.Mutex` 串行化文件写。单航班守卫 `updating`（会话级）保证同一会话同一时刻最多一个会话记忆更新在跑（跨"中途更新"与"轮末更新"共用）。

**(b) 轮末评估（条件2 / 初次提取）** —— 非 `tool_calls` 分支，`scheduleMemoryWork` 调用处：

```go
if s.EnableMemory {
    updateSession := false
    if memoryOn {
        updateSession = s.shouldUpdateSessionMemoryAtTurnEnd(conversation, state.LastContextTokens)
    }
    handedOff = s.scheduleMemoryWork(conversation, user, finalHistory, finalModelHistory,
        lockToken, stopRenew, memoryOn, updateSession)
}
```

`shouldUpdateSessionMemoryAtTurnEnd`（持锁）：取/建进度态；若 `p.updating` 为真返回 false（让中途那次跑完即可，best-effort）；否则返回 `p.shouldUpdate(currentTokens, true)`。返回 true 时**先**置 `p.updating=true` 并把"待提交的 baseTokens 与断点 = finalHistory 最后一条消息 ID"交给 `scheduleMemoryWork`，由其在更新成功后提交、finally 解除 `updating`。

### 3.4 `scheduleMemoryWork` 改造（`conversation_memory.go`）

签名新增 `updateSessionMemory bool`。`updateConversationMemory` 改为按该参数执行；成功后提交断点/基线（断点 = `finalHistory` 最后一条消息 ID）。**长期记忆与定时去重不变**：

```go
func (s *Service) scheduleMemoryWork(conv, user, history, modelHistory, token, stopRenew, memoryOn, updateSessionMemory bool) bool {
    // ...锁接管、模型历史落库不变...
    if memoryOn {
        s.extractMemories(ctx, user, history)              // 不变：每轮结束执行
        if updateSessionMemory {                            // 变更：按触发条件
            if s.updateConversationMemory(ctx, conv, user, history) { // 改为返回是否成功
                s.commitSessionMemoryBreakpoint(conv.ID, state快照携带的 baseTokens, lastMessageID(history))
            }
            s.clearSessionMemoryUpdating(conv.ID)
        }
        s.maybeRunConsolidation(ctx, user)                  // 不变
    }
    // ...
}
```

> `updateConversationMemory` 增加 bool 返回值（成功且有产出为 true），用于断点提交判定。

### 3.5 `ConversationMemoryStrategy` 尾部对齐（需求 3 核心）

`compression.Request` 新增字段：

```go
type Request struct {
    // ...existing...
    ConversationMemoryBreakpoint string // 需求3：最后一条已折叠消息 ID；空表示未知
}
```

`compressContextBeforeLLM`（runtime）在构造 `req` 时填充：`req.ConversationMemoryBreakpoint = s.sessionMemoryBreakpoint(conversation.ID)`（读内存态，持锁）。

`conversation_memory_strategy.go` 的 `Apply` 改造（保留全部既有触发门槛：`before > budget`、`count >= 5`、memTokens∈[10K,40K]）：

```go
// 计算未折叠尾部：从断点消息（含端点）到末尾。
tail, ok := selectUnfoldedTail(req.RequestHistory, req.ConversationMemoryBreakpoint)
if !ok {
    return nil // 断点未知/未命中 → 降级给 FullHistorySummarizationStrategy（见 §3.6）
}
kept := repairToolCallBoundaries(tail)
candidate := buildConversationMemoryHistory(memoryText, kept)
// 保持"本策略一旦动手，结果须落在预算内"的不变式：未折叠尾部过大则不动手，交全量摘要兜底。
if req.Estimator.EstimateRequestTokens(req.SystemPrompt, candidate, req.Tools) > budget {
    return nil
}
req.RequestHistory = candidate
return nil
```

`selectUnfoldedTail`：

```go
// 返回断点消息（含）之后的尾部；命中返回 (tail, true)，未知/未命中返回 (nil,false)。
func selectUnfoldedTail(history []storage.Message, breakpointID string) ([]storage.Message, bool) {
    if breakpointID == "" {
        return nil, false
    }
    for i := range history {
        if history[i].ID == breakpointID {
            return history[i:], true // D4：含端点
        }
    }
    return nil, false
}
```

- `buildConversationMemoryHistory` 不变：产出 `[{system,前言},{user,<conversation-memory>}, ...kept]`；叠加外层真实系统提示后，最终上下文 = **系统提示 + session memory + 未压缩（未折叠）消息**，符合需求 3。
- 折叠点之前的旧 `[前言,记忆块]` 及已折叠真实消息因位于断点之前被自然剔除，再以"当前 session memory"重建记忆块，避免陈旧。

### 3.6 边界情况枚举（需求 3"多种情况"）

| 情况 | 触发原因 | 处理 |
| --- | --- | --- |
| A. 断点已知且命中 | 进程内已成功更新过 | tail = 断点(含)→末尾；组成 系统提示 + session memory + 未压缩尾部 |
| B. 断点未知 | 进程重启 / 本会话本进程尚未成功更新过 | 本策略 no-op → `FullHistorySummarizationStrategy` 兜底（摘要 + 最近 5 条），**无数据丢失**；下次更新重建断点后恢复 |
| C. 断点已知但未命中 | 断点消息被 `MessageWindowCompressionStrategy`（>50 条）裁掉等 | 同 B：no-op 兜底 |
| D. 未折叠尾部仍超预算 | 自上次折叠后增量过大 / 单条超大 | no-op → 全量摘要兜底（避免 `ConversationMemoryStrategy` 产出仍超预算导致全量摘要二次压缩记忆块） |
| E. tail 仅含断点一条 | 断点后暂无新消息（极少见） | 保留断点单条；`repairToolCallBoundaries` 清理可能的孤儿 tool 消息 |

> B/C/D 的兜底都走既有 `FullHistorySummarizationStrategy`，其"摘要覆盖旧消息 + 保留最近 5 条逐字"保证无数据丢失，行为与现状一致。

## 4. 废弃 / 删除清单（需求注意事项：废弃无用代码）

- `selectRecentTail`（`full_history_summarization.go:108`）：改造后 `ConversationMemoryStrategy` 不再使用，全局无引用 → **删除**。
- `recentTailMinTokens`（`full_history_summarization.go:18`）：仅被 `selectRecentTail` 使用 → **删除**。
  - （核对：`FullHistorySummarizationStrategy.Apply` 自身用 `req.RequestHistory[n-tailCount:]` 直接取尾，不依赖 `selectRecentTail`/`recentTailMinTokens`；`ReactiveCompactStrategy` 用独立的 `selectReactiveTail`/`reactiveTailMinTokens`，不受影响。`recentTailMessages(5)` 仍被 `FullHistorySummarizationStrategy` 使用，保留。）
- 旧的"每轮无条件提取会话记忆"行为：被 §3 的条件化触发取代。

保留不动：`extractMemories`、`maybeRunConsolidation`、`renderDialogueForMemory`、`parseConversationMemories`、`updateConversationMemory` 主体（仅加 bool 返回）、`ReactiveCompactStrategy`、其余压缩策略。

## 6. 测试计划

- `(*sessionMemoryProgress).shouldUpdate`（纯函数，重点）：
  - 未 extracted：tokens < 10K 不触发；>= 10K 触发。
  - 已 extracted、turnEnded=false：增长 < 5000 不触发；增长 >= 5000 但工具调用 < 3 不触发；增长 >= 5000 且工具调用 >= 3 触发。
  - 已 extracted、turnEnded=true：增长 >= 5000 即触发（不看工具调用）；增长 < 5000 不触发。
  - 压缩回落：currentTokens < baseline 时基线下移，后续以新低点计算增长。
- `selectUnfoldedTail`：断点为空 → (nil,false)；断点命中 → 含端点切片；断点未命中 → (nil,false)。
- `ConversationMemoryStrategy`：
  - 断点命中且预算内 → 产出 `[前言]+[memory]+断点(含)后续`，剔除断点前的旧记忆块与已折叠消息。
  - 断点未知/未命中 → no-op，随后 `FullHistorySummarizationStrategy` 产出 摘要 + 最近 5 条。
  - 未折叠尾部超预算 → no-op 兜底。
  - `repairToolCallBoundaries` 边界正确（断点为 tool 消息时孤儿处理）。
- 断点提交：`updateConversationMemory` 失败时不提交断点/基线；成功后断点 = 折叠快照最后一条 ID。
- `scheduleMemoryWork`：`updateSessionMemory=false` 不调用 `updateConversationMemory`，但 `extractMemories`/`maybeRunConsolidation` 仍执行；`true` 时三者均执行且成功后提交断点。
- 主循环集成（沿用 `runtime_test.go` 的 fake LLM）：多 round 工具链触发条件(1) 中途更新并设断点；小会话（<10K）轮末不提取；跨轮断点链：第二轮压缩用第一轮断点之后的未折叠尾部。
- 回归：`go test ./...` 全绿；删除 `selectRecentTail`/`recentTailMinTokens` 后无残留引用。

## 7. 风险与缓解

- **跨轮断点可定位**：D4 含端点保留断点消息作为锚点，避免折叠后丢失锚点导致后续轮次找不到断点（§1.2）。
- **进程重启断点丢失**：降级走全量摘要兜底（情况 B），无数据丢失；下次会话记忆更新重建断点后恢复"记忆替代"。沿用 `injectedMemories` 内存态重建模式。
- **未折叠尾部过大**：情况 D 下不动手、交全量摘要，保持"本策略产出必在预算内、不触发记忆块二次摘要"的不变式。
- **中途异步更新与轮末更新并发**：会话级单航班守卫 `updating`；轮末发现 in-flight 则跳过（best-effort）。
- **token 增长在压缩后回落**：`shouldUpdate` 将基线下移到当前低点，避免增长被压缩噪声掩盖。
- **best-effort 语义**：所有会话记忆更新失败仅告警、不影响用户响应，且失败不提交断点/基线（沿用现有 `updateConversationMemory` 行为）。
- **范围隔离**：长期记忆与定时去重逻辑零改动；`FullHistorySummarizationStrategy`/`ReactiveCompactStrategy` 行为不变，仅删除其文件内已无引用的辅助函数/常量。

## 8. 迭代二（2026-06-20）：富内容提取 + 断点持久化

本节是对前文的修订；与前文冲突处以本节为准。三项变更（已与用户确认范围）：

### 8.1 提取改用 ModelHistory 富内容（会话记忆 + 长期记忆都改）

**现状问题**：`extractMemories`（长期记忆）与 `updateConversationMemory`（会话记忆）此前都用 `renderDialogueForMemory(history)`，只渲染 user/assistant 的**纯文本**，丢弃工具调用与结果，且上限仅 4000 字符。这与"基于完整交互内容提取记忆"的目标不符。

**变更**：
- 新增富内容渲染器 `renderModelHistoryForMemory(history []storage.Message) string`，渲染：
  - `[user] <content>`
  - `[assistant] <content>`，若该 assistant 消息含 `ToolCalls`，逐条追加 `[tool_call] <name>(<arguments>)`
  - `[tool_result] <status>: <result>`（用 `textutil.ParseToolResult` 解析 tool 消息内容；非 JSON 原样取 content）
  - 保留按字符上限截断的保护（提升上限，见下），逐条累计、超限即停。
- `extractMemories`、`updateConversationMemory`、`selectRelevantMemories`（注入侧候选精选用的对话上下文）统一改用 `renderModelHistoryForMemory`。
- **数据来源改为 ModelHistory（模型线）**：调用方传入的提取 history 改为模型线（含 user/assistant/tool 真实消息及工具调用与结果），而非 display `state.History`。
  - 轮末：`scheduleMemoryWork` 的 `history`（提取源）与 `modelHistory`（落库源）参数共用同一本轮压缩后的请求线 `finalModelHistory = lastRequestHistory + 最终 assistant`。即轮末提取与落库同源，均取本轮压缩请求线。
  - 中途：`maybeUpdateSessionMemoryMidLoop` 改为快照 `state.ModelHistory` 传入（循环内 lockstep 追加的真实消息，逐字保留 user/assistant/tool）。
  - 断点不受影响：轮末断点 = 最终 assistant 消息 ID；中途断点 = `state.ModelHistory` 末条 ID。该 ID 在 display history 中同样存在（轮末经 Stop hook 落 display；中途因 `History`/`ModelHistory` lockstep 追加同 ID），§9.1 切片仍成立。
- 字符上限常量 `maxMemoryDialogueChars` 由 4000 提升到一个能容纳工具内容的值（如 `24000`），命名保持或改为 `maxMemoryTranscriptChars`。

> 选择（注入）侧 `selectRelevantMemories` 的候选精选 prompt 也用同一富渲染器，使"挑选相关长期记忆"的对话上下文与提取口径一致。

### 8.2 断点持久化到会话记忆文件（需求：断点需持久化存储）

**现状问题**：断点只在 `sessionMemoryProgress`（进程内存态），进程重启丢失 → 跨重启需重新走全量摘要兜底直到下次更新。

**变更**：断点持久化进**会话记忆文件 frontmatter**（`sessions/<id>.md`）。

- `storage.ConsolidationState` 模式参考，但断点是会话维度，存于会话文件。新增 store 接口（`conversationStore` 与 `compression.Store` 均无需感知；仅 runtime 用）：
  - `LoadConversationMemoryBreakpoint(ctx, conversationID string) (string, error)`
  - `SaveConversationMemoryBreakpoint(ctx, conversationID, breakpointID string) error`
- `local.Store` 转发到 `MarkdownMemoryStore`（按 `sessionIDForConversation` 映射）；内存兜底分支用 map 保存。
- `MarkdownMemoryStore`：
  - 写：`writeSessionMemoryLocked` 增加 frontmatter 字段 `breakpoint_id: "<id>"`；由于该函数整文件重写，新增 `SaveConversationMemoryBreakpoint` 时需**先读已有 memories + 保留**再重写（或把 breakpoint 与 memories 解耦：`writeSessionMemoryLocked(sessionID, items, breakpointID)`，`ReplaceConversationMemories` 调用时先读旧 breakpoint 保留，`SaveConversationMemoryBreakpoint` 调用时先读旧 memories 保留）。
  - 读：`LoadConversationMemoryBreakpoint` 解析 frontmatter 的 `breakpoint_id`（复用 `splitFrontMatter`）。
- **提交链**：`commitSessionMemoryBreakpoint` 在更新内存态后，**异步持久化**调用 `SaveConversationMemoryBreakpoint`（best-effort，失败仅告警）。因 `ReplaceConversationMemories`（写会话记忆）与 `SaveConversationMemoryBreakpoint`（写断点）都改同一文件，二者需在 store 内用同一把 `m.mu` 串行，且互相保留对方字段（见上）。
  - 顺序：先 `ReplaceConversationMemories`（写入最新 memories），后 `SaveConversationMemoryBreakpoint`（写入断点）。两步都在 `updateConversationMemory` 成功后进行。
- **加载链**：`sessionMemoryProgressForLocked` 首次创建进度态时，除按"已有会话记忆是否存在"判定 `extracted`，再 `LoadConversationMemoryBreakpoint` 回填 `breakpointID`。这样进程重启后断点立即可用，`ConversationMemoryStrategy` 无需等到下次更新即可命中（情况 B 减少）。

## 9. 迭代三（2026-06-20）：保留尾部改用 DisplayHistory + 断点仅文件持久化

本节是对前文（尤其 §3.5/§3.6、§8.2）的修订；与前文冲突处以本节为准。

### 9.1 保留的"未压缩消息"改为来自 DisplayHistory（逐字 history）

之前 `ConversationMemoryStrategy` 与 `FullHistorySummarizationStrategy` 都在 `RequestHistory`（模型线 `ModelHistory` 的克隆，可能已带占位/被裁产物）上取尾。现要求：替代/摘要后保留的"最近消息"必须取自**逐字 display history**（`state.History`），保证保留的是真实、未经压缩改写的原始消息。

- `compression.Request` 新增字段 `DisplayHistory []storage.Message`：逐字 display history 的克隆，由 `compressContextBeforeLLM` 用 `state.History` 填充。
- **ConversationMemoryStrategy**：触发条件不变；命中后尾部改为 `selectUnfoldedTail(req.DisplayHistory, breakpoint)`（断点含端点）。结果 = `[前言]+[memory]+DisplayHistory[breakpoint:]`。预算守卫与降级（断点未知/未命中/尾部超预算 → no-op 交全量摘要）不变。
- **FullHistorySummarizationStrategy**：触发条件不变；改为对 `DisplayHistory` 做"摘要前缀 + 保留最近 `recentTailMessages(5)` 条 DisplayHistory"。`summarizable=DisplayHistory[:n-tail]`、`tail=DisplayHistory[n-tail:]`；摘要缓存键基于该 summarizable 计算。`DisplayHistory` 为空/过短时退回 `RequestHistory`，避免空历史。
- **ReactiveCompactStrategy 不变**：413 兜底、对 `ModelHistory` 激进压缩，不属本次语义。

> 语义：无论"会话记忆替代"还是"全量摘要"，最终上下文 = 系统提示 +（记忆或摘要）+ 最近若干条**逐字** display 消息。

- 断点值 = 折叠快照（modelHistory 快照）最后一条消息 ID；因 `History`/`ModelHistory` lockstep 追加同 ID 消息，该 ID 在 display history 中同样存在，可用于 §9.1 切片。
