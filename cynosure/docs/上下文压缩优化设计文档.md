# 上下文压缩优化设计文档

## 1. 背景

`cynosure` 的上下文压缩采用策略链（Strategy Chain），每轮 LLM 调用前按序执行（`internal/agent/runtime/compression/compression.go:64`）：

1. `ToolResultCompressionStrategy` —— 大工具结果落盘
2. `MessageWindowCompressionStrategy` —— **头尾窗口裁剪（即需求中的 “snip_compact”）**
3. `RecentToolResultRetentionStrategy` —— 仅保留最近 N 个完整工具结果
4. `ConversationMemoryStrategy` —— 会话记忆注入
5. `FullHistorySummarizationStrategy` —— **全量摘要兜底（即需求中的 “compact_history”）**

> 说明：代码中不存在字面量 `snip_compact` / `compact_history`，二者分别对应 `MessageWindowCompressionStrategy` 与 `FullHistorySummarizationStrategy`。本设计沿用项目现有命名。

压缩在每轮 LLM 调用前，对唯一的真实消息历史 `state.ModelHistory` 的深拷贝跑策略链（策略层内称 `RequestHistory`），**结果写回 `state.ModelHistory`**，使其内存态 = 发送态 = 落库态（`internal/agent/runtime/context_compression.go:30` 与 `conversation_flow.go` 主循环）。它绝不修改展示历史 `state.History`——后者仅被克隆进 `req.DisplayHistory`，供摘要 / 会话记忆策略保留逐字尾部。两种历史的统一详见《会话历史模型统一重构设计文档》。

## 2. 问题分析

### 2.1 问题一：头尾裁剪会丢掉“用户最新问题”

`MessageWindowCompressionStrategy`（`message_window_compression.go:21`）原始逻辑：

```go
if len(history) <= 50 { return nil }      // 阈值针对“全部消息”（含历史消息）
head := history[:3]                        // 保留最旧 3 条
tail := history[len(history)-47:]          // 保留最新 47 条
```

- `head` 固定取**最旧的 3 条**、`tail` 固定取**最新的 47 条**，中间一律裁掉。
- 当本轮工具调用很多、整体消息超过 50 条时，用户在当前轮的提问位于“本轮起点”，它既不在最旧 3 条、也不在最新 47 条里，于是被裁掉，模型“忘记用户在问什么”，产生幻觉。
- 补充：系统提示词 `state.SystemPrompt` 不在 `RequestHistory` 内，由外层 `buildOpenAIMessages`（`prompt_builder.go:60`）单独作为首条 `system` 消息注入，window 策略不触碰它，因此系统提示词天然永远保留。

### 2.2 问题二：全量摘要提示词与尾部窗口

- 摘要提示词 `summarizerSystemPrompt`（`internal/agent/runtime/summarizer.go:14`）为通用英文，未明确强调“用户最新问题 / 改动文件路径 / 关键决策 / 待办 / 报错结论”等关键维度，摘要质量不稳定。
- 摘要后保留的尾部窗口按 token 预算计算（`recentTailMinTokens = 16K`，`full_history_summarization.go:103` 的 `selectRecentTail`），不够直观可控。

## 3. 需求与边界

### 3.1 目标

1. **改造头尾裁剪（需求一）**：触发条件改为“**当轮对话消息数 > 50**（不含历史消息）”；触发后在 `RequestHistory` 内保留：
   - **系统提示词**：由外层注入，永远保留（不占 window 的 49 条名额）；
   - **head（固定 3 条）**：用户最新消息及其后 2 条；
   - **tail（固定 46 条）**：最新 46 条；
   - head + tail = 49 条 history，加外层系统提示词共 **50 条**；中间部分被裁剪。
2. **优化全量摘要（需求二）**：
   - 重写摘要提示词，强调：用户最新问题；已完成的工作与改动文件（**保留路径**）；关键决策及原因；当前进展 / 未完成 / 待办；重要报错、命令输出结论与约定。
   - 最终结构为 `[系统提示 + 摘要 + 最近若干轮消息]`，**最近消息固定为 5 条**（由原 token 预算窗口改为条数窗口）。

### 3.2 非目标 / 不影响项

1. 不改动 `ToolResultCompressionStrategy`、`RecentToolResultRetentionStrategy`、`ConversationMemoryStrategy` 的行为。
2. 不改动 `ReactiveCompactStrategy`（413 溢出兜底）的尾部窗口逻辑；它与全量摘要共享同一个 summarizer，因此**会一并受益于提示词优化**（无法也无需单独隔离）。
3. 不改动展示历史 `state.History`、`ModelHistory` 的存储格式。
4. 不改动 `selectRecentTail` 本身（`ConversationMemoryStrategy` 仍依赖它）。

### 3.3 关键定义

- **当轮对话消息数（不含历史消息）**：从“最新一条 `role=="user"` 的消息”到队尾的消息条数，即 `len(history) - lastUser`。该 user 消息之前的消息视为历史消息。
- **用户最新消息**：从队尾向前查找的第一条 `role=="user"` 的消息，记其下标为 `lastUser`。
- **head（固定 3 条）**：`history[lastUser : lastUser+3]`，即用户最新消息及其后 2 条。
- **无 user 消息回退**：`lastUser=-1` 时 `headStart=0`，head 取 `history[0:3]`（本轮第一条消息及其后 2 条，含可能存在的前导 `system` 消息）；tail 仍取最新 46 条；系统提示词由外层保留。
- **tail（固定 46 条）**：`history[len(history)-46:]`，即最新 46 条。
- **常量调整**：`messageWindowHead` 保持 `3`；`messageWindowTail` 由 `47` 改为 `46`；`messageWindowLimit` 保持 `50`，但语义改为“当轮消息数阈值”。系统提示词在 `RequestHistory` 之外，由外层注入，与上述 49 条共同构成发送给模型的 50 条。

## 4. 详细设计

### 4.1 需求一：`MessageWindowCompressionStrategy` 改造

文件：`internal/agent/runtime/compression/message_window_compression.go`

改造后 `Apply` 逻辑：

```go
func (s *MessageWindowCompressionStrategy) Apply(ctx context.Context, req *Request) error {
    history := req.RequestHistory

    // 定位“用户最新消息”：从尾部向前找最后一条 role=="user"。
    lastUser := -1
    for i := len(history) - 1; i >= 0; i-- {
        if history[i].Role == "user" {
            lastUser = i
            break
        }
    }

    // 当轮消息数（不含历史消息）。无 user 时退化为全部消息计数。
    turnStart := lastUser
    if turnStart < 0 {
        turnStart = 0
    }
    if len(history)-turnStart <= messageWindowLimit { // 50：当轮消息未超阈值不裁剪
        return nil
    }

    // head：用户最新消息 + 其后 2 条，共 3 条；无 user 时退回“最旧 3 条”。
    headStart := lastUser
    if headStart < 0 {
        headStart = 0
    }
    head := history[headStart : headStart+messageWindowHead] // 3
    tail := history[len(history)-messageWindowTail:]         // 46

    windowed := make([]storage.Message, 0, messageWindowHead+messageWindowTail)
    windowed = append(windowed, head...)
    windowed = append(windowed, tail...)
    req.RequestHistory = repairToolCallBoundaries(windowed)
    return nil
}
```

要点：

- 触发条件改为“**当轮对话消息数 > 50**”（`len(history) - turnStart > messageWindowLimit`）；当轮 = 从最后一条 `user` 到队尾。
- `head` 固定 3 条：从“用户最新消息”起向后取 3 条（用户最新消息 + 其后 2 条），保证用户最新提问及紧随上下文一定保留。
- `tail` 固定 46 条：`history[len-46:]`。head + tail = 49 条 `RequestHistory`。
- 系统提示词不在 `RequestHistory` 内，由外层 `buildOpenAIMessages` 单独注入；49 条 + 系统提示词 = 发送给模型的 **50 条**。
- 当轮消息数 > 50 保证 `headStart+3` 与 `len-46` 不重叠：`lastUser ≤ len-51`，故 `lastUser+3 ≤ len-48 < len-46`，head/tail 不交叉。
- 历史消息（`lastUser` 之前）在触发时被丢弃；这正是“保留当轮 head+tail”的语义。跨轮信息由后续 token 超预算时的 `FullHistorySummarizationStrategy` 摘要承载。
- 无 `user` 消息的极端场景：`headStart=0`，退回“系统提示词（外层保留）+ 本轮第一条消息及其后 2 条（含可能存在的前导 system 消息）+ 尾部 46 条”，保证健壮性。
- 继续调用 `repairToolCallBoundaries` 修复因裁剪产生的悬空 `tool_call` / 孤儿 `tool` 消息。
- 常量调整：`messageWindowTail` 由 `47` 改为 `46`；`messageWindowHead=3 / messageWindowLimit=50` 复用，`messageWindowLimit` 语义改为“当轮消息数阈值”。

### 4.2 需求二：全量摘要改造

#### 4.2.1 尾部窗口改为“最近 5 条”

文件：`internal/agent/runtime/compression/full_history_summarization.go`

- 新增常量 `recentTailMessages = 5`。
- `Apply` 中尾部选择由 token 预算改为条数：

```go
// 触发条件与缓存逻辑保持不变（仍按 token 预算触发）。
n := len(req.RequestHistory)
tailCount := recentTailMessages          // 5
if tailCount > n-1 {                      // 至少保留 1 条可摘要内容（兼容极短历史）
    tailCount = n - 1
}
summarizable := req.RequestHistory[:n-tailCount]
tail := req.RequestHistory[n-tailCount:]

sourceHash := historyHash(summarizable)
// ...（缓存命中 / 调用 summarizer 生成 summary，逻辑不变）...

kept := repairToolCallBoundaries(tail)
req.RequestHistory = buildSummaryHistory(summary, kept)
```

- 不再使用 `selectRecentTail` / `lastMessage` 分支；最终结构由 `buildSummaryHistory` 产出 `[system 摘要前言 + user 摘要 + 最近 5 条]`，与需求 `[系统提示 + 摘要 + 最近若干轮消息]` 一致。
- `selectRecentTail` 与 `recentTailMinTokens` **保留不删**（`ConversationMemoryStrategy` 仍在使用）。
- `tailCount = min(5, n-1)` 的设计使极短历史（如 2~3 条）退化为“保留最后 1~2 条、摘要其余”，与现有行为兼容。

#### 4.2.2 摘要提示词重写

文件：`internal/agent/runtime/summarizer.go` 的 `summarizerSystemPrompt`

改为中文、结构化，强制覆盖以下维度（输出 Markdown）：

```
你是上下文压缩引擎。请把目前为止的对话压缩成结构化的 Markdown 简报，使另一个 AI 助手在不丢失关键信息的前提下继续完成任务。

必须覆盖以下部分（用对应小标题，无内容则写“无”）：
1. 用户最新问题：用户当前最想解决的问题 / 目标。
2. 已完成的工作：做了哪些事、得到了哪些关键结论；改动过的文件务必保留完整路径。
3. 关键决策与原因：做了哪些技术选择，为什么。
4. 当前进展与待办：已完成到哪一步、还没做完的部分、明确的下一步 / TODO。
5. 重要报错、命令输出结论与约定：关键报错信息、命令输出的结论性信息、双方达成的约定。

规则：
- 不要调用工具，不要编造不存在的信息。
- 保留具体细节：文件路径、函数名、命令、报错、关键数值。
- 遇到 <persisted-output ...> 标记，保留其 id 并说明可用 read_persisted_output 取回完整内容。
- 工具结果若显示 "[Earlier result compacted. Re-run if needed]"，需注明该结果如有需要应重新执行。

只输出 Markdown 简报本身。
```

> 该提示词由 `FullHistorySummarizationStrategy` 与 `ReactiveCompactStrategy` 共用，两者均会获得更好的摘要质量。

## 7. 风险与回滚

- **风险 1**：当轮裁剪丢弃历史消息后，若摘要层未触发，跨轮上下文可能缺失。缓解：token 超预算时 `FullHistorySummarizationStrategy` 仍会基于 `ModelHistory` 全量生成摘要，跨轮信息由摘要承载。
- **风险 2**：摘要尾部固定 5 条，极端大消息下 token 可能仍偏高。缓解：413 兜底 `ReactiveCompactStrategy` 仍会进一步激进压缩。
- **回滚**：三处改动相互独立，可按文件粒度单独回滚至原实现。
