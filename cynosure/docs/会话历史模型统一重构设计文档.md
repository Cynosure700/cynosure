# 会话历史模型统一重构设计文档

## 1. 背景与动机

`cynosure` 运行时此前存在 **四套相互重叠的 history**，命名与职责混淆，维护成本高、容易出 bug：

| 名称 | 含义 | 问题 |
|---|---|---|
| `state.History` | 逐字**展示**历史，落库给前端 / 会话恢复 | 正常，**保留** |
| `state.ModelHistory`（`internal/agent/runtime/hooks/types.go`） | "模型线"：上轮压缩结果做种 + 本轮 lockstep **逐字**追加 | 在内存中是**未压缩**版本，与真正发送 / 落库的压缩版本分叉 |
| `requestHistory`（`conversation_flow.go` 主循环局部量） | 每轮对 `ModelHistory` 克隆后压缩的结果，真正发给 LLM | 冗余的临时量 |
| `lastRequestHistory` → `finalModelHistory`（主循环局部量） | 末轮压缩线，用于最终估算、**轮末**记忆提取、并落库为下轮模型历史 | 冗余；与 `state.ModelHistory` 各自为政 |

由此产生两处不一致：

1. **压缩源不统一**：压缩输入是 `state.ModelHistory`（逐字未压缩），但真正发送给模型、并落库给下一轮复用的是临时 `requestHistory` / `finalModelHistory`（压缩后）。内存态与真实发送态分叉。
2. **记忆提取源不统一**：轮中（`maybeUpdateSessionMemoryMidLoop`）用未压缩的 `state.ModelHistory`，轮末（`scheduleMemoryWork`）用压缩后的 `finalModelHistory`；后者甚至把同一份压缩线作为 `history` 和 `modelHistory` 两个参数重复传入。

## 2. 目标与边界

### 2.1 目标

全项目只保留 **两种 history**：

1. **展示历史**（`state.History`）：原有逻辑，逐字、不压缩，落库给前端 / 恢复。**本次不调整。**
2. **真实消息历史**（`state.ModelHistory`）：存储真实发送给模型的消息线，**含压缩后结果**，下一轮新对话复用。

并满足：

- `state.ModelHistory` 是该真实消息线的**唯一载体**：每轮压缩结果**原地写回**它，使"内存态 = 发送态 = 落库态"。
- **压缩源**统一为 `state.ModelHistory`。
- **记忆提取源**（轮中 + 轮末）统一为 `state.ModelHistory`。
- 废弃 `requestHistory` / `lastRequestHistory` / `finalModelHistory` 等冗余中间量。

### 2.2 非目标 / 不影响项

1. 不改动展示历史 `state.History` 的语义、格式与落库逻辑。
2. 不改动压缩策略链本身（5 个策略的行为、顺序、阈值均不变）。
3. 不改动存储层接口与落盘格式：仍是展示历史 + 模型历史**两份**文件（`SaveHistory` / `SaveModelHistory`），`GetConversationModelHistory` / `UpsertConversationModelHistory` / `SetConversationHistory` 保持不变。
4. 保留 `ModelHistory` 命名（重命名会波及存储层方法且收益低），仅澄清其语义。
5. 子代理（`subagent.go`）不走压缩 / 记忆流程，不受影响。

## 3. 核心设计

**核心改动：压缩结果写回 `state.ModelHistory`，而非产出临时副本。** 改造后 `state.ModelHistory` 全程等于"当前压缩后的真实消息线"。

数据流（单轮）：

```
轮开始：state.ModelHistory = 上轮压缩后的真实消息线（含本轮新追加的 user / assistant / tool）
  ↓ compressContextBeforeLLM（内部克隆 + 跑策略链）
state.ModelHistory ← 压缩结果（原地更新）
  ↓ buildOpenAIMessages(SystemPrompt, state.ModelHistory)
发送给 LLM；估算 token 也用 state.ModelHistory
  ↓ 本轮 assistant / tool 结果 lockstep 追加进 state.History 与 state.ModelHistory
轮末：最终 assistant 追加进 state.ModelHistory（与 Stop 钩子追加进 state.History 对称）
  ↓
落库（UpsertConversationModelHistory）+ 记忆提取（extractMemories / updateConversationMemory）
统一以 state.ModelHistory 为源
```

### 3.1 `internal/agent/runtime/context_compression.go`

- `compressContextBeforeLLM` 内部仍克隆 `state.ModelHistory` + 跑策略链，返回压缩后的历史；**调用方将返回值赋回 `state.ModelHistory`**。`DisplayHistory: cloneMessages(state.History)` 保持不变——摘要 / 会话记忆策略仍从逐字展示历史保留尾部，这是展示历史的合法用途，不属于冗余 history。
- `reactiveCompact` 已经写回 `state.ModelHistory`，与新模型天然一致，无需改动。
- 更新顶部注释，删去"compression works on a clone, ModelHistory untouched"的旧表述。

### 3.2 `internal/agent/runtime/conversation_flow.go`（主循环）

- 删除局部变量 `lastRequestHistory`、`requestHistory`。
- 每轮：

  ```go
  modelHistory, err := s.compressContextBeforeLLM(ctx, state)
  // ...
  state.ModelHistory = modelHistory
  state.Messages = buildOpenAIMessages(state.SystemPrompt, state.ModelHistory)
  state.LastContextTokens = estimator.EstimateRequestTokens(state.SystemPrompt, state.ModelHistory, toolDefs)
  ```

- 轮末（`finishReason != "tool_calls"`）：将最终 assistant 追加进 `state.ModelHistory`（与 Stop 钩子把它追加进 `state.History` 对称），最终估算与落库 / 记忆提取统一用 `state.ModelHistory`；删除 `finalHistoryForEstimate` / `finalModelHistory` 构造。
- `scheduleMemoryWork(..., state.ModelHistory, ...)` 仅传单一历史参数（见 §3.4）。
- 其余保持：lockstep 把 assistant / tool 追加进 `History` 与 `ModelHistory`；mid-loop 记忆调用 `maybeUpdateSessionMemoryMidLoop(..., state.ModelHistory, ...)`——其源现在即压缩线，与轮末一致。

### 3.3 `internal/agent/runtime/hooks/types.go`

更新 `ModelHistory` 字段注释：明确它是"唯一的真实消息历史，每轮被压缩结果原地更新，下一轮复用；展示由 `History` 承担"，删除"appended in lockstep while staying uncompressed"的旧描述。

### 3.4 `internal/agent/runtime/conversation_memory.go`

`scheduleMemoryWork` 去掉重复的 `modelHistory` 形参，仅保留单一 `history`（即 `state.ModelHistory`）：落库（`UpsertConversationModelHistory`）、记忆提取（`extractMemories`）、会话记忆更新（`updateConversationMemory`）共用它。更新注释。

## 4. 行为变化（符合需求，明示）

mid-loop 记忆提取的源，从"未压缩逐字线"变为"压缩后真实消息线"（大工具结果为 `<persisted-output>` 预览、超预算时为摘要块）。这与轮末记忆提取行为**统一**，正是需求 2 所要求的"压缩和记忆的提取源头都用存储真实消息的 history"。

## 5. 兼容性

- 存储层（`internal/local/store.go`、`session_history_store.go`）零改动，落盘仍是 `history` / `model_history` 两份文件，老会话可正常恢复。
- 已落库的压缩线天然就是新模型期望的"真实消息历史"，无需迁移。

## 6. 受影响测试

  - `loadModelHistory` 系列用例不变。
- `internal/agent/runtime/runtime_test.go`：`upsertedModelHistory` 相关断言（落库内容 = 压缩后线 + 最终 assistant）核对；取消路径断言不变。
