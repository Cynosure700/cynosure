# 工具输出截断与工具结果压缩调整设计文档

## 1. 背景

当前 `cynosure` 的工具结果存在两条不同消费路径：

1. **发给下一轮 LLM 的模型历史**：工具执行后，完整结果先写入 `state.ModelHistory`；每轮请求 LLM 前，`ToolResultCompressionStrategy` 会按工具声明的 `maxResultSizeChars` 判断是否把大结果落盘，并在请求上下文中替换为 `<persisted-output>` marker。
2. **发给 TUI 的展示事件**：工具执行完成后，runtime 通过 `tool_call_done` 事件发送 `result_preview`；当前预览会做单行化、最多 3 行、最多 300 字符的摘要，TUI 只渲染这个 preview，不参与模型上下文。

本次需求要调整这两条路径的边界：

- 默认不截断任何工具发给下一轮 LLM 的输出。
- TUI 仍然截断工具输出，但改为按行数截断，最多展示 5 行，并用 `... + x lines` 表示省略。
- `read_persisted_output` 工具结果不进行压缩。
- 其他策略不变，不影响现有功能。

## 2. 现状核查

### 2.1 LLM 请求侧

相关代码：

- `internal/agent/runtime/context_compression.go`
- `internal/agent/runtime/compression/compression.go`
- `internal/agent/runtime/compression/tool_result_compression.go`
- `internal/tools/definitions.go`

当前行为：

1. `compressContextBeforeLLM` 从 `state.ModelHistory` 克隆 `RequestHistory`。
2. 默认压缩链顺序为：
   - `ToolResultCompressionStrategy`
   - `MessageWindowCompressionStrategy`
   - `RecentToolResultRetentionStrategy`
   - `ConversationMemoryStrategy`
   - `FullHistorySummarizationStrategy`
3. `ToolResultCompressionStrategy` 仅处理最后一条 user message 之后的 tool messages。
4. 每个 tool result 的字符数超过 `req.maxResultSizeChars(toolName)` 时，会完整落盘，并把内联结果替换为 `<persisted-output>` marker。
5. `req.maxResultSizeChars` 当前回退到 `tools.DefaultMaxResultSizeChars = 50000`。

因此，“默认不截断任何工具发给下一轮 LLM 的输出”需要改变默认工具结果预算语义：默认工具不应触发 `ToolResultCompressionStrategy`。但这不等同于删除所有压缩策略，`MessageWindowCompressionStrategy`、`RecentToolResultRetentionStrategy`、`ConversationMemoryStrategy`、`FullHistorySummarizationStrategy` 和 413 后的 `ReactiveCompactStrategy` 仍属于“其他策略不变”范围。

### 2.2 TUI 展示侧

相关代码：

- `internal/agent/runtime/conversation_flow.go`
- `internal/tui/app.go`
- `internal/tui/events_test.go`

当前行为：

1. `emitToolCallDone` 发送 `result_preview`。
2. `previewToolResult` 优先使用 `outcome.Audit.OutcomeSummary`，为空时使用 `outcome.Result`。
3. `toolAuditPostHook` 成功时把 `h.Outcome.Result` 截断到 500 字符作为 `OutcomeSummary`。
4. `previewToolResult` 会先 `singleLine`，再 `limitPreviewLines(..., 3)`，再按 300 字符截断。
5. TUI 在 `renderToolMessage` 中显示 `status · result_preview`。

这说明当前 TUI 预览已经和模型历史分离，但预览来源被审计摘要的 500 字符截断间接影响，且 `singleLine` 会消除换行，使“最多展示 5 行”无法生效。

### 2.3 `read_persisted_output`

相关代码：

- `internal/tools/persisted_output.go`
- `internal/tools/definitions.go`

`read_persisted_output` 会返回 JSON，其中 `content` 是按 `offset`/`limit` 读取出的内容分片。该工具通常用于读取已经被 `<persisted-output>` marker 指向的完整输出。如果它自己的结果再次被 `ToolResultCompressionStrategy` 落盘，会导致模型读取恢复链路变得循环且不直观，因此本次要求显式跳过该工具结果压缩。

## 3. 目标与边界

### 3.1 目标

1. 默认工具结果预算改为“不限制”，即默认不因为单个工具结果字符数超过 50,000 而落盘或替换成 `<persisted-output>`。
2. 对发给下一轮 LLM 的常规工具结果，默认保留完整内容。
3. `read_persisted_output` 的 tool result 永远跳过 `ToolResultCompressionStrategy`，即使未来有人为它声明了正数预算也不压缩。
4. TUI 展示仍然使用独立 preview，不把完整大结果刷到界面。
5. TUI 工具结果 preview 按原始输出行数截断，最多展示 5 行；如果原始输出超过 5 行，追加一行 `... + x lines`，其中 `x` 是被省略的行数。
6. 保留工具结果中的换行，让 TUI 能展示多行 preview。
7. 保持其他上下文压缩策略、工具执行、工具日志、审批、超时、历史持久化和 `read_persisted_output` 参数/返回格式不变。

### 3.2 非目标

1. 不删除 `ToolResultCompressionStrategy`。它仍作为可选 per-tool 正数预算能力存在，供未来某些工具显式声明上限时使用。
2. 不改变 `<persisted-output>` marker 格式、落盘目录、hash 去重逻辑或读取工具的参数格式。
3. 不改变 `micro_compact` 的 20/5 策略。
4. 不改变 `snip_compact`、会话记忆压缩、全量摘要压缩和 413 reactive compact 的触发逻辑。
5. 不新增用户配置项。
6. 不为 TUI 增加展开全文、折叠、分页或复制交互。
7. 不改变 `tools.md` 审计日志；日志继续保存完整工具结果。

### 3.3 关键解释

本设计把“默认不截断任何工具的输出，这里指的是发给下一轮 LLM 的”解释为：

- **不再通过默认 50,000 字符预算把工具结果落盘成 marker。**
- 但当上下文整体触发已有压缩策略时，仍可能发生消息窗口裁剪、旧工具结果占位、会话记忆注入或摘要兜底。这些属于既有“上下文压缩机制”，本需求要求其他策略不变。

## 4. 方案对比

### 方案 A：默认预算改为无限制，保留显式正数预算能力（推荐）

做法：

- 将工具声明中的默认 `MaxResultSizeChars` 从 `50000` 改为 `0`，语义为“不按单工具大小压缩”。
- `ToolResultCompressionStrategy` 中只有当工具预算 `> 0` 且结果字符数超过预算时才压缩。
- `read_persisted_output` 在策略中按工具名直接跳过。
- TUI preview 独立改造为 5 行行数截断。

优点：

- 精确满足“默认不截断发给下一轮 LLM 的工具输出”。
- 保留原有架构：工具声明仍可在未来为特定工具开启预算。
- 改动集中，不影响其他压缩层。
- `read_persisted_output` 的特殊语义清晰，不依赖默认值偶然生效。

缺点：

- 如果未来某个工具输出极大，默认会完整进入下一轮请求，可能更依赖后续整体上下文压缩和 413 兜底。

### 方案 B：删除 `ToolResultCompressionStrategy`

做法：

- 从主 Agent 和子 Agent 压缩链中移除 `ToolResultCompressionStrategy`。

优点：

- 默认完全不会做工具结果落盘。

缺点：

- 破坏已有 `<persisted-output>` / `read_persisted_output` 能力。
- 无法支持未来特定工具显式压缩。
- 改动范围大，和“其他策略不变”冲突。

### 方案 C：保留默认 50,000，只把当前内置工具逐个声明为无限制

做法：

- `DefaultMaxResultSizeChars` 保持 50,000。
- 对所有当前内置工具设置 `MaxResultSizeChars = 0`。
- `read_persisted_output` 单独跳过。

优点：

- 对未知 MCP 工具仍有默认保护。

缺点：

- 不符合“默认不截断任何工具”的字面语义。
- 新增工具如果忘记声明，会重新出现默认压缩。
- 规则更难解释和测试。

### 推荐

采用方案 A。它最直接地把默认行为改为“不按单工具大小压缩”，同时保留显式正数预算作为局部能力，满足需求且不扩大改造范围。

## 5. 详细设计

### 5.1 工具预算语义

调整 `internal/tools/definitions.go` 中的默认预算定义：

```go
const DefaultMaxResultSizeChars = 0
```

语义：

- `MaxResultSizeChars <= 0` 表示该工具结果不由 `ToolResultCompressionStrategy` 压缩。
- `MaxResultSizeChars > 0` 表示该工具结果超过该字符数时才落盘并替换为 `<persisted-output>` marker。
- `MaxResultSizeCharsForTool(name)` 对未知工具返回 `DefaultMaxResultSizeChars`，因此未知工具默认也不压缩。

为避免命名误导，可在实现阶段考虑保留常量名但更新注释，说明 `0` 是 unlimited；不强制重命名，避免扩大改动。

### 5.2 `ToolResultCompressionStrategy` 调整

调整 `internal/agent/runtime/compression/tool_result_compression.go`：

1. 继续使用 `toolNamesByCallID(history)` 从 assistant tool call 反查工具名。
2. 如果工具名是 `tools.ReadPersistedOutputToolName`，直接 `continue`。
3. 读取 `limit := req.maxResultSizeChars(toolName)`。
4. 如果 `limit <= 0`，直接 `continue`。
5. 只有 `chars > limit` 时才调用 `persistAndBuildMarker`。

伪代码：

```go
toolName := toolNames[history[idx].ToolCallID]
if toolName == agenttools.ReadPersistedOutputToolName {
    continue
}
limit := req.maxResultSizeChars(toolName)
if limit <= 0 {
    continue
}
chars := len([]rune(result))
if chars <= limit {
    continue
}
```

`req.maxResultSizeChars` 可继续保持“resolver nil 时回退默认值”的结构，但默认值为 `0` 后不再触发压缩。

### 5.3 TUI preview 行截断

调整 `internal/agent/runtime/conversation_flow.go` 中的 preview 生成逻辑。

新增常量：

```go
toolResultPreviewMaxLines = 5
```

`previewToolResult` 改为以原始结果为主要来源：

1. 成功或失败都优先使用 `outcome.Result`，因为它保留原始换行。
2. 如果 `outcome.Result` 为空，再回退到 `outcome.Audit.OutcomeSummary`。
3. 不再对结果调用 `singleLine`。
4. 按行截断到 5 行。
5. 如果总行数超过 5，追加 `... + x lines`。

建议实现一个小 helper：

```go
func previewToolResult(outcome toolExecutionOutcome) string {
    preview := strings.TrimSpace(outcome.Result)
    if preview == "" {
        preview = strings.TrimSpace(outcome.Audit.OutcomeSummary)
    }
    return truncatePreviewLines(preview, toolResultPreviewMaxLines)
}

func truncatePreviewLines(text string, maxLines int) string {
    text = strings.TrimSpace(text)
    if text == "" || maxLines <= 0 {
        return ""
    }
    lines := strings.Split(text, "\n")
    if len(lines) <= maxLines {
        return strings.Join(lines, "\n")
    }
    omitted := len(lines) - maxLines
    kept := append([]string(nil), lines[:maxLines]...)
    kept = append(kept, fmt.Sprintf("... + %d lines", omitted))
    return strings.Join(kept, "\n")
}
```

说明：

- 行数基于原始 `\n` 分割，不先压成单行。
- 输出超过 5 行时，最终 preview 为 6 行：前 5 行加一行省略提示。需求中的“最多展示 5 行”指真实工具输出最多展示 5 行，省略提示是额外说明行。
- 如果输出本身只有 5 行或更少，不添加省略提示。
- 继续由 TUI 的 `wrapText` 处理终端宽度换行。宽度换行可能让视觉行数超过 5，但语义上仍只展示 5 行原始输出。

### 5.4 TUI 渲染保持轻量

`internal/tui/app.go` 可以继续使用当前 `ToolCallView.ResultPreview` 字段和 `renderToolMessage` 逻辑。因为 `result_preview` 已经是 runtime 生成的多行 preview，TUI 只负责渲染：

```text
✓ Bash(command: ...)
  ⎿ success · line1
line2
line3
line4
line5
... + 7 lines
```

实现阶段可根据实际渲染效果微调缩进：如果多行 preview 的后续行没有缩进，可在 `renderToolMessage` 中把 `ResultPreview` 的换行替换为 `\n    ` 或类似现有工具卡片缩进。这只影响展示，不影响事件协议。

### 5.5 审计摘要保持不变

`toolAuditPostHook` 当前仍生成 500 字符 `OutcomeSummary`。本次不改变它，因为：

- 审计摘要用于工具调用记录和 `audit_summary`。
- TUI preview 改为优先使用 `Outcome.Result` 后，不再被 `OutcomeSummary` 的 500 字符截断限制。
- 保持审计字段不变能降低回归风险。

### 5.6 子 Agent 一致性

子 Agent 当前也通过 `compressSubagentContextBeforeLLM` 使用 `ToolMaxResultSizeChars` 和 `NewSubagentCompressor()`。本次改动应自然作用于子 Agent：

- 默认工具结果不再被 `ToolResultCompressionStrategy` 落盘。
- `read_persisted_output` 跳过压缩。
- 其他四层压缩策略保持不变。

实现阶段需要补充或调整子 Agent 相关测试，确认主 Agent 与子 Agent 的默认预算语义一致。

## 6. 数据流

### 6.1 LLM 请求侧

```text
工具执行完整结果
  -> appendToolMessageHook 写入 History 与 ModelHistory
  -> 每轮请求前 clone ModelHistory 为 RequestHistory
  -> ToolResultCompressionStrategy:
       read_persisted_output: 跳过
       limit <= 0: 跳过
       limit > 0 且 chars > limit: 落盘并替换 marker
  -> 后续压缩策略按原顺序执行
  -> buildOpenAIMessages 发送给 LLM
```

### 6.2 TUI 展示侧

```text
工具执行完整结果
  -> toolAuditPostHook 写审计摘要
  -> emitToolCallDone 调用 previewToolResult
  -> previewToolResult 保留最多 5 行原始输出
  -> tool_call_done event.result_preview
  -> TUI renderToolMessage 渲染轻量工具卡片
```

两条路径互不复用截断结果，避免 TUI 截断污染 LLM 上下文。

## 8. 风险与缓解

1. **风险：默认不压缩后，大工具结果更容易进入 LLM 请求。**
   - 缓解：保留 `MessageWindowCompressionStrategy`、`RecentToolResultRetentionStrategy`、`FullHistorySummarizationStrategy` 和 413 `ReactiveCompactStrategy`；同时保留 per-tool 正数预算能力供未来按工具恢复。

2. **风险：TUI 多行 preview 破坏工具卡片缩进。**
   - 缓解：在 TUI 测试中覆盖多行 preview；必要时只在 `renderToolMessage` 中增加换行缩进处理。

3. **风险：`read_persisted_output` 压缩跳过只靠默认 0，未来显式预算误伤。**
   - 缓解：在 `ToolResultCompressionStrategy` 中按工具名硬跳过，并增加测试锁定。

4. **风险：把 TUI 截断逻辑误用于模型历史。**
   - 缓解：preview 只在 `emitToolCallDone` 事件中生成；`appendToolMessageHook` 继续写入完整 `Outcome.Result`。

5. **风险：旧测试仍假设默认 50,000 会落盘。**
   - 缓解：测试语义改为“默认不压缩”和“显式正数预算压缩”两类，避免依赖旧默认值。

## 9. 实施清单

1. 调整工具默认预算语义：`DefaultMaxResultSizeChars = 0`，注释说明 `0` 表示不限。
2. 调整 `ToolResultCompressionStrategy`：
   - 跳过 `read_persisted_output`。
   - `limit <= 0` 时不压缩。
   - `limit > 0 && chars > limit` 时保留现有落盘逻辑。
3. 调整 runtime 工具结果 preview：
   - 新增 5 行行截断 helper。
   - `previewToolResult` 优先使用完整 `Outcome.Result`。
   - 删除结果 preview 的单行化和 300 字符截断路径。
4. 如有必要，调整 TUI 多行 preview 缩进。
5. 补充 compression、runtime preview、TUI 渲染测试。
6. 运行定向测试和必要的全量测试，确认其他压缩策略与工具能力未受影响。

## 10. 自检结论

- 本设计只新增/调整设计范围内的工具结果预算和 TUI preview 行截断，不要求实施阶段修改无关功能。
- `read_persisted_output` 的“不压缩”通过策略硬跳过保证，而不是依赖默认值。
- TUI 截断与 LLM 请求历史保持分离，不会把展示 preview 写回模型上下文。
- 其他压缩策略仍按原顺序执行，符合“其他策略不变”的约束。
- 没有新增用户配置项，也没有改变工具调用协议、审批、超时、持久化日志或 marker 格式。
