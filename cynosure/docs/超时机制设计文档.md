# Cynosure 超时机制设计文档

## 1. 需求

为 cynosure（`nano_cc`）项目新增超时控制，分四个层级：

| 层级 | 对象 | 超时阈值 |
| --- | --- | --- |
| 1 | 主 agent 单轮会话 | 24 小时 |
| 1 | 子 agent 单轮会话 | 1 小时 |
| 2 | 在终端执行的工具（bash） | 120 秒 |
| 3 | 其他普通工具（read/write/edit/load_skill/read_persisted_output/todo_write 等） | 60 秒 |

## 2. 约束（来自用户确认）

- **完全不使用 `context.Context` 形式实现超时**：不新增 `context.WithTimeout` / `context.WithCancel`，不修改现有 `ctx` 透传链路。采用 **时间看门狗（watchdog）** 模式：
  - agent 轮次超时 → 在循环每一轮入口做 **截止时间检查（deadline check）**；
  - bash 子进程超时 → `time.Timer` + `cmd.Process.Kill()` 终止进程；
  - 普通工具超时 → goroutine + `time.After` 看门狗。
- **阈值硬编码为常量**，不新增 config.json 配置项。
- 不影响相关功能的现有实现。

## 3. 现状分析

### 3.1 agent 会话循环
- 主 agent：`internal/agent/runtime/conversation_flow.go:106` 的 `for {}`，已有逻辑轮次上限 `maxRound = 50`（行 26），但无时间维度限制。
- 子 agent：`internal/agent/runtime/subagent.go:82` 的 `for round := 1; round <= maxRounds; round++`，上限 `defaultSubagentMaxRounds = 20`（行 20），同样无时间限制。

### 3.2 工具执行
- 统一调度：`runtime` 层 `executeToolCall` / `executeChildToolCall` → `ToolRegistry.Execute`（`tool_registry.go:89`）→ `tools.Dispatch`（`handlers.go:33`）→ 具体 handler。
- 终端工具：仅 `bash` 一个（handler `handleBash`，`handlers.go:52`；执行 `RunBashInDirWithOptions`，`bash.go:38`）。
- 现状 bash 已有 120s 超时，但**通过 `context.WithTimeout(context.Background(), defaultTimeout)` + `exec.CommandContext` 实现**（`bash.go:48-58`）。按"完全不用 context"的约束，此处需改写为 watchdog 模式。
- 其他普通工具（read/write/edit/load_skill/read_persisted_output、以及 todo_write）目前**无任何超时**。

## 4. 设计方案

整体思路：**纯时间度量 + 看门狗**，不引入 context。分三个独立改动点，互不影响现有功能。

### 4.1 agent 单轮会话超时（24h / 1h）—— 截止时间检查

**做法**：在循环开始前记录 `start := time.Now()`，每一轮入口判断 `time.Since(start)` 是否超过阈值，超过则返回超时错误并结束本轮会话。这是 no-context 下最贴合现有结构的方式，与现有 `maxRound` 逻辑上限正交叠加。

> 说明：deadline check 在"轮与轮之间"生效，是软边界 —— 它能可靠地阻止会话继续进入下一轮，但不会强行中断某一轮内正在进行的 LLM 流式请求（中断 in-flight 请求必须依赖 ctx，与约束冲突，故不做）。这对"单轮会话不超过 X 时长"的需求是合理且足够的边界控制。

**改动文件 1**：`internal/agent/runtime/conversation_flow.go`
- 新增常量：`mainAgentTurnTimeout = 24 * time.Hour`。
- 在 `RespondToConversation` 的 `for {}` 前记录 `turnStart := time.Now()`；在循环体 `round++` 之后、`maxRound` 检查附近，新增：

```go
if time.Since(turnStart) > mainAgentTurnTimeout {
    return storage.Message{}, fmt.Errorf("main agent turn timed out after %v", mainAgentTurnTimeout)
}
```

**改动文件 2**：`internal/agent/runtime/subagent.go`
- 新增常量：`subAgentTurnTimeout = 1 * time.Hour`。
- 在 `runSubagentLoop` 的 `for` 前记录 `turnStart := time.Now()`；在循环体入口新增：

```go
if time.Since(turnStart) > subAgentTurnTimeout {
    return openai.ChatCompletionMessage{}, fmt.Errorf("subagent turn timed out after %v", subAgentTurnTimeout)
}
```

### 4.2 终端工具（bash）超时（120s）—— 改写为 watchdog + Process.Kill

**改动文件 3**：`internal/tools/bash.go`
- 保留常量语义，重命名/明确为 `terminalToolTimeout = 120 * time.Second`（替换现有 `defaultTimeout`）。
- 改写 `RunBashInDirWithOptions`，移除 `context` 依赖：用 `exec.Command`（非 `CommandContext`）启动，启动后用 `time.AfterFunc(terminalToolTimeout, func(){ _ = cmd.Process.Kill() })` 设置看门狗，命令返回后 `timer.Stop()`，并据是否被 kill 判定超时。

伪代码：

```go
cmd := exec.Command("bash", "-c", command)
if dir != "" { cmd.Dir = dir }

var timedOut atomic.Bool
timer := time.AfterFunc(terminalToolTimeout, func() {
    timedOut.Store(true)
    if cmd.Process != nil {
        _ = cmd.Process.Kill()
    }
})
output, err := cmd.CombinedOutput()
timer.Stop()

if timedOut.Load() {
    return "", fmt.Errorf("command timed out after %v", terminalToolTimeout)
}
// ……（截断/空输出处理保持不变）
```

- `import` 去掉 `context`，新增 `sync/atomic`。其余危险命令拦截、输出截断、空输出处理逻辑**完全不变**。

### 4.3 普通工具超时（60s）—— Dispatch 层看门狗

**改动文件 4**：`internal/tools/handlers.go`
- 新增常量：`normalToolTimeout = 60 * time.Second`。
- 在统一入口 `Dispatch` 中，对**非终端工具**包一层看门狗（终端工具 bash 由 4.2 自身的 120s 负责，不重复包裹）：

```go
func isTerminalTool(name string) bool { return name == "bash" }

// 在 Dispatch 内，对非 bash 工具：
func runWithTimeout(d time.Duration, name string, fn func() (ExecResult, error)) (ExecResult, error) {
    type res struct { out ExecResult; err error }
    ch := make(chan res, 1) // 缓冲 1，避免 goroutine 泄漏阻塞
    go func() { out, err := fn(); ch <- res{out, err} }()
    select {
    case r := <-ch:
        return r.out, r.err
    case <-time.After(d):
        return ExecResult{}, fmt.Errorf("tool %s timed out after %v", name, d)
    }
}
```

`Dispatch` 改造为：bash 直接调用现有逻辑（其超时在 bash.go 内部）；其余工具（含 `todo_write`）经 `runWithTimeout(normalToolTimeout, ...)` 执行。

> 说明：goroutine 看门狗对纯文件操作（read/write/edit）/技能加载已足够；超时只代表"放弃等待并返回错误"，底层 goroutine 因 channel 带缓冲不会泄漏阻塞。这些工具本质为本地同步操作，正常不会触发超时，该机制作为兜底防护。

## 5. 常量汇总（硬编码落点）

| 常量 | 值 | 位置 |
| --- | --- | --- |
| `mainAgentTurnTimeout` | `24 * time.Hour` | `conversation_flow.go` |
| `subAgentTurnTimeout` | `1 * time.Hour` | `subagent.go` |
| `terminalToolTimeout` | `120 * time.Second` | `bash.go`（替换原 `defaultTimeout`） |
| `normalToolTimeout` | `60 * time.Second` | `handlers.go` |

## 6. 影响范围与兼容性

- **不改动任何函数签名**，不改动 `ctx` 透传链路，不新增配置项。
- bash 行为对调用方无变化（仍返回 `command timed out after ...` 错误信息，阈值仍为 120s），仅内部实现由 context 改为 watchdog。
- 普通工具在正常场景（毫秒级完成）下无任何行为变化，仅新增超时兜底。
- agent 轮次超时为新增的软边界，正常会话远不会触及 24h/1h，不影响既有体验。
- `RunBash` / `RunBashInDir` 等导出函数签名保持不变。

## 7. 验证方式

- `go build ./...` 与 `go vet ./...` 通过。
- 现有测试（如有 bash/工具相关测试）保持通过。
- 手动核验：bash 执行 `sleep 200` 在 120s 后返回超时；普通工具逻辑无回归。

## 8. 不做的事（明确边界）

- 不中断正在进行的 LLM 流式请求（需 ctx，违反约束）。
- 不调整 MCP 工具（`mcp__` 前缀）的现有超时（其为远程调用，已有独立 callTimeout，且不属于"终端/普通工具"范畴）。
- 不新增 config.json 配置项（按约束硬编码）。
