# 编辑工具行号展示修正设计文档

## 1. 背景与目标

当前 cynosure 在 TUI 中以"带行号的 diff"形式展示 `edit_file`、`multi_edit` 的编辑过程，以及 `write_file` 的写入预览。但 `edit_file` 与 `multi_edit` 的行号是按 `old_string` / `new_string` **片段内部**的相对位置（从 1 开始）渲染的，而不是它们在**真实文件**中的行号。

例如对某文件第 100~102 行做修改，终端却显示为 `- 1 / - 2 / + 1 ...`，与用户在编辑器里看到的真实行号完全对不上，定位困难。

**目标**：让 `edit_file`、`multi_edit` 在 TUI 中展示的行号反映被改动文本在真实文件中的行号，且遵循标准 diff 的两套参照系——

- **`-`（删除）行的行号始终是原文件的行号**，表示"原文件的第 N 行被删除了"；
- **`+`（新增）行的行号始终是新文件的行号**，表示"新文件的第 M 行是新加的"。

`write_file` 已经是按整文件行号展示（见 §3.3），本次仅做验证、不改其行为。

**约束（用户明确要求）**：其他策略不变，不影响其他功能——即不改变模型上下文（LLM 看到的内容）、工具结果文本、审计日志、上下文压缩、持久化对模型可见的字段，以及非编辑类工具的展示。

## 2. 当前实现梳理

### 2.1 渲染链路（`internal/tui/app.go`）

- `renderToolMessage`（app.go:1124）按工具名分派到专用渲染器：
  - `renderWriteFileToolMessage`（app.go:1228）
  - `renderEditFileToolMessage`（app.go:1319）
  - `renderMultiEditToolMessage`（app.go:1331）
- 编辑类 diff 构建核心是 `buildEditPreviewBodyLines`（app.go:1404）→ `buildEditDiffLines`（app.go:1433）。
- `buildEditDiffLines(oldText, newText)` 把 `old_text`/`new_text` 各自按行切分，做公共前缀/后缀对齐，然后：
  - 上下文行编号 `idx + 1`（app.go:1441）
  - 删除行编号 `i + 1`（app.go:1447）
  - 新增行编号 `i + 1`（app.go:1453）
  
  这里的 `i` / `idx` 都是片段内偏移，**这就是 bug 根因**。
- `renderEditDiffLine`（app.go:1494）按 `"%c%2d│ %s"` 把 `Kind`、`Number`、`Text` 拼成一行。

### 2.2 数据来源

- 渲染只依赖 `ToolCallView.RawArgs`（即工具调用的原始参数 `old_text/new_text` 或 `files[].edits[]`），不持有文件内容，也不知道匹配发生在文件哪一行。
- 实时链路：runtime 执行工具后通过 `emitToolCallDone`（`internal/agent/runtime/conversation_flow.go:312`）下发 `tool_call_done` 事件，载荷含 `raw_args`、`status`、`result_preview` 等；TUI 在 `toolCallViewFromEvent`（app.go:910）/`updateToolCallDone`（app.go:808）回填到 `ToolCallView`。
  - 事件经由内存 channel 传递（`internal/tui/events.go:25` 的 `EventWriter.Event`），**不做 JSON 序列化**，因此事件载荷可携带任意 Go 值（如 `[][]int`）。
- 恢复链路（`/resume`）：`messagesForDisplay`（app.go:567）→ `reconstructToolCallMessage`（app.go:599）仅用持久化的 `assistant.ToolCalls[].Function.Arguments` 作为 `RawArgs`，同样不含文件内容；因此恢复后的编辑 diff 也走 `renderEditFileToolMessage`，目前同样显示从 1 开始的错误行号。

### 2.3 工具执行（`internal/tools`）

- `RunEditFromRoot`（file_ops.go:95）：读取文件 → `strings.Replace(content, oldText, newText, 1)` 写回。此处**原始文件内容可得**，能精确算出匹配起始行。
- `RunMultiEditFromRoot`（file_ops.go:129）：把多处编辑顺序应用到内存副本，每次 `applyEdit`（file_ops.go:165）；每个 edit 应用前的 `content` 即该 edit 的参照状态。

## 3. 问题分析

### 3.1 行号语义（两套参照系）

按用户明确的语义，diff 的两类行使用**两套独立的参照系**（即标准 unified diff 行号语义）：

- **`-` 行（删除行）的行号始终是原文件的行号**，表示"原文件的第 N 行被删除了"。
- **`+` 行（新增行）的行号始终是新文件的行号**，表示"新文件的第 M 行是新加的"。
- 上下文行（未改动、`Kind == ' '`）在两文件中都存在；本设计显示其**新文件（当前文件）行号**，表示"该行现在位于第几行"（用户只约束了 `-`/`+`，上下文取当前文件号最直观且与 `+` 一致）。

对一次 `edit_file`（`strings.Replace(..., 1)` 替换首个匹配）：

- 设替换点字节偏移 `idx = strings.Index(content, old_text)`，匹配区域起始行 `startLine = 1 + strings.Count(content[:idx], "\n")`（1-based）。
- 替换发生在局部，`idx` 之前的前缀在旧/新文件中**完全一致**，故"删除区域"在旧文件中的起始行与"新增区域"在新文件中的起始行**相同**，均为 `startLine`（即 `oldStart == newStart == startLine`）。
- **但这并不意味着每一行号都相同**：`old_text` 与 `new_text` 行数不同，会使删除块与新增块之后的编号产生分叉。因此 `buildEditDiffLines` 内部需维护**两个游标** `oldNo`、`newNo`（均从 `startLine` 起）：
  - 上下文行（前缀）：显示 `newNo`，随后 `oldNo++`、`newNo++`（前缀阶段二者相等）。
  - 删除行（来自 oldLines）：显示并自增 `oldNo`（`newNo` 不动）→ 这就是"原文件被删除的行号"。
  - 新增行（来自 newLines）：显示并自增 `newNo`（`oldNo` 不动）→ 这就是"新文件新增的行号"。
  - 上下文行（后缀）：显示 `newNo`，随后 `oldNo++`、`newNo++`。
- 示例（匹配区域起始于第 100 行，old 2 行、new 3 行）：

  ```
  - 100│ const old = "hello"
  - 101│ return false
  …
  + 100│ const new = "world"
  + 101│ return true
  + 102│ console.log("done")
  ```

  删除块用旧文件号 100/101，新增块用新文件号 100/101/102；二者前段重合、尾段因行数差而分叉，符合预期语义。

### 3.2 multi_edit

`multi_edit` 对同一文件按顺序应用多处编辑，渲染器把每个 edit 的 diff 拼成一段（`buildEditPreviewBodyLines` 遍历 `changes`）。每个 edit 需要各自的 `startLine`（在文件中的真实位置），其块内再按 §3.1 的双游标规则编号。

### 3.3 write_file 已正确（仅验证，不改）

`write_file` 的 `content` 是**整个新文件**，`renderWriteFileToolMessage` 用 `i+1`（app.go:1244）即新文件真实行号 1..N——这恰好等同于 §3.1 中 `+`（新增行）的"新文件行号"语义。它从不存在"片段相对行号"问题，因此**无需改动**。本设计会用一条针对性测试固化"write 行号 = 整文件行号"的行为，确保不被误伤。

### 3.4 谁拥有"真实行号"这一信息

- **执行时**（`RunEditFromRoot`/`RunMultiEditFromRoot`）拥有改动前的原始内容，可精确计算，且与 `strings.Replace` 实际命中的位置一致。
- **渲染时 / 恢复时**：TUI 不持有原始内容；但编辑完成后文件磁盘内容已含 `new_string`，可"读当前文件 + 定位 new_string"做近似回算。
- 这一差异决定了方案选择（见 §4）。

## 4. 可选方案与取舍

### 方案 A：执行时精确计算 + 通过 outcome/事件下发（实时精确），恢复时按当前文件回算

- runtime 执行编辑工具时计算每个改动的 `startLine`，经 `ToolExecutionOutcome`（加 `json:"-"` 字段，**不进入模型上下文/持久化内容**）→ `tool_call_done` 事件 → TUI。
- 恢复（`/resume`）因不持久化该信息，按"读当前文件定位 new_string"尽力回算，失败回退行号 1。
- 优点：实时展示**精确**（即便 `new_string` 在文件中出现多次也准确，因为用的是替换实际命中的位置）。
- 缺点：跨 `internal/tools`、`internal/agent/runtime`、`internal/tui` 多个包改动，surface 较大；实时与恢复两套机制，需各自验证。

### 方案 B：执行时精确计算 + 持久化展示元数据（实时与恢复都精确）

- 在 `storage.Message` 增加一个仅用于展示的可选字段（仿照现有 `Meta`，不进入 `buildOpenAIMessages` 因而不污染模型），把 `startLine` 落盘，恢复时直接读取。
- 优点：实时与恢复**都精确**。
- 缺点：改动持久化 schema 与 hook 落盘逻辑，blast radius 最大，与"不影响其他功能"取向最远。**不推荐**。

### 方案 C：纯 TUI 回算（推荐）

- 不改 runtime / 工具执行 / 事件协议 / 持久化 / 模型上下文，**仅改 `internal/tui`**。
- 编辑工具进入 `success` 时（实时在 `updateToolCallDone`，恢复在 `reconstructToolCallMessage`），**读取当前 workspace 文件一次**，对每个改动用 `strings.Index(content, new_string)` 定位起始行，缓存到 `ToolCallView`；渲染时直接用缓存值，不在渲染路径做文件 IO。
- `new_string` 在编辑后必然存在于文件中（编辑刚写入），故常见场景下精确。
- 优点：
  - 改动面最小，**完全不触碰模型上下文、工具结果文本、审计日志、压缩、持久化**，最契合"其他策略不变、不影响其他功能"。
  - 实时与恢复**同一套机制、表现一致**（符合"原样回放历史会话"）。
- 缺点 / 边界：
  - 若 `new_string` 在文件中出现多次，取首个匹配，可能与实际改动位置不符（极少见，且通常新文本具区分度）。
  - 同一轮对同一文件的多处顺序编辑，按**最终文件**定位各 `new_string`，得到的是改动在最终文件中的落点行号（对用户而言"现在在第几行"通常更直观），可能与"应用当刻的中间态行号"有出入。
  - 编辑后文件又被外部改动、或文件被删除：定位失败，回退行号 1（即当前行为，无回归）。

### 取舍结论

**推荐方案 C**。理由：用户本次明确强调"其他策略不变、不要影响其他的功能"，C 的改动严格限制在 TUI 展示层，零模型/持久化/协议影响，且实时与恢复一致；其精度在绝对主流场景（单处 edit、`new_string` 唯一）下与执行时精确计算等价，仅在 `new_string` 重复等罕见边界存在近似——相对"当前永远从 1 开始"是纯粹改进，无任何回归。

如果后续对实时精度有更高要求，可在不破坏本设计的前提下叠加方案 A 的执行时下发作为优先数据源、C 作为回退；本设计预留该扩展点（`ToolCallView` 的行号缓存字段一旦由事件填充即优先采用）。

## 5. 详细设计（方案 C）

### 5.1 行号缓存字段

`ToolCallView`（app.go:55）新增：

```go
// EditLineStarts 缓存每个被编辑文件、每处改动在真实文件中的 1-based 起始行，
// 仅用于编辑类工具（edit_file/multi_edit）的 TUI diff 行号展示。
// 维度：[文件索引][该文件内改动索引] = 起始行；0 或缺失表示未知，渲染回退为 1。
// 形状与 parseMultiEditDisplayFiles 返回的 []editDisplayFile 一一对应。
EditLineStarts [][]int
```

- `edit_file`：单文件单改动 → `[][]int{{startLine}}`。
- `multi_edit`：与 `parseMultiEditDisplayFiles` 解析出的文件/改动顺序对齐。

### 5.2 计算起始行（新增辅助，TUI 内）

新增 `computeEditLineStarts(workspaceRoot string, files []editDisplayFile) [][]int`：

- 对每个 `editDisplayFile`：
  - 用 `safety.SafePathFromRoot(workspaceRoot, file.FilePath)` 解析路径（越界/失败 → 该文件所有改动回退 1）。
  - `os.ReadFile` 读取当前内容（失败 → 回退 1）。
  - 对每个 `change`：`idx := strings.Index(content, change.New)`；命中则 `start := 1 + strings.Count(content[:idx], "\n")`，否则 `start = 0`（渲染回退 1）。
- 仅在工具 `success` 时计算；非编辑工具、非 success 不计算。
- `internal/tui` 引入 `cynosure/internal/safety`（叶子包，无循环依赖）。

### 5.3 实时填充

`updateToolCallDone`（app.go:808）在回填字段后，若该工具是 `edit_file`/`multi_edit` 且 `status == success`：

- `files, ok := parseMultiEditDisplayFiles(RawArgs)`（对 edit_file 用 `parseEditFileArgs` 包装为单文件单改动）。
- `m.messages[i].ToolCall.EditLineStarts = computeEditLineStarts(m.session.CWD, files)`。

> 文件在 `emitToolCallDone` 之前已由 `RunEditFromRoot`/`RunMultiEditFromRoot` 写盘，故此刻读盘内容已是编辑后的，`new_string` 必然存在。

### 5.4 恢复填充

`reconstructToolCallMessage` 增加 `workspaceRoot string` 入参，在 `status == success` 且为编辑工具时调用 `editLineStartsForTool`（内部解析 raw_args → `computeEditLineStarts`）填充 `EditLineStarts`。`messagesForDisplay` 也增加 `workspaceRoot string` 入参并透传；调用点 `handleResumeSelection` 传入 `m.session.CWD`。实时（`updateToolCallDone`）与恢复复用同一 `editLineStartsForTool` 辅助，保证表现一致。

### 5.5 渲染使用起始行（双游标编号）

每处改动只需缓存一个 `startLine`（§3.1 已论证一次 `edit` 内 `oldStart == newStart == startLine`），渲染时在块内派生出 `-`/`+` 各自的行号：

- `buildEditDiffLines(oldText, newText string, startLine int)`：
  - `startLine <= 0` 时取 1（保持当前行为，覆盖未知/恢复失败/老数据）。
  - 维护两个游标：`oldNo := startLine`（原文件行号）、`newNo := startLine`（新文件行号）。
  - 上下文行（前缀）：`Number = newNo`；随后 `oldNo++`、`newNo++`。
  - 删除行（来自 oldLines）：`Number = oldNo`；随后 `oldNo++` —— **始终是原文件行号**。
  - 新增行（来自 newLines）：`Number = newNo`；随后 `newNo++` —— **始终是新文件行号**。
  - 上下文行（后缀）：`Number = newNo`；随后 `oldNo++`、`newNo++`。
  - `…` 分隔行不变。
  - 说明：现有 `editDiffLine.Number` 字段无需改结构，只是其取值由"片段内序号"改为按上述游标计算的真实文件行号。
- `buildEditPreviewBodyLines(icon, filePath string, changes []editDisplayChange, startLines []int, status string, expanded bool)`：遍历 `changes` 时取 `startLines[k]`（越界/缺失 → 0 → 回退 1）传给 `buildEditDiffLines`。
- `renderEditFileToolMessage`：传 `EditLineStarts[0]`（不存在则 `nil`）。
- `renderMultiEditToolMessage`：按文件索引传 `EditLineStarts[fileIdx]`。
- `isExpandableToolMessage`（app.go:846）中对 `buildEditDiffLines` 的调用仅用于**计数**，行号不影响行数；传 `startLine` 占位（如 0/1）即可，逻辑不变。

### 5.6 write_file

不改渲染逻辑。新增/保留测试断言其行号即整文件 1..N（§6）。

## 6. 测试计划

均在 `internal/tui` 下，复用现有 `events_test.go` 风格（`renderMessage` + `plainTerminalText`）。需要真实文件，使用 `t.TempDir()` 写入已编辑后的文件内容，并通过 `SessionInfo{CWD: dir}` 注入 workspace root。

1. **edit_file 双参照系行号**：临时文件含若干行，目标改动落在第 N 行；构造 `old_text`（2 行）/`new_text`（3 行）并把"编辑后内容"写入文件；断言 `-` 行显示**原文件行号** `- N│ ...`、`- N+1│ ...`，`+` 行显示**新文件行号** `+ N│ ...`、`+ N+1│ ...`、`+ N+2│ ...`（验证删除块用旧号、新增块用新号，且尾段因行数差而分叉）。
2. **multi_edit 多处真实行号**：同一文件两处改动分别落在不同行段；断言两段 diff 各自从其真实行号开始（不再都从 1），且每段内 `-`/`+` 分别用旧/新文件号。
3. **回退行为**：文件不存在 / `new_string` 不在文件中 → 行号回退为 1，且不 panic（保证无回归）。
4. **/resume 一致性**：扩展/复用 `TestResumeReproducesToolCallsInOrder` 思路，恢复含 edit_file 的历史并把对应文件写入临时目录，断言恢复后的 diff 行号与实时一致。
5. **write_file 不回归**：写入多行 content，断言预览行号为 1..N（与改动前一致）。
6. **现有用例对齐**：`TestEditFileToolMessageRendersDiffPreview`（events_test.go:1435）、`TestMultiEditToolMessageRendersDiffPreviewByFile`（events_test.go:1469）当前断言 `- 1│ ...` 等从 1 起的行号——这些用例未提供真实文件，`computeEditLineStarts` 会回退为 1，断言仍成立；如为提升覆盖将其改造为提供真实文件，则需同步更新其期望行号（以"代码为事实"更新测试断言）。

验证命令：`go build ./...`、`go test ./internal/tui/ -count=1`、`go test ./... -count=1`。

## 7. 影响面

- 改动文件：仅 `internal/tui/app.go`（渲染器 + 新增 `computeEditLineStarts` + `ToolCallView` 字段 + `updateToolCallDone`/`reconstructToolCallMessage`/`messagesForDisplay` 填充）与 `internal/tui` 下测试文件。
- **不改动**：`internal/tools/*`（工具执行）、`internal/agent/runtime/*`（runtime、事件协议、outcome、hook）、`internal/agent/storage/*`（持久化 schema）、`internal/local/*`、提示词、模型上下文构建（`buildOpenAIMessages`）、压缩/审计逻辑。
- 模型看到的工具参数与结果、落盘内容、审计日志均**完全不变**。
- 新增对 `cynosure/internal/safety` 的依赖（叶子包，无循环）。

## 8. 风险与缓解

- **`new_string` 文件内重复**：取首个匹配可能偏差。缓解：相对当前"恒为 1"是纯改进；后续可叠加方案 A 执行时精确值作为优先来源（已预留 `EditLineStarts` 由事件填充则优先的扩展点）。
- **渲染期文件 IO**：仅在工具完成/恢复时各算一次并缓存，渲染路径零 IO，不影响滚动性能。
- **大文件读取**：一次性读取，编辑目标多为常规源码文件；如需可加读取上限（超限回退 1），不影响主流程。
- **并发对同一文件的编辑**：极少见且本身语义模糊，定位失败回退 1，不 panic。
