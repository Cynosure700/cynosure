# Cynosure 终端命令权限审批机制设计文档

## 1. 需求

调整终端命令执行的权限校验机制，引入**运行时交互式审批**：

1. **查询/搜索类操作**（工作区内外均可）：无需审批，直接执行。
2. **变更类操作**（替换、写、删除、`curl` 等，即除常规查找外的操作，工作区内外均如此）：执行前向用户申请权限。交互形态与截图一致：

   ```
   Bash command
     curl -s -o /dev/null ... https://www.baidu.com
     Curl Baidu homepage

   This command requires approval

   Do you want to proceed?
   ❯ 1. Yes
     2. Yes, and don't ask again for: curl *
     3. No
   ```

3. **审批结果处理**：
   - 通过（1 / 2）→ 继续执行；选项 2 额外把放行规则**持久化**，后续同类命令不再询问。
   - 不通过（3）→ **该轮对话立即结束**，且**不进行记忆与对话存储的收尾操作**。

## 2. 约束（来自用户确认）

- **审批覆盖工具范围**：`bash` + 专用写工具（`write_file` / `edit_file` / `multi_edit`）。
- **去除只读命令白名单**：不再维护"只读命令集"白名单。改为按**工具维度**判定（见 4.1）：专用查询/搜索工具天然无需审批，`bash` 一律需审批，写工具一律需审批。
- **放行规则记忆位置**：持久化到**工作区目录**下的 `<workspaceRoot>/.cynosure/settings.json`，按项目隔离生效。
- **bypass 全放行**：若工作区 `.cynosure/settings.json` 中配置 `"permissions": { "defaultMode": "bypassPermissions" }`，则一切命令直接放行，不再审批。
- **子 agent 同样审批**：子 agent（`spawn_subagent` 内部）执行工具的审批逻辑与主 agent 完全一致，共用同一审批通道与放行规则。
- 不影响相关功能的现有实现（静态校验、超时机制、记忆持久化等保持不变，审批是叠加在其之上的新拦截层）。

## 3. 现状分析

### 3.1 工具执行链路

```
TUI: Model.respond (app.go:294)
  └─ runtime.RespondToConversation (conversation_flow.go:55)
       └─ 工具循环 (conversation_flow.go:176)
            ├─ RunPreToolUse  (conversation_flow.go:178)   ← hook 拦截点，返回 err 即中断整轮
            ├─ emitToolCallStart (conversation_flow.go:181)
            ├─ executeToolCall   (conversation_flow.go:182 → tool_registry.go:214)
            │      └─ ToolRegistry.Execute (tool_registry.go:89) → tools.Dispatch (handlers.go:49)
            │             └─ handleBash (handlers.go:98) / handleWrite / handleEdit / handleMultiEdit
            ├─ RunPostToolUse (conversation_flow.go:186)
            └─ emitToolCallDone (conversation_flow.go:189)
```

### 3.2 现有校验机制（均为静态、自动判定，无人工审批）

- 危险命令黑名单：`bash.go:42` `dangerousCommandPattern`（`rm/sudo/dd...`）。
- 工作区路径越界校验：`handlers.go:111` `validateBashCommandPaths`；文件工具 `resolvePathFromContext`。
- 参数 schema 校验：`tool_registry.go:98` `ValidateToolArgs`。
- 配置开关 `BashAllowDangerousCommands` / `BashAllowOutsideWorkspace`（`runtime_env.go:10`）经 `RuntimeEnv` 透传。

**结论：当前不存在任何"向用户申请权限"的交互逻辑。**

### 3.3 TUI 事件通道现状

- `EventWriter`（events.go:25）是 **runtime → TUI 的单向 channel**。无从 TUI 回传到 runtime 的反向通道。
- TUI 已有可复用的"序号选择"交互范式：`/resume` 的 `resumeSelecting` 状态位 + 候选列表 + `enter` 分支拦截（app.go:180 / 396）。
- 工具消息已支持 `rejected` 状态展示（app.go:786 `toolIcon`、app.go:1159 `toolStyleForStatus`）。

### 3.4 会话收尾位置

会话结束分支 `conversation_flow.go:153-170`：`RunStop` 持久化 + `scheduleMemoryWork` 记忆收尾。会话锁通过 `handedOff` 转交收尾 goroutine，否则由 defer 释放（conversation_flow.go:78-86）。

## 4. 设计方案

整体思路：在工具循环中，对**需审批工具**插入一个"审批闸门"。审批通过 TUI 双向通道完成（runtime 发审批请求事件 → 用户选择 → 回传决定）。主 agent 与子 agent 共用同一审批闸门。

### 4.1 工具维度分类：是否需审批（去除白名单）

新增分类器（`internal/tools` 包内）：

```go
// internal/tools/approval.go (新增)

// RequiresApproval 按工具维度判定该调用是否需要审批，并给出放行规则候选。
func RequiresApproval(toolName string, args map[string]any) (need bool, rule string)
```

判定规则（**不再解析 bash 子命令、不再维护只读白名单**）：

| 工具 | 判定 | rule |
| --- | --- | --- |
| `bash` | **一律需要审批** | 取 `command` 首 token 作为命令名，rule 为 `<cmd> *`（如 `curl *`、`ls *`）。命令名无法解析时回退为 `bash *` |
| `write_file` / `edit_file` / `multi_edit` | **一律需要审批** | `<tool> *`（如 `write_file *`） |
| `read_file` / `grep` / `glob` / `ls` / `web_search` / `load_skill` / `todo_write` / `read_persisted_output` / `web_fetch` / `spawn_subagent` | **无需审批** | — |

> 设计依据：查询/搜索由专用工具（`read_file`/`grep`/`glob`/`ls`/`web_search`）完成，这些工具天然放行，满足"查询、搜索无需校验"。所有副作用集中在 `bash` 与写工具，因此对它们一律审批。**不再区分 bash 内部命令是否只读**——即使 `bash` 内执行 `ls`，也走审批（用户可用选项 2 记住 `ls *` 后续放行）。这简化了实现，避免白名单维护成本与误判风险。
>
> rule 仅用于"don't ask again"的匹配粒度：bash 以命令名通配（`curl *`），写工具以工具名通配（`write_file *`）。

### 4.2 持久化放行规则与 bypass 模式（工作区 settings.json）

放行规则与权限模式存储在**工作区目录**下的 `<workspaceRoot>/.cynosure/settings.json`（按项目隔离）：

```json
{
  "permissions": {
    "defaultMode": "bypassPermissions",
    "allowedRules": ["curl *", "write_file *"]
  }
}
```

- **bypass 模式**：`permissions.defaultMode == "bypassPermissions"` 时，**所有命令直接放行，不再审批**（最高优先级，先于规则匹配判定）。其它取值（含缺省/空）走正常审批流程。
- **放行规则** `permissions.allowedRules`：命中即视为已放行、无需再询问。匹配为前缀通配（`curl *` 命中所有 `curl` 开头命令；`write_file *` 命中所有 `write_file` 调用）。
- 读取：`config` 包新增 `LoadWorkspacePermissions(workspaceRoot) (Permissions, error)`（`Permissions{DefaultMode string, AllowedRules []string}`）。**每次审批时实时读取**工作区 settings.json（文件不存在时返回零值），从而运行中修改配置即时生效。工作区路径新增 `WorkspaceCynosureSettingsPath(workspaceRoot)`（与 `WorkspaceCynosureMarkdownPath` 同级目录）。
- 写入：新增 `AppendWorkspaceApprovalRule(workspaceRoot, rule string) error`，读取-去重-回写工作区 settings.json（保留其它字段，文件/目录不存在则创建）。

> 选项 2 "Yes, and don't ask again for: X" 选中时：本轮放行 **且** 调用 `AppendWorkspaceApprovalRule` 持久化到工作区 settings.json。
>
> 注意：此文件与 `~/.cynosure/settings.json`（LLM env 配置，见 local_config.go:104）不是同一个；本机制使用**工作区级**配置，互不影响。

### 4.3 双向审批通道（TUI ↔ runtime）

`EventWriter` 当前单向。新增**审批请求/响应**机制：

**方案**：在 `runtime.Service` 调用侧注入一个 `ApprovalDecider` 接口，由 TUI 实现。runtime 在审批闸门处同步调用它（阻塞等待用户决定），TUI 实现内部通过 bubbletea 的消息机制弹出选择并把结果送回。

```go
// internal/agent/runtime 新增接口
type ApprovalRequest struct {
    ToolName    string
    Title       string // 如 "Bash command"
    CommandText string // 完整命令 / 文件路径
    Description string // bash 的 description 参数 / 操作摘要
    Rule        string // 放行规则候选，如 "curl *"
}

type ApprovalDecision int
const (
    ApprovalYes ApprovalDecision = iota   // 1. Yes
    ApprovalYesAlways                      // 2. Yes, and don't ask again
    ApprovalNo                             // 3. No
)

type ApprovalDecider interface {
    // Decide 阻塞直到用户作出选择；ctx 取消（Ctrl+C）时返回 ApprovalNo。
    Decide(ctx context.Context, req ApprovalRequest) (ApprovalDecision, error)
}
```

- `RespondToConversation` 在 `Service` 上挂 `Approver ApprovalDecider`。主 agent 与子 agent 共用同一个 `s.Approver`。
- TUI 侧：`Model` 实现 `ApprovalDecider`。由于 `respond` 已在独立 goroutine（app.go:294-308），`Decide` 可阻塞等待；它向 TUI 主循环发送一个 `approvalRequestMsg`，主循环进入 `approving` 选择态（仿 `resumeSelecting`），用户按 `1/2/3` 后通过一个 `chan ApprovalDecision` 把结果回传给阻塞中的 `Decide`。
- **并发约束**：子 agent 在主 agent 工具调用（`spawn_subagent`）内部同步运行，二者不会同时发起审批，故单一审批通道无并发竞争。

**TUI 改动点**（app.go）：
- `Model` 新增字段：`approving bool`、`approvalReq *ApprovalRequest`、`approvalReply chan ApprovalDecision`、`approvalCursor int`。
- `Update` 的 `tea.KeyMsg`：当 `approving` 时拦截 `up/down/1/2/3/enter`，选定后写入 `approvalReply` 并退出选择态；`ctrl+c` 视为 No。
- 渲染：在 transcript 末尾渲染审批面板（标题、命令、三选项、光标 `❯`），复用现有 lipgloss 样式。
- 收到 `approvalRequestMsg` 时进入 `approving=true` 并渲染。

### 4.4 审批闸门接入工具循环（主 agent + 子 agent）

在 `conversation_flow.go`（主 agent，工具循环 conversation_flow.go:176）与 `subagent.go`（子 agent，工具循环 subagent.go:114）中，于 `executeToolCall` / `executeChildToolCall` 之前插入同一审批判定：

```go
for _, tc := range msg.ToolCalls {
    toolCtx := &ToolUseContext{...}
    if err := s.hookManager().RunPreToolUse(ctx, toolCtx); err != nil { return ..., err }

    // —— 新增：审批闸门 ——
    decision, approved := s.approveToolCall(ctx, tc)   // 解析 args → RequiresApproval → Approver.Decide
    if !approved {
        // 用户拒绝：标记本轮被拒，跳出，进入"不收尾结束"分支
        rejected = true
        // 给该 tool_call 写一条 rejected 的 tool 结果，发 tool_call_done(status=rejected)
        ...
        break   // 跳出 for，并在外层结束本轮
    }
    if decision == ApprovalYesAlways {
        _ = config.AppendWorkspaceApprovalRule(s.Cfg.WorkspaceRoot, rule)  // 持久化到工作区
    }

    emitToolCallStart(...)
    toolCtx.Outcome = s.executeToolCall(...)
    ...
}
```

`approveToolCall` 逻辑（主/子 agent 共用）：
1. 解析 `tc.Function.Arguments`；`need, rule := tools.RequiresApproval(name, args)`。不需审批 → 直接放行。
2. **实时读取**工作区权限：`perms := config.LoadWorkspacePermissions(s.Cfg.WorkspaceRoot)`。
3. **bypass**：`perms.DefaultMode == "bypassPermissions"` → 直接放行（最高优先级）。
4. 命中已放行规则（`perms.AllowedRules`，前缀通配）→ 直接放行。
5. `s.Approver == nil`（理论上无审批通道，见 4.5）→ 直接放行。
6. 否则调用 `s.Approver.Decide(ctx, req)`，返回决定；若 `ApprovalYesAlways` 则 `AppendWorkspaceApprovalRule` 持久化。

### 4.5 子 agent 行为与无通道边界

- **子 agent 同样审批**：子 agent 工具循环（subagent.go:114-131）接入与主 agent 完全一致的 `approveToolCall`，共用 `s.Approver`、共用工作区放行规则与 bypass 模式。
- 子 agent 拒绝处理：用户拒绝时，子 agent 立即返回错误（如 `"subagent tool rejected by user"`），由父 agent 的 `spawn_subagent` 调用收到 rejected 结果，进而触发父轮的"拒绝后结束且不收尾"流程（见 4.6）。
- **无审批通道边界**：仅当 `s.Approver == nil`（例如未来纯 CLI/批处理入口未注入 Approver）时，审批闸门放行交给下游现有静态规则（危险命令黑名单 + 路径校验）。TUI 入口始终注入 Approver，正常场景不会触发此分支。

### 4.6 拒绝后"该轮结束且不收尾"

当本轮存在被拒工具调用（`rejected == true`）：

1. 为被拒的 `tool_call` 追加一条 `tool` 角色结果消息（`status: rejected`，内容如 `"Error: user rejected this operation"`），保证 OpenAI tool_call 协议完整（每个 tool_call 必须有对应 tool 结果），避免后续上下文损坏。但**因为要立即结束本轮，不再回灌模型**。
2. 跳出工具循环，**直接 `return`**：
   - **不调用** `RunStop`、**不调用** `scheduleMemoryWork`。
   - `handedOff` 保持 `false`，由 defer（conversation_flow.go:78）释放会话锁。
   - 返回一个轻量的 assistant 消息（或空消息 + 特定 sentinel），TUI 据此结束 `running` 状态并提示"操作已被拒绝，已结束本轮"。

> 关键点：拒绝路径**绕过** conversation_flow.go:162-169 的收尾块，从而满足"不进行记忆和对话存储的收尾操作"。模型历史的本轮增量（assistant + tool 消息）**不落库**（因为落库发生在 `scheduleMemoryWork` 的 `UpsertConversationModelHistory`，被跳过）。

### 4.7 系统提示词（可选，低优先级）

无需改提示词即可工作。审批是 runtime 侧硬拦截，模型无感知；被拒时本轮直接结束。

## 6. 不改动 / 保持兼容

- 现有静态校验（危险命令黑名单、路径越界、schema 校验、超时）全部保留，审批是叠加层。
- 正常通过审批的会话，收尾流程（RunStop + scheduleMemoryWork）完全不变。
- `EventWriter` 单向事件流不变，审批走独立的 `ApprovalDecider` 接口，互不干扰。
- 工作区未配置 `permissions` 时：`DefaultMode` 为空（非 bypass）、`AllowedRules` 为空，即对 bash/写工具均审批——这是默认安全行为。

## 7. 待确认的实现细节

1. **bash rule 粒度**：`curl ...` 生成 `curl *`，命中后该工作区内所有 `curl` 命令免审批。若希望更细粒度（如仅放行特定参数），可后续扩展；当前按命令名通配，与截图一致。
2. **装配解耦**：`runtime.Service` 不能直接 import `tui`。`ApprovalDecider` 接口定义在 runtime 包，由 tui 的 Model 实现并在 `tui.Run`/装配时注入到 Service。需确认 Service 当前如何被 TUI 持有（`Model.runtime *runtime.Service`，app.go:88），注入方式为创建后 `service.Approver = &model` 或构造参数。
3. **拒绝后返回值形态**：返回空 assistant 消息 + nil error，TUI 显示系统提示；还是返回带哨兵标记的 error 由上层识别。倾向前者（非错误，正常结束）。
4. **bypass / 放行规则读取时机**：**每次审批时实时读取**工作区 settings.json，运行中修改配置即时生效。

## 8. 验证计划

- 单测：`approval_test.go` 覆盖分类器（read/grep/glob/ls/web_search 放行；bash/write_file/edit_file/multi_edit 需审批；bash rule = 首 token + ` *`）。
- 单测：`config` 读写工作区 `permissions.allowedRules` 往返、去重；`bypassPermissions` 解析。
- 手动 TUI 验证：
  - 执行 `read_file` / `grep` → 无审批直接执行。
  - 执行 `bash: curl ...` → 弹审批面板；选 1 执行一次；选 2 执行且工作区 `.cynosure/settings.json` 写入 `curl *`，再次执行不再询问；选 3 → 本轮结束、提示被拒、会话历史无本轮增量。
  - `write_file` → 弹审批。
  - 工作区 settings.json 配 `"defaultMode": "bypassPermissions"` → 所有命令（含 curl/写工具）直接执行，不弹审批。
  - 子 agent 内执行变更命令（如 `spawn_subagent` 让子 agent 跑 `curl`）→ 同样弹审批；拒绝则子 agent 失败、父轮结束不收尾。
