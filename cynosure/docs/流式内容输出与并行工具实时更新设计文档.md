# 流式内容输出与并行工具实时更新设计文档

> 状态：已实现（2026-06-23）。runtime 与 TUI 改动完成，相关单测已更新并通过；新增并行工具即时 done 单测。

## 一、背景与目标

当前主/子 Agent 的流式回答链路在 `internal/agent/runtime/conversation_flow.go` 完成，TUI 渲染在 `internal/tui/app.go` 完成。本次优化包含三项需求，且要求“其他策略不变，不影响现有功能”：

1. **不再输出思考中的内容（reasoning_content）**，改为输出**每一轮的 content 内容**（包括会触发工具调用的轮次）。
2. **模型开始最终回答时，不再删除（折叠隐藏）前面的所有内容**，包括工具调用以及每一轮的 content，全部保留可见。
3. **多个工具并行执行时，某个工具先执行完即立即更新其展示信息**，无需等待整批工具全部完成。

## 二、现状分析

### 2.1 流式事件产生（runtime）

- `runModelRoundStream`（`conversation_flow.go:518`）：
  - `choice.Delta.Content` → 累加，并缓冲为 `assistantDeltaEvent`（延迟到上层决定是否下发）。
  - `choice.Delta.ReasoningContent` → 累加，并**立即**下发 `reasoningDeltaEvent`。
- `runModelRoundWithRecovery`（`:435`）：正常返回分支仅在 `shouldEmitAssistantContentDeltas(finishReason, toolCalls)`（即非工具轮）时才 `flushContentDeltas`。**因此工具轮的 content 被缓冲但从不下发**，工具轮只下发了 reasoning。
- 轮末 Stop 钩子 `emitAssistantStopHook`（`hooks/stop.go:16`）下发最终 `assistant` 事件（含 `content`、`reasoning_content`、`final=true` 及 meta）。
- reasoning 仍会累加进 `msg.ReasoningContent` 并随 assistant 消息落库（`cumulativeReasoning`、`storage.Message.ReasoningContent`）。

### 2.2 并行工具执行（runtime）

`executeToolCallBatch`（`:222`）：
1. 串行跑 PreToolUse + 审批，串行 `emitToolCallStartWithOptions`（全部 start）。
2. 起 goroutine 并发执行每个工具，`wg.Wait()` 等待**全部完成**。
3. 之后**串行循环**：更新 todos → RunPostToolUse 钩子（落库/追加 tool 消息）→ `emitToolCallDoneWithOptions` → `ToolCallCount++` → `emitMeta`。

即所有 done 事件都在全部工具完成后才统一下发。

### 2.3 TUI 渲染（app.go）

- `reasoning_delta` → `appendThinkingDelta`，渲染为 “✽ 思考中”。
- `shouldShowReasoningAt`（`:860`）：running 且当前 assistant 尚无 content 时显示 reasoning。
- `shouldHideMessageAt`（`:869`）+ `hasAssistantContentAfter`（`:879`）：一旦后面出现“有 content 的 assistant 消息”，就**隐藏其前面的所有 tool 消息、thinking 消息、以及只有 reasoning 无 content 的 assistant 消息**。`renderToolMessage` 的 `hideResult` 同源（最终答案出现后隐藏工具结果）。
- “thinking” role 的创建路径已不存在（仅 reasoning 走 assistant 消息的 `ReasoningContent`），但渲染/转换分支仍在。

## 三、设计方案

### 3.1 需求 1：输出每轮 content、停止输出 reasoning

**runtime：**
- `runModelRoundStream`：删除 `reasoningDeltaEvent` 的下发；**保留** `reasoningContent` 的累加与写入返回消息（落库/记忆不变）。
- `runModelRoundWithRecovery`：正常返回分支改为**始终** `flushContentDeltas`（不再按是否工具轮设门槛），使工具轮的 content 也实时下发。截断/续写分支已有的 flush 行为保持不变。
- 删除 `shouldEmitAssistantContentDeltas`（不再被引用）。

**TUI：**
- 移除 `reasoning_delta` 事件分支与 `appendThinkingDelta`。
- 移除 “✽ 思考中” 渲染、`shouldShowReasoningAt`、`renderMessageAt` 中的 `showReasoning` 逻辑、`"thinking"` role 渲染/转换分支；`isLiveAssistantRole` 简化为 `role == "assistant"`。
- 保留 `Message.ReasoningContent` 字段（仍由最终 `assistant` 事件回填，用于与落库一致），但不再参与渲染。

> 行为效果：每轮模型 content 以 `assistant_delta` 实时流式显示；工具轮若有 content 则显示在该工具调用上方，作为独立 assistant 消息块。

### 3.2 需求 2：最终回答出现后不折叠前面内容

**TUI：**
- 移除 `shouldHideMessageAt` 及其在 `renderMessages` 中的调用（不再隐藏任何消息）。
- `renderMessageAt`/`renderToolMessage` 的 `hideResult` 恒为 `false`（工具结果始终可见）。
- 移除仅服务于隐藏判断的 `hasAssistantContentAfter`（确认无其他用途后删除）。

> 行为效果：transcript 变为追加式——第 1 轮 content、工具调用与结果、第 2 轮 content……直到最终答案，全部保留。最终 `assistant` 事件仍用 `replaceLastAssistant` 覆盖“最终轮已流式出的同一条 assistant 消息”，不产生重复。

### 3.3 需求 3：并行工具完成即时更新

**runtime（`executeToolCallBatch`）：**
- 在每个工具的执行 goroutine 内，工具执行完成后**立即** `emitToolCallDoneWithOptions`（仅用于 UI 即时更新；done 事件经 channel 下发，多 goroutine 并发发送安全）。
- `wg.Wait()` 之后保留原有**串行**收尾，但**不再重复下发 done**：仅执行 todos 更新、RunPostToolUse 钩子（落库/追加 tool 消息，必须串行以保证消息顺序与避免对 `state.Messages/History/ModelHistory` 的数据竞争）、`ToolCallCount++`、`emitMeta`。

**正确性说明：**
- done 事件的 `result_preview` 由 `previewToolResult` 计算，优先取 `outcome.Result`（工具执行时已就绪），失败时为 `Error: ...`，无需依赖 PostToolUse。
- done 事件的 `audit_summary` 在 goroutine 阶段尚缺 `OutcomeSummary`（由 `toolAuditPostHook` 串行补齐），但 TUI **不消费** `audit_summary`（已确认），落库审计仍由串行 `persistToolCallHook` 用完整 audit 完成，故不影响持久化。
- start 仍串行先发，done 改为按**完成顺序**下发；TUI `updateToolCallDone` 按 tool id 原地更新，乱序无碍。子 Agent 的 `tool_call_group_clear` 仍在子 Agent 执行内、父 `spawn_subagent` done 之前发送，顺序不变。
