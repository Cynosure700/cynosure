# 会话记忆异步化与分布式锁设计文档

## 1. 背景与目标

### 1.1 需求
每轮对话结束后，需要执行一系列「会话收尾操作」（记忆提取、记忆更新等）。当前这些操作是**同步阻塞**执行的，会拖慢用户感知到的响应尾延迟。需求如下：

1. 将每轮对话结束后的收尾操作（记忆提取/更新）改为**异步执行**。
2. 对**会话**加一把**分布式锁**：收尾操作开始时加锁，完成后释放锁。
3. 当用户在收尾操作尚未完成前**再次进入同一会话**时，需要**等待锁释放**后再继续。

### 1.2 目标
- 用户的回答返回不再被记忆提取/更新阻塞，响应更快。
- 同一会话的收尾操作与下一轮请求之间，通过分布式锁保证**串行、不并发冲突**（避免 `SetConversationHistory` 与 `ReplaceConversationMemories` 互相覆盖产生竞态）。
- 锁具备 TTL 自动过期能力，避免进程崩溃导致死锁。

### 1.3 非目标
- 不改变记忆提取/更新的业务逻辑本身（prompt、整合裁剪规则等保持不变）。
- 不引入新的中间件（如 etcd），复用现有 Redis。

## 2. 现状分析

### 2.1 收尾操作的触发位置
文件 `go-agent/internal/web/runtime/conversation_flow.go`，函数 `RespondToConversation`：

```go
// conversation_flow.go:82-91
if finishReason != "tool_calls" || len(msg.ToolCalls) == 0 {
    stopCtx := &StopContext{...}
    if err := s.hookManager().RunStop(ctx, stopCtx); err != nil { // 持久化历史(MySQL+Redis) + SSE 下发
        return storage.Message{}, err
    }
    if s.EnableMemory {
        s.extractMemories(ctx, user, append(state.History, stopCtx.AssistantMessage))          // 同步、阻塞、多次 LLM 调用
        s.updateConversationMemory(ctx, conversation, user, append(state.History, stopCtx.AssistantMessage)) // 同步、阻塞、1 次 LLM 调用
    }
    return stopCtx.AssistantMessage, nil
}
```

存在的问题：
- `extractMemories` / `updateConversationMemory` 在 `return` 之前**同步执行**，每个内部都有若干次 LLM 调用，显著增加尾延迟。
- 两者共用入站 HTTP 请求的 `ctx`。一旦客户端断开或请求结束，`ctx` 被取消会中断这些后台写入。
- 无任何并发保护：同一会话并发请求时，历史与会话记忆的写入可能互相覆盖。

### 2.2 现有基础设施
- `Store.Redis`（`go-redis/v9`）已就绪（`go-agent/internal/web/storage/store.go:38-42`），可直接用于实现分布式锁。
- 已有 Redis key 命名约定（`go-agent/internal/web/storage/cache.go`：`conversation-cache:<id>`、`session:<id>`）。
- `idgen.New(prefix)` 可生成唯一字符串（用于锁 token）。

## 3. 方案设计

### 3.1 总体思路
1. 在 `storage` 层新增一组基于 Redis 的**分布式锁原语**（带等待获取 / 续期 / 释放）。
2. 在 `RespondToConversation` **入口处获取会话锁**：若锁被占用（上一轮收尾尚未完成）则**阻塞等待**直到拿到锁或等待超时。
3. 获取锁后，由一个**续期看门狗**在请求处理期间定期为锁续期，避免长对话（多轮工具+LLM）期间锁因 TTL 提前过期。
4. 一轮对话结束、响应返回给用户后，把锁的所有权**移交给异步收尾 goroutine**：它用独立 background context（带超时）执行 `extractMemories` + `updateConversationMemory`，**完成后停止续期并释放锁**。
5. 收尾期间锁仍被持有，因此下一次进入同一会话会在入口处等待，直到收尾完成释放锁。

### 3.2 分布式锁设计（Redis）

**Key**：`conversation-lock:<conversationID>`

**加锁**：`SET key <token> NX PX <ttl>`
- `token`：每次加锁生成的唯一值（`idgen.New("lock")`），用于安全续期/释放，避免误删他人持有的锁。
- `ttl`：锁的过期时间。由于锁要覆盖「整个对话处理 + 异步收尾」全过程，时长不可控，因此采用**较短 TTL + 周期续期**：TTL 作为崩溃保护的上限（进程崩溃后最多 TTL 时间锁自动失效），存活期间由看门狗续期。

**阻塞获取（带等待）**：入口需要拿到锁才能继续。`AcquireConversationLock` 内部轮询 `SET NX`（间隔约 100ms），直到成功或达到等待超时；等待期间响应 context 取消则立即返回。这天然实现了「上一轮收尾未完成 → 新请求等待」的语义。

**续期**：使用 Lua 脚本，先比对 token 再 `PEXPIRE`（只续自己持有的锁）：
```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("PEXPIRE", KEYS[1], ARGV[2])
else
    return 0
end
```

**释放**：使用 Lua 脚本，先比对 token 再删除（保证原子性 & 只释放自己持有的锁）：
```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

> 锁的生命周期：**入口 Acquire（拿到 token）→ 处理对话期间看门狗周期续期 → 异步收尾完成后 Release**。整个过程持有同一个 token，收尾阶段不再重复加锁，只负责最终释放。

### 3.3 关键改造点

#### (A) `storage` 层：新增锁文件 `go-agent/internal/web/storage/lock.go`
新增方法（挂在 `*Store` 上）：
- `AcquireConversationLock(ctx, conversationID, token string, ttl, waitTimeout time.Duration) (bool, error)` —— 阻塞获取，被占用时轮询等待至 `waitTimeout`。
- `RenewConversationLock(ctx, conversationID, token string, ttl time.Duration) (bool, error)` —— 续期（Lua 比对 token + PEXPIRE）。
- `ReleaseConversationLock(ctx, conversationID, token string) error` —— 释放（Lua 比对 token + DEL）。
- 私有 helper：`conversationLockKey(id) = "conversation-lock:" + id`（放在 `cache.go` 或 `lock.go`）。

#### (B) `runtime` 层：扩展 store 接口
`go-agent/internal/web/runtime/runtime.go` 的 `conversationStore` 接口新增上述 3 个方法签名，使 `Service.Store` 可调用。

#### (C) `runtime` 层：改造 `RespondToConversation`
1. **入口获取锁 + 启动续期看门狗**（`conversation_flow.go:28` 函数体最前，`loadConversationMessages` 之前）：
   ```go
   var lockToken string
   var stopRenew func() // 停止看门狗
   if s.EnableMemory {
       token := idgen.New("lock")
       ok, err := s.Store.AcquireConversationLock(ctx, conversation.ID, token, s.Cfg.ConversationLockTTL, s.Cfg.ConversationLockWaitTimeout)
       if err != nil {
           logger.Warn(...) // Redis 异常：降级，lockToken 置空，后续不续期/不释放/不收尾
       } else if !ok {
           logger.Warn(...) // 等待超时仍未拿到锁：降级放行（不阻死用户请求）
       } else {
           lockToken = token
           stopRenew = s.startLockRenewer(conversation.ID, token) // 后台周期续期
       }
   }
   ```
   说明：获取锁失败（Redis 异常或等待超时）时**降级放行**，仅记录告警，避免锁异常导致整个会话不可用；此时 `lockToken` 为空，收尾阶段据此跳过。

2. **收尾改异步**（替换 `conversation_flow.go:87-90`）：响应返回前停止本请求的续期看门狗，并把锁交给异步收尾。
   ```go
   if s.EnableMemory {
       finalHistory := append(state.History, stopCtx.AssistantMessage)
       s.scheduleMemoryWork(conversation, user, finalHistory, lockToken, stopRenew)
   }
   ```
   > 注意：所有 `return`（含中途出错返回）路径都必须保证停止看门狗并释放锁，否则会泄漏。实现时用 `defer` 兜底：默认 `defer` 释放锁；正常走到收尾时把所有权转交，并将 `defer` 置为 no-op（如用一个布尔标记 `handedOff`）。

3. 新增方法 `scheduleMemoryWork`：
   - 若 `lockToken == ""`（入口未拿到锁，已降级）→ **跳过本次收尾**，直接返回。
   - 否则停止本请求看门狗，启动异步 goroutine：
     - 用 `context.WithTimeout(context.Background(), MemoryWorkTimeout)` 独立 context（**不复用请求 ctx**）。
     - 在该 goroutine 内重新启动续期看门狗（覆盖收尾期间），`defer` 停止续期 + `defer` 释放锁 + `recover()`。
     - 依次执行 `extractMemories`、`updateConversationMemory`。

   伪代码：
   ```go
   func (s *Service) scheduleMemoryWork(conv storage.Conversation, user storage.User, history []storage.Message, token string, stopRenew func()) {
       if token == "" { // 入口未持锁(降级) → 跳过收尾
           if stopRenew != nil { stopRenew() }
           return
       }
       if stopRenew != nil { stopRenew() } // 停止请求期看门狗，收尾期重新起一个
       go func() {
           defer func() { if r := recover(); r != nil { logger.Warn(...) } }()
           ctx, cancel := context.WithTimeout(context.Background(), s.Cfg.MemoryWorkTimeout)
           defer cancel()
           stop := s.startLockRenewer(conv.ID, token) // 收尾期续期
           defer stop()
           defer s.Store.ReleaseConversationLock(context.Background(), conv.ID, token)
           s.extractMemories(ctx, user, history)
           s.updateConversationMemory(ctx, conv, user, history)
       }()
   }
   ```

4. 新增续期看门狗 `startLockRenewer(convID, token) (stop func())`：
   - 启动一个 `time.Ticker`（周期 = `ConversationLockTTL/3`），周期调用 `RenewConversationLock`。
   - 返回的 `stop` 关闭 ticker goroutine（幂等，可多次调用）。
   - 若某次续期返回 `false`（锁已不属于自己，例如 TTL 已被抢占），记录告警并停止续期。

#### (D) 配置项（放入 `config.AppConfig`）
在 `go-agent/internal/config/config.go` 的 `AppConfig` 与 `fileConfig` 中新增字段，并在 `web_config.go` 的 `LoadWebConfig` 中赋默认值：

| 配置字段 (AppConfig) | 含义 | 默认值 |
|----------------------|-------------|--------|
| `ConversationLockTTL` (time.Duration) | 锁单次有效期（崩溃保护上限），存活期间由看门狗按 `TTL/3` 续期 | 30s |
| `MemoryWorkTimeout` (time.Duration) | 异步收尾操作整体超时 | 110s |
| `ConversationLockWaitTimeout` (time.Duration) | 入口阻塞获取锁的最大等待时长 | 130s |

说明：
- 引入续期看门狗后，**锁的实际持有时长不再受 TTL 限制**，由对话处理 + 收尾的真实耗时决定；TTL 只是「持锁方失联后多久自动失效」的上限，故取较小值（30s）即可，崩溃后最多 30s 自动解锁。
- `ConversationLockWaitTimeout` 决定下一个请求最多等多久；建议 ≥ 一次收尾的预期耗时（`MemoryWorkTimeout` 量级），否则可能在收尾完成前就等待超时降级放行。
- 文件配置以秒为单位的整数字段（如 `conversation_lock_ttl_seconds`），加载时转换为 `time.Duration`；未配置时用上述默认值。具体字段命名在实现时与现有 `fileConfig` 风格保持一致。

### 3.4 改造后流程图

```
HTTP POST /api/conversations/{id}/stream
  └─ RespondToConversation(reqCtx)
       ├─ [新增] AcquireConversationLock(reqCtx, convID, token, ttl, waitTimeout)  // 阻塞获取:被占用则等待
       │         └─ 拿到锁后 startLockRenewer()  // 看门狗按 TTL/3 续期
       ├─ loadConversationMessages
       ├─ for round { LLM + 工具 }   ← 处理期间持锁并持续续期
       └─ turn 结束:
            ├─ RunStop  (持久化历史 + SSE assistant)
            ├─ scheduleMemoryWork: 停止请求期看门狗, 把锁(token)移交异步收尾
            ├─ return AssistantMessage   ← 用户在此即可拿到回答(不再等待记忆)
            └─ go func(bgCtx):           // 异步收尾, 继续持锁
                 ├─ startLockRenewer()    // 收尾期续期
                 ├─ extractMemories
                 ├─ updateConversationMemory
                 ├─ defer stopRenewer
                 └─ defer ReleaseConversationLock   // 收尾完成后释放
```

> 关键：锁在**入口获取**、**全程持有（含异步收尾）**、**收尾完成后释放**。收尾阶段不再重新加锁，只是接管同一 token 的续期与最终释放。

## 5. 边界与异常处理

1. **请求 ctx 取消导致后台中断**：异步收尾 goroutine 使用 `context.Background()` 派生的独立 ctx，与 HTTP 请求生命周期解耦，客户端断开不影响收尾与锁释放。
2. **持锁进程崩溃**：续期看门狗随进程消失，锁在最多 1 个 `ConversationLockTTL`（默认 30s）后自动过期，不会永久死锁；其他请求在入口等待期间即可重新获取。
3. **入口获取锁失败**（Redis 异常）：记录告警并**降级放行**（`lockToken` 置空），正常处理对话但**跳过收尾**，避免锁异常导致整个会话不可用。
4. **入口等待锁超时**（`ConversationLockWaitTimeout` 内仍未拿到）：同样降级放行并跳过收尾，宁可放行也不阻死用户请求。
5. **锁泄漏防护**：`RespondToConversation` 所有 return 路径（含中途出错）都通过 `defer` 兜底停止看门狗并释放锁；仅在正常走到异步收尾时把所有权转交，避免被兜底 `defer` 误释放。
6. **续期失败**：某次 `RenewConversationLock` 返回 false（锁已不属于自己）时，看门狗记录告警并停止，避免误续他人锁。
7. **goroutine panic**：异步收尾 `defer recover()` 兜底，且 `defer stopRenewer` 与 `defer ReleaseConversationLock` 仍会执行。
8. **超时关系**：`ConversationLockTTL`（默认 30s，小，靠续期维持）与 `MemoryWorkTimeout`（默认 110s）、`ConversationLockWaitTimeout`（默认 130s）相互独立；三者均为可配置项。

## 7. 已确认的关键决策

1. **锁的生命周期**：**入口获取锁**（被占用则阻塞等待）→ 对话处理 + 异步收尾**全程持有同一把锁**（看门狗续期）→ **收尾完成后释放**。收尾阶段不再重复加锁。
2. **再次进入会话**：在入口 `AcquireConversationLock` 处阻塞等待，直到上一轮收尾释放锁或等待超时。
3. **获取锁失败/等待超时**：降级放行，正常处理对话但跳过收尾，仅记录告警。
4. **超时参数**：作为**配置项**放入 `config.AppConfig`（`ConversationLockTTL` / `MemoryWorkTimeout` / `ConversationLockWaitTimeout`）。
5. **锁实现位置**：放在 `storage` 层（`lock.go`，与 cache 并列），复用现有 `Store.Redis`。
```
