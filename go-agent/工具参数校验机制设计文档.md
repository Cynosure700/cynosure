# 工具执行前参数校验机制 — 设计文档

## 1. 背景与目标

当前 `go-agent` 在执行工具（tool）前**不会**根据工具声明的参数 Schema 做统一校验：

- 工具的参数 Schema（`type` / `required` / `enum`）已在 `internal/tools/definitions.go` 中声明，但运行时完全没有利用。
- 实际校验只散落在各 handler 内部，且不完整。例如 `handleBash` 仅判断 `command == ""`（`handlers.go:54`），`handleRead` 对 `limit` 类型不匹配时静默忽略（`handlers.go:77`），缺失必填项时也只能依赖 handler 是否恰好写了判断。
- 当 LLM 传入不符合要求的参数（缺少必填字段、类型错误、enum 非法）时，行为不可控：要么得到含糊错误，要么被静默忽略。

**目标**：在工具执行**前**，依据工具自身声明的 JSON Schema 对参数做统一校验；校验失败时，将**清晰、可读的错误信息重新返回给 LLM**，让其据此修正后重试。要求**不影响现有任何功能**。

## 2. 现状分析（关键调用链）

```
conversation_flow.go:142  遍历 msg.ToolCalls
        │
        ▼
tool_registry.go:205  Service.executeToolCall(name, rawArgs)
        ├─ mcp__*           → s.MCP.CallTool            (外部 MCP，schema 由 MCP server 负责)
        ├─ spawn_subagent   → json.Unmarshal + runSubagent
        └─ 其它内置工具      → ToolRegistry.Execute
                                    │
                                    ▼
                          tool_registry.go:88  Execute
                            json.Unmarshal(rawArgs) → args map[string]any   ← 【校验插入点】
                            isAllowed(name)
                            agenttools.Dispatch(ctx, name, args)
                                    │
                                    ▼
                          handlers.go:33  Dispatch → 具体 handler
```

**错误返回链路（已天然适配，无需改动）**：
任意一层返回 `error` → `executeToolCall` 包装为 `toolExecutionOutcome{Status:"rejected", Result:"Error: ..."}`（`tool_registry.go:231`）→ `appendToolMessageHook` 序列化为 `role:"tool"` 消息追加回 `state.Messages` → 下一轮发给 LLM。

> 因此本次只需在执行前**新增校验并返回 error**，错误回传机制自动复用。

## 3. 设计方案

### 3.1 总体思路

新增一个**轻量级、零第三方依赖**的 JSON Schema 校验器，校验工具声明 Schema 中最常用、最关键的约束：

1. `required`：必填字段是否存在；
2. `type`：字段类型是否匹配（`string` / `integer` / `number` / `boolean` / `array` / `object`）；
3. `enum`：取值是否在枚举集合内。

在 `ToolRegistry.Execute` 中，于 `json.Unmarshal` 之后、`Dispatch` 之前调用校验。校验失败返回 error，由现有链路回传给 LLM。

> 说明：仅覆盖以上三类约束，是为了「最小改动 + 解决核心问题」。`minLength`、`pattern`、嵌套对象深度校验等高级约束不在本次范围内（当前工具 Schema 也未使用），避免过度设计。

### 3.2 新增文件：`internal/tools/validation.go`

提供入口函数：

```go
// ValidateToolArgs 依据工具的 JSON Schema 校验已解析的参数。
// params 为 openai.FunctionDefinition.Parameters（json.RawMessage）。
// 校验通过返回 nil；失败返回聚合后的可读错误。
func ValidateToolArgs(params json.RawMessage, args map[string]any) error
```

核心逻辑：
1. 若 `params` 为空 → 视为无约束，直接放行（保持对无 Schema 工具的兼容）。
2. 解析 Schema 为 `map[string]any`，读取 `required []` 与 `properties map`。
3. 校验 `required`：逐项检查是否存在于 `args`，缺失则累计错误 `missing required parameter: <name>`。
4. 校验每个已传入字段：若 `properties` 中声明了 `type`，做类型匹配（注意 JSON 数字经 `json.Unmarshal` 为 `float64`，`integer` 需额外判断是否为整数值）；声明了 `enum` 则检查取值。
5. 将所有错误聚合为一条信息返回，例如：
   `invalid arguments for tool "read_file": missing required parameter: path; parameter "limit" expects integer, got string`。

类型匹配规则（`type` → Go 实测类型）：

| Schema type | 接受的 Go 类型 |
|---|---|
| `string`  | `string` |
| `number`  | `float64` |
| `integer` | `float64` 且为整数值 |
| `boolean` | `bool` |
| `array`   | `[]any` |
| `object`  | `map[string]any` |

### 3.3 修改点：`internal/web/runtime/tool_registry.go`

在 `Execute`（`:88`）中插入校验。由于此处已有 `name`，可通过现有 `lookupRegisteredTool(name)`（或遍历 `r.definitions`）拿到 `openai.Tool` 及其 `Function.Parameters`：

```go
func (r *ToolRegistry) Execute(...) (ToolExecutionResult, error) {
    var args map[string]any
    if err := json.Unmarshal([]byte(rawArgs), &args); err != nil {
        return ToolExecutionResult{}, fmt.Errorf("invalid tool arguments: %w", err)
    }
    if !r.isAllowed(name) {
        return ToolExecutionResult{}, fmt.Errorf("tool %s is not registered for web runtime", name)
    }
    // 新增：执行前参数校验
    if def, ok := r.lookupDefinition(name); ok && def.Function != nil {
        if err := agenttools.ValidateToolArgs(rawMessageOf(def.Function.Parameters), args); err != nil {
            return ToolExecutionResult{}, err
        }
    }
    ...
}
```

辅助：新增 `lookupDefinition(name)` 从 `r.definitions` 取定义（与 `isAllowed` 同源，确保被校验的 Schema 与暴露给 LLM 的一致）。`Function.Parameters` 类型为 `any`（实际存 `json.RawMessage`），做一次类型断言转换。

### 3.4 spawn_subagent 分支（可选，建议纳入）

`spawn_subagent` 不走 `Execute`，在 `executeToolCall`（`:216`）单独处理，已有 `json.Unmarshal` 到结构体的校验。可在其后补一行 `task` 必填校验（`args.Task == ""` 时返回 rejected），保持与其它工具一致的体验。改动极小、风险低。

### 3.5 MCP 工具（`mcp__*`）— 不在本次范围

MCP 工具 Schema 来自外部 MCP server，参数校验由 MCP server 侧负责，`s.MCP.CallTool` 也会处理。本次**不改动** MCP 分支，避免引入跨系统兼容问题。

## 4. 影响面与兼容性

- 仅新增 1 个文件 + 修改 `tool_registry.go` 1 处（+ 可选 `executeToolCall` 1 处），不触碰 handler、Dispatch、hook、前端。
- 对**合法参数**：校验通过，行为与现状完全一致 → 不影响正常功能。
- 对**非法参数**：原本可能静默失败/含糊报错，现在返回明确错误并回传 LLM → 行为改善，方向与需求一致。
- 无 Schema / 空 Schema 的工具自动放行，向后兼容。
- 子 agent 共用 `ToolRegistry.Execute`，同样获得校验能力，行为一致。

## 5. 测试计划

新增 `internal/tools/validation_test.go`，覆盖：
1. 缺失必填字段 → 报错且包含字段名（如 `read_file` 不传 `path`）。
2. 类型不匹配 → 报错（如 `limit` 传字符串；`integer` 传 `1.5`）。
3. `integer` 传整数值的 `float64`（如 `3`）→ 通过。
4. `enum` 非法值 → 报错（如 `todo_write` 的 `status` 传非法枚举，可针对单字段函数测试）。
5. 合法参数 → 通过。
6. 空 Schema / 空 params → 放行。

并运行 `go test ./...` 确保现有测试（含 `server_test.go`、conversation 相关）全部通过。
