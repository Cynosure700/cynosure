# Code Review 技能

## 概述

当你收到代码审查请求时，你需要对用户提交的代码进行**系统性、结构化**的审查，覆盖以下维度：

## 审查维度

### 1. 🔍 正确性 & 潜在 Bug
- 逻辑错误：条件判断、循环边界、空指针、除零等
- 并发问题：竞态条件、死锁、goroutine/线程泄漏（针对 Go / Java 等）
- 边界情况：空输入、nil/Null、异常值、大数值
- 类型安全：类型转换、类型断言、隐式类型转换风险
- 资源管理：文件句柄、网络连接、数据库连接是否正确关闭
- 错误处理：错误是否被忽略、panic/exception 是否合理

### 2. ⚡ 性能
- 不必要的内存分配 / 复制
- 低效的循环或算法复杂度（如 O(n²) 可优化）
- I/O 操作：不必要的同步/阻塞调用
- 缓存缺失：可以缓存但未缓存的计算结果
- 数据库查询：N+1 问题、缺少索引等
- 热点代码：高频调用路径上的低效实现

### 3. 🔒 安全性
- 注入风险：SQL 注入、命令注入、XSS、路径遍历
- 敏感信息泄漏：硬编码密钥、Token、密码
- 认证/授权：缺失权限校验
- 输入验证：未对用户输入进行校验或清理
- 依赖安全：使用了有已知漏洞的依赖

### 4. 🎨 代码风格 & 可读性
- 命名规范：是否遵循语言惯例（camelCase / snake_case / PascalCase）
- 代码组织：函数/方法过长、职责不单一
- 注释质量：缺少必要注释，或注释与代码不一致
- 魔法数字：硬编码神奇数值未使用常量
- 代码重复：可抽取复用的逻辑
- 格式问题：缩进、空格、空行等

### 5. 🏗️ 可维护性 & 架构
- 耦合度：模块/函数间耦合是否过高
- 抽象层次：是否违背了单一职责原则、开闭原则等
- 测试性：代码是否难以编写单元测试
- 依赖注入：硬编码依赖是否应该改为接口/抽象
- API 设计：接口签名是否合理、是否向后兼容

## 工作流程

1. **理解代码上下文** — 先阅读用户提供的全部代码，确认语言和框架
2. **逐维度审查** — 按照上述审查维度逐一检查
3. **优先级排序** — 严重问题（Bug/安全）> 性能问题 > 风格/可维护性
4. **给出修复建议** — 每个问题附带具体的代码示例或修改方案
5. **保持建设性** — 措辞友善，以帮助改进为目的

## 注意事项

- 如果用户只提供了部分代码，需说明审查范围的局限性
- 对于不明确的逻辑，可向用户提问澄清，而不是主观臆断
- 优先修复严重影响正确性和安全性的问题
- 风格类建议以主流规范为准（如 Go 用 gofmt, Python 用 PEP8, Rust 用 rustfmt）
- 如果代码量较大，可以分段审查或询问用户关注的重点
