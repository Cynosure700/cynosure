# 助手消息元信息展示设计

## 1. 需求

在前端助手消息（assistant）的右侧，展示三项元信息，并尽量做到「实时」：

1. **回复耗时**：本次助手回复从开始到结束所花费的时间（毫秒/秒）。
2. **调用的工具数量**：本次助手回复过程中调用工具的次数（多轮 tool_calls 累加）。
3. **当前上下文大小**：本次请求发送给模型的上下文估算 token 数。

要求：
- 流式过程中即时反馈（至少在回复结束时显示完整三项）。
- 历史会话重新加载后，助手消息仍能显示这三项元信息。
- 前后端同步改造，不影响现有工具执行、审计、压缩、记忆等核心流程。

---

## 2. 现状分析

### 2.1 后端关键流程

- `RespondToConversation`（`internal/web/runtime/conversation_flow.go:27`）是主对话循环：
  - 每一轮 `compressContextBeforeLLM` 得到本轮请求历史，`buildOpenAIMessages` 组装 `state.Messages`。
  - `runModelRoundStream` 流式调用模型，发送 `assistant_delta` / `reasoning_delta` SSE 事件。
  - 若 `finishReason == "tool_calls"`，对每个 `msg.ToolCalls` 执行工具（Pre/Post Hook）。
  - 否则进入 `RunStop`，由 `emitAssistantStopHook` 发送最终 `assistant` 事件。
- `LoopState`（`internal/web/runtime/hooks/types.go:37`）贯穿整轮对话，是累计「工具数量」的天然载体。
- `StopContext`（`types.go:71`）携带最终 assistant 消息，是回传元信息的天然出口。

### 2.2 SSE 事件

- `SSEWriter.Event(name, data)`（`internal/web/runtime/sse.go:13`）。
- 现有事件：`conversation`、`assistant_delta`、`reasoning_delta`、`assistant`、`error`、`done`。
- 最终 `assistant` 事件（`internal/web/runtime/hooks/stop.go:20`）payload：
  ```json
  {"message_id":"...","content":"...","reasoning_content":"...","final":true}
  ```

### 2.3 Token 估算

- `compression.DefaultTokenEstimator`（`internal/web/runtime/compression/token_estimator.go`）已提供：
  - `EstimateRequestTokens(systemPrompt, history, tools) int`
  - `ContextTokenBudget() int`
- 估算方式：`ceil(utf8Bytes/3)`，已在压缩流程中使用，可直接复用。

### 2.4 持久化

- 助手消息以 `storage.Message`（`internal/web/storage/models.go:49`）形式存入会话历史 JSON（`SetConversationHistory`）。
- `Message` 结构当前**没有**耗时 / 工具数 / token 字段。
- `GET /api/conversations/{id}` 经 `displayConversationMessages`（`internal/web/app/conversation_handlers.go:121`）返回 user 与 assistant（无 tool_calls）消息。

### 2.5 前端

- `web/src/api.ts`：`ChatMessage` 类型、`streamConversation` 的 `onAssistant` 回调、`getConversation` 取历史。
- `web/src/App.tsx`：消息渲染在 `messages.map(...)`（约 `App.tsx:706`），助手消息含 `message-role`、`message-reasoning`、`message-content`。
- 流式时用临时 `streaming-${ts}` 消息，`onAssistant` 时迁移为正式 `message_id`。

## 3. 设计方案

### 3.1 数据模型：新增元信息字段

在 `storage.Message` 增加一个可选的元信息结构（向后兼容，历史 JSON 缺省即为零值）：

```go
// models.go
type Message struct {
    // ... 现有字段不变
    Meta *MessageMeta `json:"meta,omitempty"`
}

type MessageMeta struct {
    ElapsedMs     int64 `json:"elapsed_ms,omitempty"`      // 回复耗时（毫秒）
    ToolCallCount int   `json:"tool_call_count,omitempty"` // 调用工具次数
    ContextTokens int   `json:"context_tokens,omitempty"`  // 当前上下文估算 token
    ContextBudget int   `json:"context_budget,omitempty"`  // 上下文预算（用于算占比）
}
```

仅对 assistant 最终消息填充 `Meta`。

### 3.2 后端：累计与计算

#### (a) LoopState 增加累计字段

`internal/web/runtime/hooks/types.go` 的 `LoopState` 增加：

```go
type LoopState struct {
    // ... 现有字段
    StartedAt        time.Time // 本次回复开始时间
    ToolCallCount    int       // 累计工具调用次数
    LastContextTokens int      // 最近一轮发送给模型的上下文 token
}
```

#### (b) 在主循环中赋值

`conversation_flow.go` 的 `RespondToConversation`：

1. 进入函数即记录 `state.StartedAt = time.Now()`（在 `newLoopState` 内统一设置）。
2. 每轮组装 `state.Messages` 后，计算并记录上下文 token：
   ```go
   est := compression.DefaultTokenEstimator{}
   state.LastContextTokens = est.EstimateRequestTokens(state.SystemPrompt, requestHistory, s.Tools.Definitions())
   ```
   （取「最后一轮」即最终请求的上下文大小，符合「当前上下文大小」语义。）
3. 工具执行循环里，每执行一个工具 `state.ToolCallCount++`（按实际执行计数；`spawn_subagent` 是否计入见 §3.5）。

> 说明：为避免 runtime 直接依赖 compression 的循环引用风险，估算调用放在 `conversation_flow.go`（runtime 包已 import compression）。

#### (c) Stop 时回填 Meta 并下发

`internal/web/runtime/hooks/stop.go`：

- `persistAssistantStopHook` 在构造 `AssistantMessage` 时附加 `Meta`：
  ```go
  meta := &storage.MessageMeta{
      ElapsedMs:     time.Since(state.StartedAt).Milliseconds(),
      ToolCallCount: state.ToolCallCount,
      ContextTokens: state.LastContextTokens,
  }
  h.AssistantMessage = storage.Message{..., Meta: meta}
  ```
- `emitAssistantStopHook` 在 `assistant` 事件 payload 增加三字段：
  ```json
  {
    "message_id":"...","content":"...","reasoning_content":"...","final":true,
    "elapsed_ms": 1234, "tool_call_count": 2, "context_tokens": 5120
  }
  ```

#### (d) 历史接口透传

`displayConversationMessages` 返回的 `storage.Message` 已自动带 `Meta`（JSON 序列化），前端可直接读取。无需改 handler 逻辑。

### 3.3 实时刷新（已确认采用）

新增轻量 `meta` SSE 事件，在回复过程中即时推送当前累计值：

- **每轮请求前**：组装好 `state.Messages` 并算出 `LastContextTokens` 后，下发一次 `meta`，刷新上下文大小与耗时。
- **每个工具执行后**（PostToolUse Hook）：`ToolCallCount++` 后下发一次 `meta`，刷新工具数与耗时。
- 事件格式：
  ```
  event: meta
  data: {"elapsed_ms": 800, "tool_call_count": 1, "context_tokens": 4096, "context_budget": 116736}
  ```
- 最终 `assistant` 事件再给出定稿值（含相同四字段），作为最终归位。

前端收到 `meta` 即更新当前 streaming 助手消息的右侧数值，做到实时反馈。

### 3.4 前端改造

#### (a) `api.ts`

- `ChatMessage` 增加可选字段：
  ```ts
  export type ChatMessage = {
      // ...
      elapsed_ms?: number;
      tool_call_count?: number;
      context_tokens?: number;
  };
  ```
- 历史接口 `getConversation`：后端 `Meta` 是嵌套对象，需在前端拍平或直接读取 `message.meta`。**方案**：后端历史也按拍平字段返回（在 handler 里把 `Meta` 展开为同级字段），保持前后端一致；或前端读取 `meta.*`。建议**前端读取嵌套 `meta`，流式事件读取拍平字段**，并在赋值时统一归一化为 `ChatMessage` 的三个可选字段。
- `streamConversation` 的 `onAssistant` 回调参数增加 `elapsed_ms?`、`tool_call_count?`、`context_tokens?`；新增可选 `onMeta` 回调（若采用 §3.3 实时推送）。

#### (b) `App.tsx`

- 流式起始：临时助手消息初始化三字段为 `undefined`（或 0）。
- `onMeta`（可选）：更新当前 streaming 消息的三字段。
- `onAssistant`：迁移消息时写入定稿三字段。
- 历史加载：`getConversation` 返回的 `meta` 归一化到消息字段。
- 渲染：在助手消息内新增一个元信息条（右对齐），仅 assistant 且有数据时显示：
  ```tsx
  {message.role === "assistant" && hasMeta && (
      <div className="message-meta">
          <span>⏱ {formatElapsed(message.elapsed_ms)}</span>
          <span>🛠 {message.tool_call_count ?? 0} 次调用</span>
          <span>🧮 {formatTokens(message.context_tokens)} tokens</span>
      </div>
  )}
  ```
  （按项目规范默认不使用 emoji，实际用纯文本标签：`耗时`、`工具`、`上下文`。）

#### (c) `styles.css`

- 新增 `.message-meta`：小字号、次要色、右对齐、flex 间距；放在 `message-content` 下方或 `message` 右上角。
- 截图要求「右边」，可用 `.message.assistant` 内 `.message-meta` 绝对定位右上或顶部右对齐 flex。

### 3.5 计数口径

- **工具数量**：统计**实际执行**的工具调用次数（每轮 `msg.ToolCalls` 累加）。
- `spawn_subagent`：默认**计入**主 Agent 的工具调用次数（用户视角它确实调用了一次工具）。子 Agent 内部的工具调用不计入主消息。
- `todo_write` 等内部工具：默认计入（保持口径一致、简单）。

### 3.6 上下文大小口径

- 取**最终发送给模型那一轮**的 `EstimateRequestTokens`（systemPrompt + 压缩后 requestHistory + tools）。
- 同时回传 `ContextBudget`（`DefaultTokenEstimator.ContextTokenBudget()`）。
- 前端展示：`token + 预算百分比`，如 `上下文 5120 / 116K (4%)`。

## 6. 已确认决策

1. **实时刷新粒度**：采用**中途实时刷新**（新增 `meta` SSE 事件，每轮请求前 + 每个工具执行后推送），最终 `assistant` 事件定稿。
2. **耗时口径**：从「用户发送」到「回复结束」的**端到端总耗时**（含工具执行与多轮模型调用）。
3. **工具计数**：**全部计入**，包括 `spawn_subagent`、`todo_write` 等内部工具（按主 Agent 实际执行次数累加，子 Agent 内部调用不计入）。
4. **上下文展示**：**token 绝对值 + 预算百分比**（如 `上下文 5120 / 116K (4%)`）。
5. **展示位置**：助手消息卡片**顶部右对齐的一行小字**。

## 8. 缺陷修复：历史会话工具数不显示

### 8.1 现象

助手消息在**流式回复时**能显示「工具 N 次」，但**历史会话重新加载**（刷新页面 / 切换会话再切回）后不再显示工具数。

### 8.2 根因

`storage.MessageMeta.ToolCallCount` 字段带了 `omitempty` 标签（`models.go`）：

```go
ToolCallCount int `json:"tool_call_count,omitempty"`
```

- 当某轮助手回复**工具调用数为 0** 时，`ToolCallCount = 0`，`omitempty` 使该字段在 JSON 序列化时被**省略**。
- 但同一 `meta` 对象里的 `context_tokens` 恒为正值，所以 `meta` 对象本身存在、非空。
- 历史加载链路：DB `history_json` → `DecodeConversationHistory` → `displayConversationMessages` → GET 返回的 `meta` 中**缺少** `tool_call_count` 键。
- 前端归一化（`api.ts` getConversation）：`meta` 为 truthy 走展平分支，但 `meta.tool_call_count` 为 `undefined` → `message.tool_call_count = undefined`。
- 前端渲染（`App.tsx` renderMessageMeta）：`typeof message.tool_call_count === "number"` 为 `false` → 不显示。

而**流式路径**用显式 `map[string]any{"tool_call_count": meta.ToolCallCount}`（`stop.go` / `emitMeta`），map 序列化不会因值为 0 丢 key，故前端拿到 `0`，`typeof 0 === "number"` 为真，正常显示「工具 0 次」。

**结论**：该缺陷精确发生在「该助手回复工具调用数为 0」的会话上——流式时显示「工具 0 次」，刷新后消失。

### 8.3 修复方案（治本）

去掉 `MessageMeta.ToolCallCount` 的 `omitempty`，让 0 也被序列化，使历史与流式两条路径数据形状一致：

```go
// go-agent/internal/web/storage/models.go
type MessageMeta struct {
    ToolCallCount int `json:"tool_call_count"`           // 去掉 omitempty
    ContextTokens int `json:"context_tokens,omitempty"`  // 保持不变（恒为正）
    ContextBudget int `json:"context_budget,omitempty"`  // 保持不变（恒为正）
}
```

- 只改 `tool_call_count` 一个字段；`context_tokens`/`context_budget` 实践中恒为正，无需改动。
- 前端无需改动：历史归一化拿到的 `tool_call_count` 将为数字（含 0），`renderMessageMeta` 正常显示。
- 兼容性：旧历史数据（缺 `tool_call_count` 键）刷新后该条仍不显示工具数，但新产生的会话恢复正常；不影响其它字段与功能。

### 8.4 验证

- 后端：新增/调整单测，断言「工具数为 0」的 assistant 消息序列化后 `meta` 含 `tool_call_count: 0`，经 `displayConversationMessages` 往返后仍带该键。
- 运行 `go test ./...`（config 包预存的环境变量失败除外）。
- 手动：发起一次纯文本回复（0 工具调用），刷新后助手消息仍显示「工具 0 次」。
