# 会话记忆层（Conversation Memory）设计

## 背景

`go-agent` 当前有两套与“信息浓缩”相关、但定位不同的机制：

1. **三层长期记忆**（`internal/web/runtime/memory.go` + `memories` 表）：跨会话、按用户/系统级沉淀的长期记忆（用户喜好 / 过往经历 / 通用知识），在每轮对话开始前经 LLM 相关性筛选后注入 system prompt。
2. **上下文压缩流水线**（`internal/web/runtime/compression/`）：在每次调用 LLM 前，对“请求态历史副本”做四层压缩，最后一层 `FullHistorySummarizationStrategy` 在 token 超预算时调用 LLM 做**一次性全量摘要**，把历史替换成「摘要 + 近期 tail + 最后一条消息」，结果只缓存在 `context_summaries`，不沉淀为可复用的会话主体信息。

现状的缺口：全量摘要是**临时的、被动的、一次性的**——只有 token 撑爆才生成，且每次源历史 hash 变化就要重新调用一次 LLM 摘要，既慢又贵；它产出的是“为塞进窗口而压扁的快照”，不是对**当前这场会话主干信息**的持续维护。

本设计新增**会话记忆层（Conversation Memory）**：一份**按会话粒度、随对话增量维护**的、结构化的“当前会话主要信息”。它：

- **不同于全量摘要**：它是主动、持续维护的，不是 token 超限才临时生成；
- **不同于聊天记录**：它是浓缩后的“主干信息条目”，不是逐字消息；
- **不同于三层长期记忆**：它是**当前会话级**（`conversation_id` 维度）的，而非跨会话沉淀。

**核心目标**：当压缩流水线本应触发**全量摘要**时，若当前会话记忆**满足质量阈值**（`>= 10k token` 且 `>= 5 条记忆条目` 且 `<= 40k token`），则**直接采用已就绪的会话记忆替代全量摘要**，跳过这一次昂贵的 LLM 摘要调用。

## 与现有机制的边界

```text
聊天记录 (state.History / conversations.history_json)
    = 逐字真实消息，前端展示与请求构造的源头

三层长期记忆 (memories 表)
    = 跨会话 / 跨用户的长期沉淀，注入 system prompt

全量摘要 (context_summaries 表)
    = token 超限时一次性 LLM 摘要，临时快照，请求态专用

【新增】会话记忆 (conversation_memories 表)
    = 当前会话主干信息，随每轮对话增量维护的多条结构化条目，
      在全量摘要本应触发时作为“已就绪替代品”优先使用
```

会话记忆**只服务于请求态上下文压缩**，与三层长期记忆完全独立，互不读写。

### 与三层记忆的两点本质差异（务必遵守）

1. **不注入 system prompt**：三层长期记忆会经 `selectRelevantMemories` → `buildSystemPrompt` 在**每轮对话开始前**注入到 system prompt（`<memory>` 区块）。**会话记忆完全不走这条路径**——它既不参与 `selectRelevantMemories`，也不出现在 `MemorySection` / system prompt 中。会话记忆**仅在压缩流水线触发全量摘要的那一刻**被读取并拼进**请求态历史副本**，起一次性的“替代全量摘要”优化作用，正常对话轮次中模型完全看不到它。
2. **不做整理与淘汰**：三层记忆有独立的阈值整理/淘汰机制（`maybeConsolidateUserPreferences` / `maybePruneSessionSummaries` / `maybeConsolidateSemantic` / `DeleteOldestMemories` 等）。**会话记忆没有任何此类机制**——它的“精炼”只是每轮维护时 LLM 重写完整列表的自然产物（见下文“生成与更新”），不存在独立的 consolidate / prune / 按条数上限淘汰逻辑。会话记忆的天然边界就是单个会话；会话被删除时随 `conversation_id` 外键级联清理即可。

## 数据模型

会话记忆是**一组结构化条目**（多条），而非单份 Markdown。每条对应会话中的一个“主干信息单元”（如：当前目标、关键决策、已完成产物、重要约束、待办项等），形态对齐现有 `storage.Memory`，便于按条计数与增量合并。注意：该形态相似仅为复用解析/截断逻辑，**会话记忆不复用三层记忆的注入、整理、淘汰路径**。

### 结构体 `storage.ConversationMemory`（新增于 `models.go`）

```go
type ConversationMemory struct {
    ID             string    `json:"id"`              // "cm_..."
    ConversationID string    `json:"conversation_id"`
    UserID         string    `json:"user_id"`
    Name           string    `json:"name"`           // 短标题，<=80 runes
    Description    string    `json:"description"`    // 一句话要点，<=300 runes
    Body           string    `json:"body"`           // 支撑细节，<=2000 runes
    CreatedAt      time.Time `json:"created_at"`
    UpdatedAt      time.Time `json:"updated_at"`
}
```

> 说明：不引入 `category` 枚举，保持与 `Memory` 一致的 `name/description/body` 三字段；条目的“类别”信息由 LLM 写进 `name`（如 `[目标] ...`、`[决策] ...`）即可，避免过度设计。

### 表 `conversation_memories`（migration）

```sql
CREATE TABLE IF NOT EXISTS conversation_memories (
    id VARCHAR(64) PRIMARY KEY,
    conversation_id VARCHAR(64) NOT NULL,
    user_id VARCHAR(64) NOT NULL,
    name VARCHAR(255) NOT NULL,

```

### Repository（新增 `conversation_memories_repo.go`）

```go
ListConversationMemories(ctx, conversationID string) ([]ConversationMemory, error)   // 按 updated_at ASC
ReplaceConversationMemories(ctx, conversationID, userID string, items []ConversationMemory) error // 事务内整表替换该会话条目
```

采用**整会话整体替换**（delete by conversation_id + 批量 insert）而非逐条 diff，匹配“增量维护 = LLM 输出完整新版列表”的更新方式，逻辑最简、无并发写冲突（单会话串行处理）。

## 生成与更新（每轮对话后增量维护）

**时机**：与三层记忆 `extractMemories` 完全相同的位置——主循环结束、Stop hook 之后，见 `conversation_flow.go:87`。新增 best-effort 调用：

```go
if s.EnableMemory {
    s.extractMemories(ctx, user, append(state.History, stopCtx.AssistantMessage))
    s.updateConversationMemory(ctx, conversation, user, append(state.History, stopCtx.AssistantMessage)) // 新增
}
```

**`updateConversationMemory` 流程**（新增 `conversation_memory.go`，置于 `runtime` 包）：

1. 加载该会话已有会话记忆 `ListConversationMemories(conversationID)`。
2. 渲染本轮对话文本（复用 `renderDialogueForMemory`，仅取 user/assistant 文本，截断）。
3. 一次非流式、无工具的 LLM 调用：system prompt 要求基于「已有会话记忆 + 最新对话」**输出完整的新版会话记忆条目列表**（合并新信息、更新已变更项、剔除过时项、保持条目精炼），输出 JSON 数组 `[{"name","description","body"}]`。这里的“合并/剔除”是单次重写完整列表时的自然产物，**不是**三层记忆那种独立的 consolidate/prune/按条数上限淘汰逻辑——会话记忆没有任何独立整理或淘汰流程。
4. 解析、校验、按 runes 截断（复用 `parseExtractedMemories` 的解析与截断思路，去掉 `type` 校验）。
5. `ReplaceConversationMemories` 整体替换落库。
6. 全程 best-effort：任意失败仅 `logger.Warn`，绝不影响用户响应。

> 设计取舍：**增量维护**确保在 token 撑爆、压缩流水线触发全量摘要的那一刻，会话记忆**已经就绪且最新**，无需临时生成——这正是“替代全量摘要”得以成立的前提。

新增 system prompt（`conversation_memory.go` 常量）：

```text
你是“当前会话记忆”维护引擎。给你“已有会话记忆条目”和“最新一轮对话”，
请输出更新后的【完整】会话记忆条目列表，使其准确反映本场会话至今的主干信息：
- 覆盖：当前用户目标、关键决策与结论、已完成/已产出的内容、重要约束与上下文、待办与下一步。
- 合并重复、用新信息更新旧条目、删除已过时或被推翻的内容；只重组已知信息，不编造。
- name：短标题(<=80字，可用 [目标]/[决策]/[产出]/[待办] 等前缀)。description：一句话要点(<=300字)。body：支撑细节(<=2000字)。
- 仅输出 JSON 数组：[{"name","description","body"}]。无可记录时输出 []。
```

## 在全量摘要触发点的接入

新增压缩策略 **`ConversationMemoryStrategy`**，注册在 `FullHistorySummarizationStrategy` **之前**：

```go
func NewDefaultCompressor() *Compressor {
    return &Compressor{strategies: []Strategy{
        &ToolResultCompressionStrategy{},
        &MessageWindowCompressionStrategy{},
        &RecentToolResultRetentionStrategy{},
        &ConversationMemoryStrategy{},        // 新增：满足阈值则用会话记忆替代
        &FullHistorySummarizationStrategy{},  // 兜底：会话记忆不达标时仍走全量摘要
    }}
}
```

**`ConversationMemoryStrategy.Apply` 逻辑**：

```text
1. 若 Estimator 缺失 → no-op。
2. before = EstimateRequestTokens(system, RequestHistory, tools)
   若 before <= budget → no-op（未到摘要触发线，不动）。
3. 若 len(RequestHistory) < 2 → no-op（无可压缩历史）。
4. 加载当前会话记忆条目 items（经 Store 接口）。
5. memTokens = 估算“会话记忆注入文本”的 token；count = len(items)。
6. 判定是否采用会话记忆：
     count >= 5  AND  memTokens >= 10*1024  AND  memTokens <= 40*1024
   不满足 → no-op（交给后面的 FullHistorySummarizationStrategy 兜底）。
7. 满足 → 用会话记忆重建 RequestHistory，使后续全量摘要因 before<=budget 自然 no-op：
     lastMessage  = RequestHistory[len-1]            // 始终原样保留
     summarizable = RequestHistory[:len-1]
     tail         = selectRecentTail(...)            // 复用现有 tail 选取
     kept         = repairToolCallBoundaries(tail + lastMessage)
     RequestHistory = buildConversationMemoryHistory(items, kept)
```

**阈值常量**（`compression` 包内）：

```go
const (
    conversationMemoryMinTokens = 10 * 1024
    conversationMemoryMaxTokens = 40 * 1024
    conversationMemoryMinCount  = 5
)
```

**请求态上下文构造**（与 `buildSummaryHistory` 同构，文案区分来源）：

```text
[
  system: "以下是本会话的记忆，由系统随对话持续维护，仅用于本次模型推理，不是用户发送的真实消息。",
  user:   "<conversation-memory>\n{渲染后的条目列表}\n</conversation-memory>",
  ...recentTailMessages,
  lastMessage,   // 始终原样保留
]
```

条目渲染：每条一行 `- {name}：{description}`，`body` 视实现可附在条目下（受 40k 上限保护，token 充足时建议带上 body 以保留细节）。

> 关键：会话记忆**不消耗额外 LLM 调用**（已在每轮对话后离线维护好），命中时压缩这一步是纯本地拼装，比全量摘要快得多。

## token 与条数判定细节

- **token 估算**：复用 `DefaultTokenEstimator` 的 `ceil(utf8Bytes/3)` 口径。`memTokens` 估算的是**最终注入文本**（即 `<conversation-memory>` 区块的字节数），保证与“是否真的省了上下文”一致。
- **`>= 5 条`**：指**会话记忆条目数** `len(items)`（已在“数据形态=多条结构化条目”确认）。
- **区间含义**：
  - `< 10k token`：信息太少，会话记忆不足以替代摘要 → 不采用，走全量摘要（或本就够小不触发）。
  - `> 40k token`：会话记忆本身过大，注入后无助于把上下文压回预算 → 不采用，走全量摘要。
  - `[10k, 40k] 且 >= 5 条`：质量与体量都合适 → 采用会话记忆。

## 一致性与分离原则（沿用现有约定）

1. 会话记忆的生成/更新只写 `conversation_memories` 表，**绝不修改** `state.History` / `history_json`，前端聊天记录不出现任何记忆条目。
2. `ConversationMemoryStrategy` 只改 `RequestHistory` 副本，与其他压缩层一致。
3. 维护与命中均为 best-effort：失败/缺失时静默回退到 `FullHistorySummarizationStrategy`，行为与新增前完全一致。
4. 单会话对话串行处理，整表替换无并发写冲突。
5. `lastMessage` 始终原样保留、不参与压缩、不因预算被裁；tail + lastMessage 一起做 tool 边界修复。

## 日志与观测

- 维护阶段：`conversation_id`、`memory_count`、`updated`（是否落库），不记条目正文。
- 命中阶段：`conversation_id`、`strategy=conversation_memory`、`memory_count`、`memory_tokens`、`estimated_tokens_before/after`、`adopted=true/false`、未采用时的 `reason`（count_lt_5 / tokens_lt_10k / tokens_gt_40k / under_budget）。

## 测试要点

- 维护：空对话 no-op；首轮生成多条；次轮合并更新；解析失败/LLM 失败不落库且不影响主流程；超长字段按 runes 截断。
- 命中判定：`before<=budget` no-op；`count<5` 不采用；`memTokens<10k` 不采用；`memTokens>40k` 不采用；`[10k,40k] 且 >=5 条` 采用并使后续全量摘要 no-op。
- 替换正确性：`lastMessage` 始终保留；tail 按预算选取；tool 边界修复正确；`RequestHistory` 重建为 `system + <conversation-memory> + tail + last`。
- 分离：维护与命中均不改 `state.History`；`SetConversationHistory` 仍为真实历史；会话记忆不达标时退回 `FullHistorySummarizationStrategy` 行为不变。
