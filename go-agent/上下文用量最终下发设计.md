# 上下文用量（LastContextTokens）最终下发设计

## 1. 需求

`LastContextTokens` 当前的计算与下发时机不正确：它表示的是「每轮请求**前**的上下文估算」，并不能反映会话结束（模型回答完毕）时的最终上下文用量。

目标：**在会话结束后（即模型本轮回答完毕、不再发起新一轮 tool_calls 时），把当前会话最终的 token 用量计算出来，存储到 assistant 消息的 `Meta` 中，并通过 SSE 下发给前端。**

约束：不影响现有功能（工具执行、压缩、记忆、实时 meta 等）。

---

## 2. 现状分析

### 2.1 计算位置

`internal/web/runtime/conversation_flow.go:81` 起的主循环 `for { ... }`：

```go
for {
    round++
    requestHistory, err := s.compressContextBeforeLLM(ctx, state) // 本轮压缩后的请求历史
    lastRequestHistory = requestHistory
    state.Messages = buildOpenAIMessages(state.SystemPrompt, requestHistory)
    ...
    estimator := compression.DefaultTokenEstimator{}
    state.LastContextTokens = estimator.EstimateRequestTokens(state.SystemPrompt, requestHistory, s.Tools.Definitions())
    state.LastContextBudget = estimator.ContextTokenBudget()
    emitMeta(state)                              // 请求前实时下发
    msg, finishReason, err := s.runModelRoundStream(ctx, state, req)  // 模型本轮回复
    ...
    if finishReason != "tool_calls" || len(msg.ToolCalls) == 0 {
        // —— 会话结束分支 ——
        stopCtx := &StopContext{State: state, ModelMessage: msg, ...}
        s.hookManager().RunStop(ctx, stopCtx)   // 写入 Meta + 下发 assistant 事件
        ...
        return stopCtx.AssistantMessage, nil
    }
    // 否则：追加 assistant + 执行工具，进入下一轮
}
```

### 2.2 问题根因

1. **时机错误**：`LastContextTokens` 在 `runModelRoundStream` **之前**计算，只包含「发送给模型的输入」（systemPrompt + requestHistory + tools），**不包含模型本轮生成的回复内容**。
2. **会话结束时未重算**：进入会话结束分支（`finishReason != "tool_calls"`）后，`state.LastContextTokens` 仍是「最后一轮请求前」的旧值。`stopMessageMeta`（`hooks/stop.go:33`）直接读取该旧值写入 `Meta` 并下发，导致最终用量偏小、不准确。
3. **口径不符**：用户期望的「会话最终 token 用量」应为 total（输入 + 本轮模型输出），因为模型回复也会进入下一轮上下文。当前值缺失了输出部分。

### 2.3 相关结构

- `LoopState.LastContextTokens` / `LastContextBudget`（`hooks/types.go:65-66`）：贯穿整轮对话的累计载体。
- `stopMessageMeta(state)`（`hooks/stop.go:33`）：构造 `storage.MessageMeta`，被 `persistAssistantStopHook`（存储）与 `emitAssistantStopHook`（下发）共用。
- `storage.MessageMeta.ContextTokens`（`storage/models.go:65`）：持久化到会话历史 JSON，历史接口透传给前端。
- 估算器 `compression.DefaultTokenEstimator.EstimateRequestTokens(systemPrompt, history, tools)`：按 `ceil(utf8Bytes/3)` 估算，已在压缩流程复用。

### 2.4 已确认口径

| 项 | 决策 |
|---|---|
| Token 来源 | 沿用 `DefaultTokenEstimator` 估算（不引入 `include_usage`），仅修正**计算时机** |
| Token 口径 | **total**：最终请求上下文 + 本轮模型回复（含 content/reasoning/tool_calls） |
| 实时下发 | **保留**：过程中每轮请求前 + 每个工具后仍按现状用估算实时刷新；会话结束后用「最终用量」定稿覆盖 |

## 3. 设计方案

### 3.1 核心改动：会话结束后重算最终用量

在主循环的**会话结束分支**（`conversation_flow.go:115` 的 `if finishReason != "tool_calls" || len(msg.ToolCalls) == 0`）内，于调用 `RunStop` **之前**，把本轮模型回复纳入上下文后重新估算，覆盖 `state.LastContextTokens`：

```go
if finishReason != "tool_calls" || len(msg.ToolCalls) == 0 {
    // 将本轮模型最终回复纳入上下文，得到「会话结束时」的最终 token 用量
    finalContextHistory := append(cloneMessages(lastRequestHistory), requestMsg)
    estimator := compression.DefaultTokenEstimator{}
    state.LastContextTokens = estimator.EstimateRequestTokens(state.SystemPrompt, finalContextHistory, s.Tools.Definitions())
    state.LastContextBudget = estimator.ContextTokenBudget()

    stopCtx := &StopContext{State: state, ModelMessage: msg, ...}
    if err := s.hookManager().RunStop(ctx, stopCtx); err != nil { ... }
    ...
}
```

要点：
- `lastRequestHistory` 是「最后一轮发送给模型的压缩后请求历史」（`storage.Message`），已在循环中维护。
- `requestMsg`（即本轮 `msg`，类型 `storage.Message`）= 模型最终回复。需要把它转为 `storage.Message` 形态后再参与估算——循环中已有 `assistantMessage`/`stopCtx.AssistantMessage` 的构造逻辑可复用其等价形态。
- 用 `cloneMessages` 避免污染 `lastRequestHistory`（该切片随后还用于 `scheduleMemoryWork`）。

> 说明：`requestMsg` 在源码中是 `openai.ChatCompletionMessage`。为参与 `EstimateRequestTokens([]storage.Message)`，应使用 `stopCtx.AssistantMessage`（已由 `persistAssistantStopHook` 在 `RunStop` 中构造为 `storage.Message`）。因此更稳妥的顺序是：

**方案 A（推荐）**：在 `RunStop` 内部（即 `stopMessageMeta` 计算前）完成最终估算。

### 3.2 方案 A 落地：在 stop hook 内重算

让 stop hook 自己负责「最终用量」计算，主循环只需把估算所需的依赖透传给 `LoopState`，从而保持职责单一、不改变主循环结构。

#### (a) `LoopState` 增加估算依赖

`hooks/types.go` 的 `LoopState` 增加一个可选的最终用量估算回调（避免 hooks 包反向依赖 compression / tools，沿用现有依赖注入风格）：

```go
type LoopState struct {
    // ... 现有字段
    // FinalContextTokens 计算「会话结束时」最终上下文 token 用量：
    // 输入 = systemPrompt + 最后一轮请求历史 + 本轮模型最终回复 + tools。
    // 由 runtime 在 newLoopState 注入，hooks 包不直接依赖 compression。
    EstimateFinalContextTokens func(finalAssistant storage.Message) (tokens int, budget int)
}
```

#### (b) runtime 注入实现

在 `conversation_flow.go` 会话结束分支，先把「最后一轮请求历史」挂到 state（或闭包捕获），再设置回调：

```go
// newLoopState 之后、循环之前无法拿到 lastRequestHistory；
// 因此在会话结束分支赋值闭包：
state.EstimateFinalContextTokens = func(finalAssistant storage.Message) (int, int) {
    est := compression.DefaultTokenEstimator{}
    history := append(cloneMessages(lastRequestHistory), finalAssistant)
    return est.EstimateRequestTokens(state.SystemPrompt, history, s.Tools.Definitions()),
        est.ContextTokenBudget()
}
```

#### (c) `stopMessageMeta` 使用最终用量

`hooks/stop.go`：`persistAssistantStopHook` 已先构造出 `h.AssistantMessage`（含完整 content/reasoning），随后计算 meta。让 `stopMessageMeta` 优先使用最终估算：

```go
func persistAssistantStopHook(ctx context.Context, h *StopContext) error {
    state := h.State
    h.AssistantMessage = storage.Message{..., Content: h.Content, ReasoningContent: h.ReasoningContent}
    // 先用最终回复重算上下文用量，再写入 Meta
    if state.EstimateFinalContextTokens != nil {
        tokens, budget := state.EstimateFinalContextTokens(h.AssistantMessage)
        state.LastContextTokens = tokens
        state.LastContextBudget = budget
    }
    h.AssistantMessage.Meta = stopMessageMeta(state)
    updatedHistory := append(state.History, h.AssistantMessage)
    return state.Store.SetConversationHistory(ctx, state.Conversation.ID, updatedHistory)
}
```

`emitAssistantStopHook` 仍调用 `stopMessageMeta(h.State)`，此时 `state.LastContextTokens` 已被 `persistAssistantStopHook` 覆盖为最终值——**前提是 stop hook 注册顺序为「先 persist 后 emit」**。需确认 `NewDefaultHookManager` 的注册顺序（见 §5 验证项）。

> 若注册顺序不可靠，则改为：在 §3.1 主循环分支内、`RunStop` 之前直接覆盖 `state.LastContextTokens`/`LastContextBudget`，hook 内不再重算。这样 persist 与 emit 都读到同一最终值，顺序无关。**这是更稳妥的最终选择（见 §3.3）。**

### 3.3 最终选择：在主循环 RunStop 之前重算（最简、顺序无关）

综合「不改变 hook 职责、不依赖注册顺序、改动最小」，采用：

- **仅改 `conversation_flow.go`**：在会话结束分支、构造 `stopCtx` 之前，用「最后一轮请求历史 + 本轮模型回复」重算并覆盖 `state.LastContextTokens` / `state.LastContextBudget`。
- `hooks/stop.go` **无需改动**：`stopMessageMeta` 读取的 `state.LastContextTokens` 已是最终值，存储与下发自动一致。

伪代码：

```go
if finishReason != "tool_calls" || len(msg.ToolCalls) == 0 {
    // 本轮模型最终回复（storage.Message 形态）
    finalAssistant := storage.Message{
        Role: "assistant", Content: msg.Content,
        ReasoningContent: msg.ReasoningContent,
        ToolCalls: openAIToolCallsToStorage(msg.ToolCalls),
    }
    finalHistoryForEstimate := append(cloneMessages(lastRequestHistory), finalAssistant)
    est := compression.DefaultTokenEstimator{}
    state.LastContextTokens = est.EstimateRequestTokens(state.SystemPrompt, finalHistoryForEstimate, s.Tools.Definitions())
    state.LastContextBudget = est.ContextTokenBudget()

    stopCtx := &StopContext{State: state, ModelMessage: msg, Content: fallbackAssistantContent(msg.Content), ReasoningContent: cumulativeReasoning.String()}
    if err := s.hookManager().RunStop(ctx, stopCtx); err != nil {
        return storage.Message{}, err
    }
    if s.EnableMemory { ... }   // 不变
    return stopCtx.AssistantMessage, nil
}
```

只新增「重算 3 行 + finalAssistant 构造」，其余逻辑保持原样。

### 3.4 实时 meta 保持不变

- 主循环 `conversation_flow.go:90-93` 每轮请求前的估算 + `emitMeta` **保留**（用于过程中实时刷新「当前上下文」）。
- 每个工具执行后的 `emitMeta`（`conversation_flow.go:144`）保留。
- 仅在会话结束时，用「最终用量」覆盖，并通过最终 `assistant` 事件定稿。前端 `onAssistant` 已写入 `context_tokens`/`context_budget`（`App.tsx:473/477`），无需前端改动。

### 3.5 子 Agent

`runSubagentLoop`（`subagent.go:80`）不走 `RunStop`、也不下发 meta，且其结果以文本摘要并入主 Agent。本次**不改动子 Agent**，保持现状。

## 5. 测试与验证

- **单测（runtime 包）**：
  - 构造一次「无工具调用」的纯文本回复，断言最终 `assistant` 事件 / 写入历史的 `Meta.ContextTokens` **大于**「请求前估算值」（因包含了模型输出），且等于 `EstimateRequestTokens(systemPrompt, lastRequestHistory + finalAssistant, tools)`。
  - 构造一次「多轮工具调用后结束」的回复，断言最终用量基于**最后一轮**请求历史 + 最终回复计算。
  - 复用现有 `captureEventWriter` 断言事件字段。
- **回归**：
  - 过程中 `meta` 事件仍按每轮 / 每工具实时下发（值为请求前估算）。
  - 压缩、记忆（`scheduleMemoryWork` 使用的 `lastRequestHistory` 未被污染——已用 `cloneMessages`）、`done` 事件不变。
- **构建**：`go build ./...`、`go test ./...`（config 包预存环境变量相关失败除外）。

## 6. 待确认 / 风险

1. `cloneMessages` 须确认存在且做深/浅拷贝足够（避免污染 `lastRequestHistory`）。若仅需估算、不修改元素，浅拷贝切片即可。
2. 估算口径为 total（输入+输出），数值会比过程中的实时值略大，前端百分比相应变化，属预期。
3. 若后续要改为模型真实 `usage`，可在此基础上替换估算来源（开启 `stream_options.include_usage` 并解析 `Usage`），本设计的「时机」修正同样适用。
