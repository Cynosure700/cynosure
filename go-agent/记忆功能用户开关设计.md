# 记忆功能用户开关设计文档

## 1. 背景与目标

### 1.1 需求
支持用户自选「记忆功能」是否开启。具体行为：

1. 前端个人界面（侧边栏个人信息卡片区域）增加一个开关按钮，展示并切换当前用户的记忆开关状态。
2. 当记忆功能**开启**时，行为与现状完全一致（注入记忆系统提示词、对话结束提取记忆）。
3. 当记忆功能**关闭**时：
   - 调用 LLM 前，**不注入**长期记忆到系统提示词中（即 `MemorySection` 为空）。
   - 对话结束时，**不进行**有效记忆的提取（用户长期记忆 + 会话记忆均不提取/更新）。

### 1.2 关键约束（来自注意事项）
- **不影响其他功能。**
- **会话进来仍然要加锁，结束后依旧要释放锁。** 即：记忆开关只控制「记忆注入」与「记忆提取」，**不得**关闭会话锁与模型历史持久化等收尾基础设施。

### 1.3 非目标
- 不改变记忆提取/注入的业务算法（prompt、整合裁剪规则等保持不变）。
- 不改变锁机制、上下文压缩机制。
- 不为记忆开关引入额外缓存层。

## 2. 现状分析

### 2.1 `EnableMemory` 的现状
当前 `runtime.Service.EnableMemory`（`runtime/runtime.go:60`）是一个 **Service 级别的全局布尔**，在 `NewService` 中固定为 `true`。它同时控制三处逻辑（`conversation_flow.go`）：

| 位置 | 作用 | 是否应受用户开关影响 |
|------|------|----------------------|
| `conversation_flow.go:35` 入口 | **加会话锁** + 启动续期看门狗 | ❌ 不应（约束要求始终加锁） |
| `prompt_builder.go:17` → `selectRelevantMemories` | **注入记忆** 到 system prompt | ✅ 应（关闭时不注入） |
| `conversation_flow.go:127` 结束分支 | `scheduleMemoryWork`：释放锁 + 持久化模型历史 + **提取记忆** | 部分（释放锁/持久化要保留，提取要受控） |

> 结论：现有的「全局 `EnableMemory`」把「锁基础设施」和「记忆业务」耦合在一起。本次需求要求二者解耦——锁始终生效，记忆业务按用户偏好开关。

### 2.2 记忆提取的执行链路
`scheduleMemoryWork`（`conversation_memory.go:128`）在异步 goroutine 中依次执行：
1. `UpsertConversationModelHistory`（模型历史持久化）—— **属于上下文压缩基础设施，必须保留。**
2. `extractMemories`（提取用户长期记忆：偏好/经历/语义）—— **记忆业务，受开关控制。**
3. `updateConversationMemory`（更新会话记忆条目）—— **记忆业务，受开关控制。**

### 2.3 用户身份与持久化
- 用户通过 JWT 鉴权后，`storage.User` 被注入 `request context`（`auth/service.go:99`），`RespondToConversation` 入参已携带 `user`。
- 已有 `user_profiles` 表（`migrations.go:104`）及 `GetUserProfile/UpsertUserProfile`（`user_profiles_repo.go`），但目前未用于该场景。本设计**不复用** profile_json（语义不清晰），而是在 `users` 表新增一个明确的布尔列，简单直观。

## 3. 设计方案

### 3.1 总体思路
将「记忆是否开启」从 **Service 全局** 下沉为 **用户级偏好**，持久化在 `users` 表。每轮对话根据当前用户的偏好决定：
- 是否注入记忆到 system prompt；
- 是否在收尾时提取记忆。

**会话锁、模型历史持久化保持无条件执行**，与记忆开关解耦。

### 3.2 数据模型变更

#### 3.2.1 `users` 表新增列
```sql
ALTER TABLE users ADD COLUMN memory_enabled TINYINT(1) NOT NULL DEFAULT 1;
```
- 默认 `1`（开启），保证存量用户与新用户行为不变。
- 通过 `migrations.go` 中新增 `ensureUsersMemoryEnabledColumn(ctx)`（参照现有 `columnExists` 幂等模式），不修改 `001_init.sql` 的既有建表语义（也会在 `001_init.sql` 的 `users` 表补充该列定义，保持新库一致）。

#### 3.2.2 `storage.User` 结构体（`models.go`）
```go
type User struct {
    ...
    MemoryEnabled bool `json:"memory_enabled"`
    ...
}
```

#### 3.2.3 scan/查询调整（`scan.go` / `users_repo.go`）
- `scanUser` 增加 `&user.MemoryEnabled`。
- `GetUserByID`、`GetUserByEmailOrUsername` 的 SELECT 列表增加 `memory_enabled`。
- `CreateUser` 无需显式写入（依赖默认值），保持注册逻辑不变。
- 新增 `UpdateUserMemoryEnabled(ctx, userID string, enabled bool) error`。

### 3.3 后端运行时改造

#### 3.3.1 解耦锁与记忆（`conversation_flow.go`）
保持 `s.EnableMemory` 作为「系统是否启用记忆能力」的总开关（用于测试场景默认关闭，行为不变），**新增按用户判定**：

```go
memoryOn := s.EnableMemory && user.MemoryEnabled
```

- **入口加锁**：维持 `if s.EnableMemory { ...AcquireConversationLock... }`。
  > 说明：锁的目的是串行化「收尾写库」与「下一轮请求」。即使用户关闭记忆，仍有 `UpsertConversationModelHistory` 写库收尾，故锁条件维持 `s.EnableMemory`（系统级），**不**依赖 `user.MemoryEnabled`。满足「会话进来仍要加锁、结束后释放锁」。
- **注入记忆**：`buildSystemPrompt` 改为按 `memoryOn` 决定是否调用 `selectRelevantMemories`。
- **结束收尾**：维持 `if s.EnableMemory { scheduleMemoryWork(...) }`，把 `memoryOn` 传入 `scheduleMemoryWork`，由其内部决定是否执行记忆提取（但**始终**释放锁、**始终**持久化模型历史）。

#### 3.3.2 注入侧（`prompt_builder.go`）
`buildSystemPrompt` 增加是否注入记忆的判断：
```go
func (s *Service) buildSystemPrompt(ctx, conversation, user, snapshot, history) string {
    memorySection := ""
    if s.EnableMemory && user.MemoryEnabled {
        memorySection = s.selectRelevantMemories(ctx, user, history)
    }
    return s.buildSystemPromptWithMemory(user, snapshot, memorySection)
}
```
> `selectRelevantMemories` 内部已有 `!s.EnableMemory` 守卫；这里额外加 `user.MemoryEnabled` 判断，关闭时直接传空 section，**不发起记忆检索 LLM 调用**。

#### 3.3.3 收尾侧（`conversation_memory.go`）
`scheduleMemoryWork` 增加 `memoryOn bool` 参数：
```go
func (s *Service) scheduleMemoryWork(conv, user, history, modelHistory, token, stopRenew, memoryOn) bool {
    ...
    go func() {
        defer release lock          // 不变：始终释放锁
        ...
        if len(modelHistory) > 0 {  // 不变：始终持久化模型历史
            s.Store.UpsertConversationModelHistory(...)
        }
        if memoryOn {               // 新增：仅开启时提取记忆
            s.extractMemories(ctx, user, history)
            s.updateConversationMemory(ctx, conv, user, history)
        }
    }()
    return true
}
```
> 锁的获取/续期/释放、模型历史持久化均不受 `memoryOn` 影响，完全满足约束。

### 3.4 后端接口改造

#### 3.4.1 `GET /api/me`（`auth_handlers.go:handleMe`）
返回的 `user` 已经天然带上 `memory_enabled`（结构体序列化），前端首屏即可读取开关状态。无需新增字段处理。

#### 3.4.2 新增 `PATCH /api/me/memory`
- 路由（`routes.go`）：`s.mux.Handle("/api/me/memory", s.authService.AuthenticateRequest(http.HandlerFunc(s.handleUpdateMemoryPreference)))`
- handler（`auth_handlers.go`）：
  - 仅接受 `PATCH`，否则 `methodNotAllowed`。
  - body：`{ "enabled": bool }`。
  - 从 context 取当前 user，调用 `store.UpdateUserMemoryEnabled(ctx, user.ID, enabled)`。
  - 返回 `{ "memory_enabled": enabled }`。
- `server.go` 的 `serverStore` 接口增加 `UpdateUserMemoryEnabled`。

> 安全：只能修改"当前登录用户自己"的偏好（user 来自鉴权 context），无越权风险。

### 3.5 前端改造

#### 3.5.1 类型与 API（`api.ts`）
- `User` 类型增加 `memory_enabled: boolean`。
- 新增 `api.updateMemoryPreference(enabled: boolean)` → `PATCH /api/me/memory`。

#### 3.5.2 个人界面开关（`App.tsx`）
- 在侧边栏 `sidebar-header`（用户名/邮箱 + 退出按钮）附近，新增一个「记忆功能」开关。
- 状态：从 `user.memory_enabled` 初始化；切换时乐观更新 + 调用 API，失败回滚并提示。
- 交互参考截图风格（深色卡片 + 按钮/开关），使用现有样式类（如复用 `secondary-toggle` 风格或新增轻量 `.memory-toggle`）。

#### 3.5.3 样式（`styles.css`）
新增少量样式承载开关按钮，保持与现有深色 UI 一致。不大改布局。

## 5. 兼容性与风险

- **存量数据**：新增列默认 `1`，所有已有用户记忆保持开启，行为不变。
- **测试**：现有 `memory_test.go` 用例构造 `Service{EnableMemory:...}` 不受影响；`RespondToConversation` 相关用例中 `storage.User` 未设 `MemoryEnabled` 时默认为 `false`——需确认这些用例若依赖记忆注入需显式置 `true`（实际现有测试默认 `EnableMemory:false`，注入侧本就返回空，无影响）。
- **锁安全（重点）**：锁的 acquire/renew/release 与 `memoryOn` 完全解耦，关闭记忆时锁流程不变，满足「进来加锁、结束释放锁」。
- **关闭记忆时性能**：跳过记忆检索（1 次 LLM）与记忆提取（多次 LLM），尾延迟更低。
