# 错误兜底机制设计

## 1. 需求

用户在会话中发送消息后，当系统执行出错（LLM 调用失败、上下文压缩失败、超过单次对话最大轮数、未捕获 panic 等）时，应当向前端用户统一返回一句友好提示：

> 系统运行出错，请稍后重试

而**不是**把后端原始错误信息（如 `conversation round limit 50 exceeded`、`model stream returned no choices`、底层 SQL/网络错误等）直接暴露给终端用户。

要求：
- 统一兜底文案，避免泄露内部实现细节。
- 覆盖所有「用户发消息后系统侧出错」的路径，不仅仅是题述两种场景。
- 工具调用失败（含 `spawn_subagent` 子任务）**不中断当前会话**，按现有逻辑把失败结果回传给 LLM。
- **不引入数据库事务/回滚**：会话数据在对话完成后才存储，中断不会污染会话数据（详见 3.6）。
- **不影响**正常对话、工具执行、审计、压缩、记忆等现有功能。
- 后端仍保留原始错误用于日志排查（不能因为兜底而丢失错误上下文）。

---

## 2. 现状分析

### 2.1 主对话入口与错误下发

- `RespondToConversation`（`internal/web/runtime/conversation_flow.go:30`）是主对话循环，返回 `(storage.Message, error)`。
- HTTP 流式处理在 `handleConversationByID`（`internal/web/app/conversation_handlers.go:97`）：
  ```go
  assistant, err := s.runtime.RespondToConversation(r.Context(), conversation, user, body.Content, writer)
  if err != nil {
      _ = writer.Event("error", map[string]any{"message": err.Error()}) // ← 原始错误直接下发
      return
  }
  ```
  这里 `err.Error()` 被原样塞进 SSE `error` 事件下发到前端。

- 前端 `streamConversation`（`web/src/api.ts:214`）收到 `error` 事件后调用 `onError(payload.message)`；`App.tsx:581` 直接 `setError(message)` 展示给用户。
- 因此**前端展示的就是后端的原始 error 字符串**，这是本次要兜底的核心位置。

### 2.2 会触发 error 返回的场景（全量梳理）

`RespondToConversation` 及其调用链中，所有 `return ..., err` / `return ..., fmt.Errorf(...)` 都会冒泡到 `conversation_handlers.go:110` 被下发。逐一梳理：

| # | 位置 | 场景 | 当前错误文案（示例） |
|---|------|------|---------------------|
| 1 | `conversation_flow.go:88` | **超过单次对话最大轮数** `maxRound=50` | `conversation round limit 50 exceeded` |
| 2 | `conversation_flow.go:108`→`runModelRoundStream` | LLM 流式调用失败 / 建流失败 | 底层 SDK 错误 |
| 3 | `conversation_flow.go:225` | 模型未返回任何 choice | `model stream returned no choices` |
| 4 | `conversation_flow.go:91` | 上下文压缩 `compressContextBeforeLLM` 失败 | 压缩/摘要相关错误 |
| 5 | `conversation_flow.go:63` | 加载历史消息失败 | DB / 缓存错误 |
| 6 | `conversation_flow.go:69` | `RunUserPromptSubmit` hook 失败 | hook 错误 |
| 7 | `conversation_flow.go:73` | `buildSkillSnapshot` 失败 | skill 加载错误 |
| 8 | `conversation_flow.go:132,148,155` | `RunStop` / `RunPreToolUse` / `RunPostToolUse` hook 失败 | hook 错误 |
| 9 | SSE handler 内 **panic** | 任意未捕获 panic | 连接直接断开，前端无任何提示 |

> 说明：场景 1（最大轮数）与场景 2/3（系统执行出错）是题述明确要求的两类；其余 4–9 同属「用户发消息后系统侧失败」，应一并纳入兜底，避免遗漏导致原始错误泄露或前端无提示。

#### 不纳入兜底：工具执行失败（含 `spawn_subagent` 子任务）

`executeToolCall`（`conversation_flow.go:151`）返回的是 `toolExecutionOutcome`（含 `Status` / `Result`），**工具调用失败不会 `return err` 中断对话**，而是把失败结果作为 tool 消息回传给 LLM，由模型自行决定后续动作。这是现有设计，**保持不变、不做兜底**。

`spawn_subagent` 子任务出错同理：`tool_registry.go:247-249` 已把 `runSubagent` 返回的 error 包装成 `toolExecutionOutcome{Status: "rejected", Result: "Subagent failed: ..."}` 回传给主 agent，**当前就不会冒泡中断主会话**。因此子任务出错按工具失败逻辑处理，不纳入兜底、不中断当前会话。

### 2.3 SSE 事件与前端约定

- `SSEWriter.Event(name, data)`（`internal/web/runtime/sse.go:13`）。
- 现有事件：`conversation` / `assistant_delta` / `reasoning_delta` / `meta` / `assistant` / `error` / `done`。
- 前端对 `error` 事件的处理已存在且完善（`api.ts:214`、`App.tsx:575`），**无需改前端**：只要后端把 `error` 事件的 `message` 字段替换成统一兜底文案即可。

### 2.4 关键约束

- 流式响应中，`error` 事件可能在已经下发了部分 `assistant_delta` 之后才出现（例如第 3 轮工具执行后才报错）。前端 `onError` 已会清理无内容的流式占位消息（`App.tsx:582`），保持兼容即可。
- panic 当前无任何 recover 保护（仅 `conversation_memory.go:140` 的异步记忆协程有 recover），SSE handler 内 panic 会导致 HTTP 连接异常中断，用户侧无任何反馈。

## 3. 设计方案

### 3.1 总体思路

采用「**收口在 HTTP handler 边界**」的最小侵入方案：

1. 在 `handleConversationByID` 的流式分支里，把下发给前端的错误文案统一替换为兜底文案，原始错误仅写日志。
2. 增加 panic recover，保证任意 panic 也能下发兜底文案而非断连。
3. 定义一个统一的兜底文案常量，便于后续维护与复用。

**为什么收口在 handler 边界而不是逐个改 `return err`？**
- 所有错误都最终汇聚到 `conversation_handlers.go:110` 这一处下发点，改一处即可覆盖场景 1–8，改动面最小、最不易遗漏、最不影响内部逻辑。
- 内部仍传递原始 error，日志可读、可排查，符合「保留原始错误」要求。

### 3.2 兜底文案常量

在 `internal/web/runtime`（或 app 包）新增常量：

```go
// 用户可见的统一兜底文案，避免泄露内部错误细节。
const FallbackErrorMessage = "系统运行出错，请稍后重试"
```

放置位置建议：`internal/web/runtime/sse.go` 或新增 `internal/web/runtime/errors.go`，由 app 包引用。

### 3.3 改动点一：统一错误下发（覆盖场景 1–8）

`internal/web/app/conversation_handlers.go` 流式分支：

```go
assistant, err := s.runtime.RespondToConversation(r.Context(), conversation, user, body.Content, writer)
if err != nil {
    // 原始错误仅记录日志，便于排查
    logger.Warn(fmt.Sprintf("conversation stream failed conversation=%s user=%s: %v",
        conversation.ID, user.ID, err))
    // 客户端主动断开（context.Canceled）属正常现象，连接已断，不下发 error 事件
    if !errors.Is(err, context.Canceled) {
        _ = writer.Event("error", map[string]any{"message": runtime.FallbackErrorMessage})
    }
    return
}
```

要点：
- 对用户下发的文案统一为 `runtime.FallbackErrorMessage`，不再使用 `err.Error()`。
- 新增 `logger.Warn`，保留原始错误用于排查。
- `context.Canceled`（用户主动断开）只记日志、**不下发** `error` 事件。
- 其余逻辑不变。

### 3.4 改动点二：panic 兜底（覆盖场景 9）

在流式分支外层包一层 recover，防止任意 panic 直接断连：

```go
if len(parts) == 2 && parts[1] == "stream" && r.Method == http.MethodPost {
    // ... 解析 body、设置 SSE 头、写 conversation 事件 ...
    writer := runtime.SSEWriter{W: w}
    _ = writer.Event("conversation", map[string]any{"id": conversation.ID, "title": conversation.Title})

    defer func() {
        if rec := recover(); rec != nil {
            logger.Error(fmt.Sprintf("conversation stream panic conversation=%s: %v", conversation.ID, rec))
            _ = writer.Event("error", map[string]any{"message": runtime.FallbackErrorMessage})
        }
    }()

    assistant, err := s.runtime.RespondToConversation(...)
    // ... 同 3.3 ...
}
```

要点：
- recover 在 SSE 头与 `conversation` 事件写出之后注册，确保仍可下发 `error` 事件。
- panic 记 `logger.Error`（含堆栈可后续增强），用户侧得到统一兜底文案。

### 3.5 不改动的部分（明确边界）

- **不改前端**：`error` 事件处理链路已完善，文案由后端决定。
- **不改 `RespondToConversation` 内部**的任何 `return err`：保持原始错误向上传递，仅在边界收口。
- **不改** `maxRound` 的值与判断逻辑：超轮仍返回 error，只是下发文案变为兜底文案。
- **不改**记忆、压缩、工具、审计等流程。

### 3.6 关于数据库事务/回滚：不引入

本方案**不引入数据库事务，也不做中断回滚**，原因如下：

- 会话核心数据（用户消息、assistant 消息、整条会话历史 `history_json`）在对话过程中**只追加到内存** `state.History` / `state.ModelHistory`，直到对话**成功结束**时才由 `RunStop` → `SetConversationHistory`（`conversations_repo.go:72`）一次性落库。因此对话中断时，会话历史**根本不会被写入**，天然不会产生需要回滚的脏数据。
- 模型历史 `UpsertConversationModelHistory`、各类记忆写入均在**对话成功结束后**的异步协程 `scheduleMemoryWork`（`conversation_memory.go:129`）中执行；中断/出错路径不会触发该协程，无需回滚。
- 对话进行中逐步落库的仅是**审计/旁路数据**（`tool_calls`、`persisted_outputs`、`context_summaries`、`subagent_messages`），它们是「已发生事实」的记录，保留下来反而有利于排查，无需回滚。

> 结论：在当前「会话数据对话完成后才存储」的架构下，中断不会污染会话数据，因此不需要事务机制。本设计仅聚焦「统一错误文案 + panic 兜底」。

## 4. 影响面与风险

| 项 | 评估 |
|----|------|
| 前端 | 无需改动，自动展示新文案 |
| 正常对话 | 无影响（仅错误路径变化） |
| 日志/排查 | **增强**：原始错误改为显式落日志 |
| panic 安全性 | **增强**：新增 recover，避免断连 |
| 测试 | 需新增/调整：超轮场景、LLM 失败场景下，下发的 `error.message` 应为兜底文案 |

潜在风险：
- 现有测试若断言了具体错误文案（如 `server_test.go` 检查 `error` 事件内容），需同步更新断言为兜底文案。改动前需检查 `internal/web/app/server_test.go` 与 `runtime_test.go`。

## 5. 实施步骤

1. 新增常量 `FallbackErrorMessage`（`runtime/sse.go` 或 `runtime/errors.go`）。
2. 修改 `conversation_handlers.go` 流式分支：原始错误落日志 + 下发兜底文案（改动点一）。
3. 在流式分支新增 panic recover（改动点二）。
4. 检查并更新受影响的测试断言（`server_test.go`、`runtime_test.go`）。
5. 自测：
   - 模拟 LLM 失败 → 前端显示「系统运行出错，请稍后重试」。
   - 将 `maxRound` 临时调小触发超轮 → 前端显示同样文案。
   - 日志中能看到原始错误。

## 6. 已确认决策

1. **统一文案**：所有系统侧错误（含超时/超轮）统一返回「系统运行出错，请稍后重试」，不区分错误类型。
2. **用户主动断开**：`context.Canceled` 只记日志、不下发 `error` 事件（见 3.3）。
3. **常量位置**：兜底文案常量放 `runtime` 包，由 `app` 包引用。
4. **工具失败不兜底、不中断**：工具调用失败（含 `spawn_subagent` 子任务出错）按现有逻辑把结果回传 LLM、不中断对话（见 2.2）。
5. **不引入数据库事务/回滚**：会话数据对话完成后才存储，中断不会污染会话数据，无需事务（见 3.6）。
