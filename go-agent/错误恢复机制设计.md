# 错误恢复机制设计

## 1. 需求

为 go-agent（`nano_cc`）新增 LLM 调用层的**错误恢复机制**，覆盖三类场景：

1. **输出被截断**（模型话说一半，`max_tokens` 用完）
   - 默认 `max_tokens = 8000`。
   - **第一次**截断：直接把 `max_tokens` 从 8K 升到 **64K**（8 倍），**重试同一请求**——此时**不**把截断输出追加进 messages，保持原始请求不变。
   - 64K 仍不够：才**保存截断输出**并注入**续写提示**让模型接着说，**最多 3 次**。
2. **上下文超限**（LLM 返回 `prompt_too_long`，HTTP **413**）
   - 触发 **reactive compact**（比现有全量摘要更激进的压缩），压缩后重试。
   - 仍不行则**直接报错**（当前仅需日志记录）。
3. **临时故障**（**429** 限流、**529** 过载）
   - 统一走**指数退避 + 抖动**：第 1 次等 0.5s，第 2 次等 1s，第 3 次等 2s……最多 **10 次**。

约束（沿用《错误兜底机制设计》的边界）：
- **不影响**正常对话、工具执行、审计、压缩、记忆等现有功能。
- 恢复**全部失败后**仍向上返回 error，由现有 HTTP 边界兜底（`FallbackErrorMessage`）+ 日志收口，不改前端。
- 改动面最小、surgical。

## 2. 现状分析（关键缺口）

### 2.1 LLM 调用层 `internal/llm/client.go`

- `CreateChatCompletion`（`:43` 非流式）与 `CreateChatCompletionStream`（`:93` 流式）各自手搓 HTTP 请求体：
  ```go
  body := map[string]any{
      "model": req.Model, "messages": req.Messages,
      "thinking": ..., "reasoning_effort": "high", "stream": false/true,
  }
  ```
  **缺口 ①**：body 里**完全没有 `max_tokens`**。需求"默认 8000 / 升级 64K"无从谈起，截断检测也无意义。
- 错误处理（`:81-83` 非流式、`:123-130` 流式）：
  ```go
  if resp.StatusCode != http.StatusOK {
      return ..., fmt.Errorf("API error (status %d): %s", resp.StatusCode, string(respBody))
  }
  ```
  **缺口 ②**：413/429/529 全被压成**无类型 error 字符串**，上层无法判断该退避还是该压缩。

### 2.2 主循环 `internal/web/runtime/conversation_flow.go`

- 主循环 `for {` 在 `:86`，每轮：
  1. `:91` `compressContextBeforeLLM`（已有压缩管线）。
  2. `:102` 组装 `openai.ChatCompletionRequest`（**未设置 `MaxTokens`**）。
  3. `:108` `msg, finishReason, err := s.runModelRoundStream(ctx, state, req)`。
  4. `:111` `if err != nil { return ..., err }`（直接冒泡）。
  5. `:123` `if finishReason != "tool_calls" ...` 判断会话是否结束。
- `runModelRoundStream`（`:176`）聚合流式分片，**已拿到 `finishReason`**（`:220-222`），但**未对 `openai.FinishReasonLength`（截断）做任何处理**。
- **缺口 ③**：无任何重试 / 退避 / 截断续写逻辑。

### 2.3 压缩管线 `internal/web/runtime/compression/`

- `NewDefaultCompressor()`（`compression.go:64`）顺序执行 5 个策略，末层是 `FullHistorySummarizationStrategy`（全量摘要，`full_history_summarization.go`）。
- 全量摘要触发条件（`:49-52`）：仅当 `EstimateRequestTokens > ContextTokenBudget()`（= 128K-8K-4K = 116K）才压缩；`summaryTargetTokens=8K`、`recentTailMinTokens=16K`。
- `compressContextBeforeLLM`（`context_compression.go:30`）构造 `compression.Request` 执行管线，返回 request-only 历史。
- **复用点**：reactive compact 需要"比全量摘要更激进"——更小的摘要目标、更短的 tail 窗口、忽略预算阈值（强制压缩）。

### 2.4 配置 `internal/config`

- `s.Cfg.LLM`（`ModelID` / `BaseURL` / `APIKey`）。`max_tokens` 默认值与重试参数将以**常量**形式落在对应包内，不引入新配置项（保持最小改动；如需可配置后续再加）。

## 3. 设计方案

### 3.0 总体分层：退避在 client 层，截断/压缩在 runtime 层

| 恢复类型 | 是否需操作 messages/history | 落点 |
|---|---|---|
| 429/529 指数退避 | 否（重发同一请求即可） | **`llm/client.go` 内部**（仅建流/发请求阶段） |
| 输出截断重试（升 token / 续写） | 是（要改 `MaxTokens`、可能追加续写提示） | **`conversation_flow.go` 单轮请求内**（包一层 `runModelRoundWithRecovery`） |
| 413 上下文超限 reactive compact | 是（要改 history） | **`conversation_flow.go` 单轮请求内** + 新增压缩策略 |

理由：退避只是"原样重发"，不碰 messages，最适合收在 client 层（对 runtime 透明）；截断与 413 都要改请求内容，必须在能访问 `state` / `req` 的 runtime 层处理。三类恢复**都作用在"单轮 LLM 请求"粒度**（用户选定），即每进入一轮模型调用独立计数，下一轮工具调用后重新计数。

---

### 3.1 前置改造 ①：client 层下发 `max_tokens`

`openai.ChatCompletionRequest` 自带 `MaxTokens int` 字段。在 `client.go` 两处 body 透传：

```go
body := map[string]any{ ... }
if req.MaxTokens > 0 {
    body["max_tokens"] = req.MaxTokens
}
```

主循环组装请求时设默认值（新增常量）：

```go
// conversation_flow.go
const (
    defaultMaxTokens = 8000   // 默认输出上限
    truncationMaxTokens = 64 * 1024  // 第一次截断后升级到 64K
)
req := openai.ChatCompletionRequest{
    Model: s.Cfg.LLM.ModelID, Messages: state.Messages, Tools: toolDefs,
    MaxTokens: defaultMaxTokens,
}
```

> 摘要调用（`summarizer.go`）维持现状不设 `MaxTokens`，不受影响。

### 3.2 前置改造 ②：可识别的 API 错误类型

在 `internal/llm` 新增 `errors.go`：

```go
package llm

type APIError struct {
    StatusCode int
    Body       string
}
func (e *APIError) Error() string {
    return fmt.Sprintf("API error (status %d): %s", e.StatusCode, e.Body)
}

// 语义判断辅助（供 runtime 层使用）
func IsContextOverflow(err error) bool { // 413
    var apiErr *APIError
    return errors.As(err, &apiErr) && apiErr.StatusCode == 413
}
func isRetryableStatus(code int) bool { // 429 / 529
    return code == http.StatusTooManyRequests || code == 529
}
```

`client.go` 两处 `if resp.StatusCode != http.StatusOK` 改为返回 `&APIError{StatusCode, Body}`，错误文案保持不变（向后兼容日志）。

> 注：413 也可能在 body 里带 `prompt_too_long` 字样。以 **HTTP 413 状态码**为主判据（需求明确），文案匹配作为兜底辅助判断（防止网关把 413 透传成别的码）。

### 3.3 场景三：429/529 指数退避 + 抖动（client 层）

在 `client.go` 把"发请求 + 读状态码"封装成内部带重试的逻辑，**仅覆盖建流/发请求阶段**（用户选定）——流一旦建立、开始吐 token 就不再重试，避免向用户重复输出。

新增退避常量与函数：

```go
const (
    retryBaseDelay = 500 * time.Millisecond // 第1次 0.5s
    retryMaxDelay  = 30 * time.Second
    maxTransientRetries = 10                 // 最多 10 次
)

// 第 n 次重试（n 从 0 起）：base * 2^n，再加 [0, delay/2) 抖动，封顶 retryMaxDelay
func backoffDelay(attempt int) time.Duration { ... }
```

退避序列：0.5s → 1s → 2s → 4s → 8s …（封顶 30s），叠加抖动。`CreateChatCompletionStream` 与 `CreateChatCompletion` 各自包一层 `for attempt := 0; attempt <= maxTransientRetries; attempt++`：
- 收到 `*APIError` 且 `isRetryableStatus(code)` → `select { case <-time.After(backoffDelay(attempt)): case <-ctx.Done(): return ctx.Err() }`，继续重试。
- 其他错误 / 成功 → 直接返回。
- 超过次数 → 返回最后一次 `*APIError`。

> 退避在 client 内对 runtime 完全透明；`ctx.Done()` 保证用户主动断开时立即停止（沿用现有 `context.Canceled` 兜底）。

### 3.4 场景一：输出截断恢复（runtime 单轮内）

在 `conversation_flow.go` 用 `runModelRoundWithRecovery` 包裹原 `runModelRoundStream`，封装"截断 + 413"两类单轮内恢复。截断处理状态机：

```
进入一轮 → MaxTokens=8000 发请求
  ├─ finishReason != length  → 正常返回
  └─ finishReason == length（截断）
        ├─ 尚未升过 token？ → MaxTokens=64K，重试【不动 messages】（升级阶段，1 次）
        └─ 已升到 64K 仍截断 → 进入"续写"循环（最多 3 次）：
              1. 把已截断的 assistant 内容作为一条 assistant 消息追加进 req.Messages
              2. 追加一条续写提示（user/system role，见 §3.6）
              3. MaxTokens 维持 64K 重试
              4. 把新产出拼接到累计 content
              直到 finishReason != length 或续写用尽 3 次
```

关键点：
- **升级阶段不污染 messages**（需求明确"保持原始请求不变"）——只改 `req.MaxTokens` 重发。
- 续写阶段把"截断片段 + 续写提示"作为**临时请求消息**（仅本轮 LLM 请求使用），最终把所有片段**拼接成一条完整 assistant 消息**返回给主循环（`msg.Content = 片段1+片段2+...`），主循环的 `state.Messages`/`state.History` 只看到拼接后的完整结果，对话历史保持干净。
- 续写 3 次仍截断：用拼接到当前的内容**尽力返回**（finishReason 置为非 length，正常收尾），并 `logger.Warn` 记录"截断续写耗尽"。
- **流式兼容**：续写产生的多段需要正确地向前端 `assistant_delta` 推送。现有 `runModelRoundStream` 内有 `bufferedContentDeltas` 缓冲并在末尾统一 flush（`:228-232`）。续写循环每段沿用同一缓冲，保证用户侧看到的是连续输出。

> 计数：`tokenUpgrade` 1 次 + 续写 ≤ 3 次，均为**单轮请求内**计数，下一轮重新开始。

### 3.5 场景二：413 上下文超限 reactive compact（runtime 单轮内 + 新策略）

当 `runModelRoundWithRecovery` 内 LLM 调用返回 `llm.IsContextOverflow(err) == true`：

1. 调用新方法 `s.reactiveCompact(ctx, state)`：用**更激进**的压缩重建 `state.Messages`。
2. 重建后**重试一次**该轮 LLM 调用。
3. 仍 413（或仍失败）→ **直接返回 error**（冒泡到 HTTP 边界，日志记录，需求只需日志）。

**新增独立压缩策略**（用户选定）`compression/reactive_compact.go`：

```go
const reactiveCompactStrategyName = "reactive_compact"

const (
    reactiveSummaryTargetTokens = 2 * 1024  // 比全量摘要 8K 更小
    reactiveTailMinTokens       = 4 * 1024  // 比全量摘要 16K 更短
)

type ReactiveCompactStrategy struct{}
func (s *ReactiveCompactStrategy) Name() string { return reactiveCompactStrategyName }
func (s *ReactiveCompactStrategy) Apply(ctx, req *Request) error {
    // 与 FullHistorySummarization 同构，但：
    // 1. 强制压缩，忽略 before<=budget 的阈值判断（既然真 413 了）
    // 2. summaryTargetTokens / recentTail 用更激进的小值
    // 3. 丢弃 reasoning_content，tool_result 仅留占位
}
```

调用方式：reactive compact **不进默认管线**（避免影响正常路径），而是由 runtime 在捕获 413 时**显式单独运行**；**压缩成功后同时写回 `state.ModelHistory`**，使下一轮对话直接复用这次压缩结果，避免重复 413 与重复压缩：

```go
// conversation_flow.go
func (s *Service) reactiveCompact(ctx, state) error {
    history := cloneMessages(state.ModelHistory)
    req := &compression.Request{ ...同 compressContextBeforeLLM..., RequestHistory: history }
    if err := (&compression.ReactiveCompactStrategy{}).Apply(ctx, req); err != nil { return err }
    // 1) 本轮立即生效
    state.Messages = buildOpenAIMessages(state.SystemPrompt, req.RequestHistory)
    // 2) 写回模型历史，供下一轮复用压缩结果（关键）
    state.ModelHistory = req.RequestHistory
    return nil
}
```

> 复用 `compression.Request` / `Store` / `Summarizer` / 现有 `historyHash`、`buildSummaryHistory` 等辅助；只是参数更激进 + 强制执行。
>
> **与 §3.5 之前表述的差异（按需求修正）**：reactive compact **既修改本轮 `state.Messages`，也写回 `state.ModelHistory`**——因为 413 是真实发生的上下文超限，压缩后的精简历史必须成为后续轮次的新基线，否则下一轮 `compressContextBeforeLLM` 仍从未压缩的旧 `ModelHistory` 出发，会再次 413 并重复压缩，浪费一次 LLM 摘要调用。
>
> **边界**：
> - **只写 `state.ModelHistory`，不写 `state.History`**：`state.History` 是面向前端的完整展示历史，不能被压缩污染；`state.ModelHistory` 才是"可复用的模型历史"（语义见 §2.2 `loadModelHistory`），正是用来跨轮复用压缩结果的。
> - `state.ModelHistory` 在会话成功结束后由现有 `scheduleMemoryWork` → `UpsertConversationModelHistory` 持久化，因此本次压缩结果也会自然落库、跨请求复用，无需额外持久化代码。
> - reactive compact 失败时**不写回**任何状态，保持 `state` 原样后直接报错（见 §3.6）。

### 3.6 最终失败：复用现有错误兜底机制

三类恢复机制**全部耗尽/仍失败**时，均**不再自行造文案**，而是直接向上 `return ..., err`（原始错误），冒泡到现有 HTTP 边界统一兜底——即《错误兜底机制设计》已落地的逻辑：`conversation_handlers.go` 流式分支把原始错误写日志，对前端下发统一文案 `runtime.FallbackErrorMessage = "系统运行出错，请稍后重试"`（`context.Canceled` 除外，不下发）。

各场景最终失败的冒泡路径：

| 场景 | 恢复耗尽后的行为 | 冒泡终点 |
|------|------------------|----------|
| 截断-续写 ≤3 次仍截断 | 尽力返回已拼接内容并 `logger.Warn`（**不算失败**，正常收尾，**不触发兜底**） | — |
| 413 reactive compact 后仍 413 / 压缩本身失败 | `return ..., err`（`logger.Warn` 记原始错误） | HTTP 边界 → `FallbackErrorMessage` |
| 429/529 退避达 10 次仍失败 | client 层返回最后一次 `*APIError`，runtime `:108` 处 `return ..., err` | HTTP 边界 → `FallbackErrorMessage` |
| 截断/413 恢复过程中遇到其它非可恢复错误 | 直接 `return ..., err` | HTTP 边界 → `FallbackErrorMessage` |

要点：
- **零额外改动**：恢复机制只负责"尽力恢复"，恢复不了就让原始 error 自然冒泡，**复用** §2 现有兜底，不在 runtime/llm 层新增任何用户可见文案。
- **原始错误不丢失**：各恢复入口在放弃前 `logger.Warn` 记录恢复过程（如"截断续写耗尽""413 压缩后仍超限""429 退避耗尽"），HTTP 边界再记一次最终错误，便于排查。
- **续写耗尽是特例**：截断续写 3 次用尽属"已尽力产出"，按正常结果返回（拼接内容 + 非 length 收尾），**不**走兜底文案——否则会丢弃已生成的大段有效内容。

### 3.7 续写提示词（参考 Claude Code / Codex 风格）

升级到 64K 仍截断后注入的续写提示（英文，贴合模型续写语境）：

```
Output token limit hit. Resume directly — no apology, no recap of what
you were doing. Pick up mid-thought if that is where the cut happened.
Break remaining work into smaller pieces.
```

放置为常量 `truncationResumePrompt`，以 `role: user`（或 `system`）的临时消息追加到续写请求。

## 6. 影响面与风险

| 项 | 评估 |
|----|------|
| 正常对话 | 无影响：未截断、无 413、无 429/529 时所有恢复分支均不进入 |
| `max_tokens` 首次下发 | **行为变化**：以前不限输出，现在默认 8000。需确认 8000 对正常回答足够（截断时会自动升 64K，安全） |
| 退避阻塞 | 最坏 10 次累计可能等待较久；`ctx.Done()` 可被用户取消打断，避免长时间挂起 |
| 续写流式推送 | 需保证多段 `assistant_delta` 顺序正确、不重复 |
| 压缩重试 | reactive compact 复用 LLM 摘要调用，若摘要本身 413/失败 → 直接报错（符合需求） |
| 日志 | 各恢复动作均 `logger.Warn/Info` 记录，便于排查 |

## 7. 待确认 / 假设

1. **413 判据**：以 HTTP 413 状态码为主，body 含 `prompt_too_long` 作辅助。若实际网关返回的码不同，需按真实返回调整 `IsContextOverflow`。
2. **默认 8000 是否影响正常长回答**：截断会自动升 64K 兜底，假设可接受。
3. **退避封顶 30s**：需求只给到第 3 次（2s）和"最多 10 次"，第 4 次起按 ×2 继续（4s/8s/16s/30s 封顶），如需固定上限可调整。
4. 三类恢复参数暂以**常量**硬编码，不新增配置项（最小改动）；如需可配置后续再提。
