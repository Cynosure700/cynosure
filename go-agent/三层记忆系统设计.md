# 三层记忆系统设计文档

> 本文档描述对 go-agent（Link）记忆系统的重构。它**替换**现有的「用户档案卡 + 会话话题清单」两层记忆，改为「过往会话总结 / 用户喜好 / 语义记忆」三层记忆体系。旧设计文档 `记忆系统设计.md` 保留作为历史归档。

## 1. 背景与目标

现状（提交 `8362829`）的记忆系统是两层：

- **用户档案卡**：模型主动调用 `update_memory` 工具，整段覆盖写入一份 JSON，全量注入系统提示词。
- **会话话题清单**：每轮对话结束用 LLM 抽取 3-6 个话题短语，跨会话静态注入。

新需求要求把记忆能力升级为**三类、自动提取、智能召回**：

| 记忆类型 | type 值 | 说明 | 归属 |
| --- | --- | --- | --- |
| **过往会话总结** | `session_summary` | 存储具体事件和经历（不是单个会话的原始消息），保持事件完整性和时间序列关系 | 单个用户 |
| **用户喜好记忆** | `user_preference` | 用户的喜好、约束、长期习惯 | 单个用户 |
| **语义记忆** | `semantic` | 系统中长期积累的抽象通用知识 | 系统级共享 |

三个核心时机：

1. **注入（每轮会话开始前）**：把当前上下文 + 全部相关记忆传给大模型，由模型挑选相关的最多 10 条，注入系统提示词的 `<memory>` 段。
2. **提取（每轮会话结束后）**：调用大模型从对话中抽取三类记忆，存入数据库。
3. **整理/淘汰（提取入库后按阈值触发）**：
   - 用户喜好达到 **20 条** → 调用大模型去重、合并矛盾、淘汰过时记忆。
   - 过往会话总结达到 **20 条** → 按更新时间淘汰**最早的 10 条**。
   - 语义记忆达到 **50 条** → 调用大模型去重、合并矛盾、淘汰过时记忆。

设计原则（沿用现有系统）：

- **低侵入**：复用 `PromptOptions.MemorySection` → `<memory>` 标签、现有 `RespondToConversation` 流程的注入点/结束点。
- **可降级**：所有记忆读写与 LLM 调用 best-effort，失败仅记日志，绝不中断主对话。
- **不破坏旧库**：保留旧的 `user_profiles`/`conversation_topics` 表（迁移不 DROP），仅停用代码引用。

## 2. 总体架构

```
┌────────────────────────────────────────────────────────────────┐
│ RespondToConversation (conversation_flow.go)                    │
│                                                                 │
│  1. 进入对话循环前（注入）：                                      │
│     buildSystemPrompt(ctx, conversation, user, snapshot, history)│
│       └─> selectRelevantMemories(ctx, user, history)            │
│             ├─ ListRelevantMemories(userID)  // 两类+系统语义     │
│             ├─ LLM 相关性筛选 → 选 ≤10 条索引                     │
│             └─ renderMemorySection → 注入 <memory>               │
│                                                                 │
│  2. 对话循环中：正常工具调用（不再有 update_memory）              │
│                                                                 │
│  3. 对话结束后（提取 + 整理/淘汰）：                              │
│     extractMemories(ctx, user, history)                         │
│       ├─ ListRelevantMemories(existing) + LLM 抽取三类记忆        │
│       ├─ 逐条 InsertMemory                                       │
│       └─ 按出现的 type 触发：                                     │
│           ├─ user_preference≥20 → consolidate(LLM) → Replace     │
│           ├─ session_summary≥20 → DeleteOldest(10)               │
│           └─ semantic≥50        → consolidate(LLM) → Replace      │
└────────────────────────────────────────────────────────────────┘
```

每条记忆的统一结构（对应需求里的 `{name, type, description, body}`）：

```json
{
  "name": "偏好简洁中文回答",
  "type": "user_preference",
  "description": "用户希望回答简洁、用中文、偏好示例代码",
  "body": "在多次对话中用户反复要求精简表达，并指出偏好直接给出可运行示例。"
}
```

- `name`：短标题（≤80 字）。
- `description`：一句话要点（≤300 字），**注入时只用 name + description**。
- `body`：支撑细节（≤2000 字），仅在「提取去重」「召回筛选」阶段喂给模型，不注入提示词以控制 token。

## 3. 数据库设计

### 3.1 单表 `memories`

三类记忆统一存一张表，用 `type` 区分。

```sql
CREATE TABLE IF NOT EXISTS memories (
    id VARCHAR(64) PRIMARY KEY,
    user_id VARCHAR(64) NULL,
    type VARCHAR(32) NOT NULL,
    name VARCHAR(255) NOT NULL,
    description TEXT NOT NULL,
    body LONGTEXT NOT NULL,
    created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    updated_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6),
    KEY idx_memories_user_type (user_id, type, updated_at),
    KEY idx_memories_type (type, updated_at),
    CONSTRAINT fk_memories_user FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

- `idx_memories_user_type`：支撑「按 user+type 查询/计数」「按 updated_at 删最旧 N 条」。
- `idx_memories_type`：支撑语义记忆按 type 全局查询/计数。
- `type` 用 `VARCHAR(32)` + Go 侧常量校验，而非 MySQL `ENUM`，便于扩展。

### 3.2 语义记忆的 user_id 与外键

**`user_id` 可空**，并**保留**外键 `FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE`：

- 用户级记忆（`session_summary`/`user_preference`）：`user_id` = 真实用户 ID，外键生效，用户删除时级联清理。
- 系统级语义记忆（`semantic`）：`user_id = NULL`。InnoDB 对外键列值为 `NULL` 的行不做引用检查（SQL 标准行为），因此 NULL 行合法存在，又不牺牲用户级的级联删除。

> 不用固定 `'system'` 标识：因为 `users` 表无 `id='system'` 行，保留外键会导致插入失败；要支持就得删外键，从而失去所有用户级记忆的级联删除能力。`NULL + 保留外键`兼顾两者。

Go Model 用空串 `""` 表示系统级，repo 层负责 `"" ↔ sql.NullString{Valid:false}` 转换，上层逻辑只跟空串打交道。

### 3.3 Model 与 Repo

`internal/web/storage/models.go` 新增：

```go
type Memory struct {
    ID          string    `json:"id"`
    UserID      string    `json:"user_id"`   // "" 表示系统级语义记忆
    Type        string    `json:"type"`
    Name        string    `json:"name"`
    Description string    `json:"description"`
    Body        string    `json:"body"`
    CreatedAt   time.Time `json:"created_at"`
    UpdatedAt   time.Time `json:"updated_at"`
}
```

新建 `internal/web/storage/memories_repo.go`（方法挂 `*Store`）：

| 方法 | 用途 |
| --- | --- |
| `ListRelevantMemories(ctx, userID)` | 注入/提取去重用：该用户两类 + 全部系统语义，`updated_at DESC` |
| `ListMemoriesByUserAndType(ctx, userID, memType)` | 整理喜好用 |
| `ListSemanticMemories(ctx)` | 整理语义用 |
| `InsertMemory(ctx, m)` | 写入（空串 user_id → NULL） |
| `CountMemoriesByUserAndType(ctx, userID, memType)` | 阈值判断 |
| `CountSemanticMemories(ctx)` | 阈值判断 |
| `DeleteOldestMemories(ctx, userID, memType, n)` | 会话总结淘汰：`updated_at ASC LIMIT n` 删最旧 |
| `ReplaceMemoriesByUserAndType(ctx, userID, memType, items)` | 整理喜好：事务内先删该范围再批量插 |
| `ReplaceSemanticMemories(ctx, items)` | 整理语义：同上，范围 `user_id IS NULL AND type='semantic'` |

`DeleteOldestMemories` 关键 SQL（MySQL 不允许 DELETE 直接 LIMIT+同表子查询，需包一层）：

```sql
DELETE FROM memories WHERE id IN (
  SELECT id FROM (
    SELECT id FROM memories
    WHERE user_id = ? AND type = ?
    ORDER BY updated_at ASC LIMIT ?
  ) AS t
)
```

## 4. 记忆逻辑层（`internal/web/runtime/memory.go`）

新建 `memory.go`，删除旧 `topic_memory.go`。

### 4.1 常量

```go
const (
    MemoryTypeSessionSummary = "session_summary"
    MemoryTypeUserPreference = "user_preference"
    MemoryTypeSemantic       = "semantic"
)
const (
    maxPreferenceMemories    = 20  // 喜好达此值触发 LLM 整理
    maxSessionSummaries      = 20  // 会话总结达此值触发淘汰
    sessionSummaryPruneCount = 10  // 删最旧 10 条
    maxSemanticMemories      = 50  // 语义达此值触发 LLM 整理
    maxInjectedMemories      = 10  // 注入最多 10 条
    maxMemoryDialogueChars   = 4000
    maxMemoryNameRunes       = 80
    maxMemoryDescRunes       = 300
    maxMemoryBodyRunes       = 2000
)
```

### 4.2 提取（会话结束）

`extractMemories(ctx, user, history)`：

1. `renderDialogueForMemory(history)`：仅取 user/assistant 文本，截断 4000 字（沿用旧 `renderHistoryForTopics` 思路）。空则返回。
2. `existing := ListRelevantMemories(user.ID)`（best-effort）作为去重上下文。
3. 一次非流式、无工具 LLM 调用（system=提取提示词，user=existing+dialogue）。
4. `parseExtractedMemories` 解析 + 校验（type 合法、name/body 非空、按 Runes 截断、丢非法）。
5. 逐条 `InsertMemory`（`semantic` 用空 user_id）。
6. 按本轮出现的 type 触发整理/淘汰。

全程 best-effort，任何步骤失败仅 `logger.Warn` 并返回，不影响已返回用户的回答。

### 4.3 整理/淘汰

- `maybeConsolidateUserPreferences(ctx, userID)`：`CountMemoriesByUserAndType ≥ 20` → `consolidateViaLLM` → `ReplaceMemoriesByUserAndType`。
- `maybeConsolidateSemantic(ctx)`：`CountSemanticMemories ≥ 50` → `consolidateViaLLM` → `ReplaceSemanticMemories`。
- `maybePruneSessionSummaries(ctx, userID)`：`CountMemoriesByUserAndType ≥ 20` → `DeleteOldestMemories(...,10)`（删 `updated_at ASC` 最旧 10 条）。
- `consolidateViaLLM(ctx, memType, items)`：把全量记忆喂模型，要求返回**精简后的完整列表**（覆盖语义）；解析失败返回 nil（不动数据，避免误删）。

### 4.4 注入（会话开始）

`selectRelevantMemories(ctx, user, history) string`：

1. 守卫：`!EnableMemory || LLM==nil` → 返回 ""。
2. `all := ListRelevantMemories(user.ID)`；空则返回 ""。
3. 候选记忆带 `[i]` 编号 + 最近对话喂模型，要求返回相关索引数组 `[0,3,7]`（最多 10）。
4. `parseSelectedIDs` 解析索引，`pickMemoriesByIndex` 去重/越界过滤/截断 10。
5. `renderMemorySection(selected)`：按 type 分组渲染 Markdown，**仅 name+description**，空返回 ""。

渲染示例：

```markdown
### 关于用户的长期记忆
- (喜好) 偏好简洁中文回答：用户希望回答简洁、用中文、偏好示例代码
- (经历) 迁移系统资源：用户把运行时资源迁移到 app_home

### 通用知识
- Go 错误处理惯例：优先显式返回 error 而非 panic
```

## 5. 提示词草案（英文，claude/codex 风格，强制可解析 JSON）

### 5.1 提取 `memoryExtractionSystemPrompt`

```
You are a long-term memory extraction engine for a personal assistant named Link.
From the dialogue, extract durable memories worth keeping. Use the "type" field for three kinds:
- "session_summary": a concrete event/experience the user went through. Preserve factual
  integrity and temporal order; summarize what happened, not raw messages.
- "user_preference": a stable preference, constraint, or recurring habit of this user.
- "semantic": an abstract, reusable fact or general knowledge NOT tied to this specific user.
  It will be shared across users, so it must be de-identified and generally applicable.

Rules:
- Only extract NEW information not already covered by "Existing memories".
- Do not store one-off, trivial, or sensitive private data (passwords, payment, health).
- "name": short title (<=80 chars). "description": one-sentence gist (<=300 chars).
  "body": supporting detail (<=2000 chars).
- Output ONLY a JSON array: [{"name","type","description","body"}].
- If nothing new or everything is already covered, output exactly [].
```

User：`Existing memories:\n{existing}\n\nDialogue:\n{dialogue[:4000]}`（existing 渲染为 `- [type] name: description` 列表，无则 `(none)`）。

### 5.2 整理 `memoryConsolidationSystemPrompt`（喜好/语义共用，按 type 替换标签）

```
You are a memory consolidation engine. You are given the FULL current list of "{TYPE_LABEL}" memories.
Rewrite them into a clean, minimal set:
- Merge duplicates and near-duplicates into a single entry.
- Reconcile contradictions, keeping the most recent / most reliable statement.
- Drop outdated or superseded memories.
- Never invent new facts; only reorganize what is given.
- Keep limits: name <=80, description <=300, body <=2000 chars.
Output ONLY a JSON array [{"name","type","description","body"}] representing the COMPLETE refined
list (it fully replaces the old list). All entries must have type "{TYPE_VALUE}".
```

### 5.3 相关性筛选 `memorySelectionSystemPrompt`

```
You are a memory retrieval engine. Given the current conversation context and a numbered list of
candidate memories, select the ones RELEVANT and USEFUL for answering the user right now.
- Select at most 10.
- Prefer specific, on-topic memories; ignore unrelated ones.
- Output ONLY a JSON array of the selected memory indices, e.g. [0,3,7]. If none, output [].
```

User：`Recent conversation:\n{dialogue}\n\nCandidate memories:\n[0] (type) name: description\n...`

## 10. 风险与权衡

| 风险 | 缓解 |
| --- | --- |
| 每轮新增最多 2 次额外 LLM 调用（注入筛选在循环前，增首响应延迟；整理时再 +1） | 全部 best-effort，失败降级为空注入/不动数据；可后续异步化 |
| 注入筛选同步阻塞首字 | 失败仅 `logger.Warn` 返回空注入，不阻断 |
| 语义记忆系统级共享，A 产出可被 B 召回 | 提取提示词强制 semantic 为脱敏通用知识 |
| 模型整理返回垃圾导致误删 | 解析失败返回 nil 不动数据；Replace 在事务内 |
| 会话总结删最旧 10 条 | 明确按 `updated_at ASC`（删最早，保留最近经历） |

## 11. 本期不做（边界）
- 不做向量检索 / 语义召回（注入靠 LLM 相关性筛选，非向量检索）。
- 不做记忆前端管理 UI。
- 不做整理触发的节流缓冲（按精确阈值 20/50）。
- 不物理 DROP 旧表（仅停用代码引用）。
