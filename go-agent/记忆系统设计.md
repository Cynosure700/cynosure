# 记忆系统设计文档

## 1. 背景与目标

当前 go-agent 每次对话都是无状态的：系统提示词只包含身份、运行时上下文、技能列表，不携带任何跨会话的用户信息。用户每次都要重新交代自己的偏好、背景、正在做的事。

本设计参考 ChatGPT 的记忆实现，为 agent 引入两层记忆：

| 记忆类型 | 对标 ChatGPT | 形态 | 更新方式 | 读取方式 | 存储 |
| --- | --- | --- | --- | --- | --- |
| **用户档案卡** | Saved memories（"参考已保存的记忆"） | 结构化 JSON | 模型主动调用工具，随时更新/覆盖 | 精确全量读取，注入系统提示词 | 持久化（MySQL），每用户一条 |
| **近期对话摘要** | Chat history reference（"参考聊天记录"） | 轻量话题清单 | 每轮对话结束后自动抽取 | 静态注入到**新**会话的系统提示词 | 持久化话题清单，**不存原文** |

设计原则：
- **低侵入**：复用已有的 `PromptOptions.MemorySection`（已预留但未使用）、`Stop` hook、summarizer 模式、单表单 repo 模式。
- **可降级**：记忆读写失败不能中断主对话流程，全部 best-effort。
- **可控开销**：档案卡只在用户提供新信息时由模型触发写入；话题清单抽取用一次轻量 LLM 调用，且只在对话结束时执行。

---

## 2. 总体架构

```
┌─────────────────────────────────────────────────────────────┐
│ RespondToConversation (conversation_flow.go)                 │
│                                                              │
│  1. 进入对话循环前：                                          │
│     buildSystemPrompt(user, snapshot)                        │
│       └─> 读取 用户档案卡(JSON) + 近期话题清单                 │
│           └─> 拼成 MemorySection 注入 system prompt           │
│                                                              │
│  2. 对话循环中：                                              │
│     模型可调用 update_memory 工具                             │
│       └─> 覆盖式写入档案卡 JSON                               │
│                                                              │
│  3. 对话结束 (Stop hook):                                    │
│     summarizeConversationTopics                              │
│       └─> 轻量 LLM 抽取本轮话题 → 覆盖写该会话话题清单         │
└─────────────────────────────────────────────────────────────┘
```

两层记忆在数据上完全独立：
- **档案卡**：`user_id` 为主键，跨所有会话共享，存"关于这个人的稳定事实"。
- **话题清单**：`conversation_id` 为粒度，存"这个会话聊过什么"，多个会话的清单聚合后注入新会话。

## 3. 用户档案卡（User Profile Card）

### 3.1 数据形态

每个用户一条记录，核心字段是一段 JSON。JSON 的 schema 不做强约束（模型自由组织），但约定一个推荐结构供提示词引导：

```json
{
  "profile": {
    "identity": "后端工程师，使用 Go",
    "preferences": ["回答简洁", "中文交流", "偏好示例代码"],
    "projects": [
      {"name": "nano_cc", "note": "go-agent 项目，正在做记忆系统"}
    ],
    "constraints": ["不要自动提交 git"]
  },
  "updated_at": "2026-06-08T10:00:00Z"
}
```

- **随时更新、随时覆盖**：写入采用整段覆盖语义（whole-document replace）。模型决定新档案卡内容，工具直接覆盖旧值。不做字段级 merge（merge 容易产生冲突且复杂；模型每次拿到旧卡 + 新信息，自行产出完整新卡）。
- **精确读取**：注入提示词时是**全量原样**的 JSON，不做摘要、不做截断（设上限保护，见 3.5）。

### 3.2 存储设计

新增表 `user_profiles`：

```sql
CREATE TABLE IF NOT EXISTS user_profiles (
    user_id VARCHAR(64) PRIMARY KEY,
    profile_json LONGTEXT NOT NULL,
    updated_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6),
    CONSTRAINT fk_user_profiles_user FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

- 主键即 `user_id`，天然保证"每用户一条、覆盖写"。
- 写入用 `INSERT ... ON DUPLICATE KEY UPDATE profile_json = VALUES(profile_json)`。

storage models 新增：

```go
type UserProfile struct {
    UserID      string    `json:"user_id"`
    ProfileJSON string    `json:"profile_json"`
    UpdatedAt   time.Time `json:"updated_at"`
}
```

新增 repo 文件 `user_profiles_repo.go`：
- `GetUserProfile(ctx, userID) (UserProfile, bool, error)` — 不存在返回 `ok=false`。
- `UpsertUserProfile(ctx, profile UserProfile) error` — 覆盖写。

### 3.3 写入路径：`update_memory` 工具

参考 ChatGPT 的"模型自主决定保存记忆"。新增一个无状态工具 `update_memory`。

工具定义（`internal/tools/definitions.go` 注册）：
```
name: update_memory
description: 当用户透露了值得长期记住的稳定信息（身份、长期偏好、正在进行的项目、明确约束等）时，调用本工具更新用户档案卡。传入完整的新档案卡 JSON，将整段覆盖旧档案卡。不要存储一次性的、临时的或敏感隐私信息。
parameters:
  profile (string, required): 完整的档案卡 JSON 字符串。
```

实现要点（`internal/tools/` 新增 handler）：
- 由于工具需要写 DB（用户态），而现有 stateless handler 只能访问 `RuntimeEnv` / `SkillSnapshot`，**不能直接拿到 Store 和 userID**。因此 `update_memory` 不走 `tools.Dispatch` 的 stateless 路径，而是像 `spawn_subagent` 一样在 `tool_registry.go` 的 `executeToolCall` 里特判处理（那里能拿到 `ToolContext{User, Conversation}` 和 `s.Store`）。
- 校验传入 `profile` 是合法 JSON；非法则返回错误让模型重试。
- 调用 `Store.UpsertUserProfile`，写入 `{"profile": <模型给的>, "updated_at": now}` 或直接存模型给的整串（取决于是否要包一层；倾向直接存模型给的 JSON，updated_at 用列维护）。
- 返回简短成功提示（"档案卡已更新"），best-effort：DB 失败返回 error 字符串但不 panic。

> 备选方案：不引入工具，改为对话结束时用 LLM 自动抽取档案卡。**不采用**，因为档案卡要求"精确、可控、覆盖"，模型显式调用比自动抽取更可控、噪音更低，也更贴近 ChatGPT 的 saved memories 交互。

### 3.4 读取路径：注入系统提示词

在 `prompt_builder.go` 的 `buildSystemPrompt` 中：
1. 读取 `Store.GetUserProfile(ctx, user.ID)`。
2. 若存在，作为 `MemorySection` 的一部分（见 §5 注入格式）。

`buildSystemPrompt` 当前签名是 `(user, snapshot)` 且无 `ctx`、不返回 error。需要改造：
- 改为 `buildSystemPrompt(ctx, user, snapshot)`，内部读 DB。
- 读取失败仅记录日志、降级为空记忆，不阻断对话。

### 3.5 安全与边界
- **注入上限**：档案卡 JSON 超过阈值（建议 4KB）时截断并标注，避免 prompt 膨胀。
- **隐私**：工具描述明确指示模型"不要存储敏感隐私/一次性信息"。
- **多端一致**：主键 `user_id` 保证任意会话写入都覆盖同一份，天然一致。

## 4. 近期对话摘要（Recent Conversation Topics）

### 4.1 数据形态

**轻量话题清单**，不是原文摘要。每个会话维护一个话题列表：

```json
{
  "topics": [
    "为 go-agent 设计记忆系统",
    "把系统资源迁移到 app_home",
    "前端回车发送消息"
  ]
}
```

- 每条 topic 是一句话级别的短语（≤ 30 字），描述聊过的事，**不含对话原文、不含结论细节**。
- 静态注入：构建**新**会话提示词时，聚合该用户**最近 N 个其它会话**的话题清单，作为"近期聊过的话题"提示给模型。模型据此判断是否要追问/衔接，但拿不到原文（要原文得让用户自己说或开新需求）。

### 4.2 存储设计

新增表 `conversation_topics`：

```sql
CREATE TABLE IF NOT EXISTS conversation_topics (
    conversation_id VARCHAR(64) PRIMARY KEY,
    user_id VARCHAR(64) NOT NULL,
    topics_json LONGTEXT NOT NULL,
    updated_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6),
    KEY idx_conversation_topics_user (user_id, updated_at),
    CONSTRAINT fk_conversation_topics_conv FOREIGN KEY (conversation_id) REFERENCES conversations(id) ON DELETE CASCADE,
    CONSTRAINT fk_conversation_topics_user FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

- 主键 `conversation_id`：每会话一条，覆盖写（每轮结束重算整会话话题清单）。
- `idx_conversation_topics_user (user_id, updated_at)`：支持"按用户取最近 N 个会话话题"。

storage models 新增：
```go
type ConversationTopics struct {
    ConversationID string    `json:"conversation_id"`
    UserID         string    `json:"user_id"`
    TopicsJSON     string    `json:"topics_json"`
    UpdatedAt      time.Time `json:"updated_at"`
}
```

新增 repo 文件 `conversation_topics_repo.go`：
- `UpsertConversationTopics(ctx, ConversationTopics) error` — 覆盖写。
- `ListRecentTopicsByUser(ctx, userID, excludeConversationID string, limit int) ([]ConversationTopics, error)` — 取最近 N 个会话（排除当前会话），按 `updated_at DESC`。

### 4.3 写入路径：Stop hook 抽取话题

参考已有 `summarizer.go`，新增一个 Stop hook，在对话每轮结束后异步/同步抽取本会话话题。

- 在 `hooks.NewDefaultHookManager` 的 `Stop` 链尾追加 `summarizeConversationTopicsHook`。
- 该 hook 需要 LLM + Store。当前 `Stop` hooks 只拿到 `LoopState`，而 `LoopState.Store` 是受限接口、且无 LLM。两个改造选项：
  - **选项 A（推荐）**：不放进 hooks 包，而是在 `conversation_flow.go` 的 `RespondToConversation` 返回前，由 `Service`（持有 LLM 和完整 Store）直接调用 `s.updateConversationTopics(ctx, conversation, user, state.History)`。Service 层能力完整，改动集中。
  - 选项 B：扩展 `hooks.Store` 接口 + 给 LoopState 注入 summarizer 回调。改动面更大。
  - **采用选项 A**。
- 抽取逻辑（`internal/web/runtime/` 新增 `topic_memory.go`）：
  1. 用一次非流式、无工具的 LLM 调用，system prompt 指示"把这段对话压缩成 3-6 个 ≤30 字的话题短语，只输出 JSON 数组，不要原文、不要结论细节"。
  2. 解析为 `[]string`，做长度/数量截断。
  3. `UpsertConversationTopics` 覆盖写。
  4. 全程 best-effort：失败仅记日志，不影响已返回给用户的回答。
- **触发节流**：每轮结束都重算成本偏高。约定只有当历史消息数较上次变化达到阈值，或简单地"每轮都算但内容短所以便宜"。初版采用每轮结束都重算（输入只喂 user/assistant 文本，去掉 tool 噪音，开销可控），后续可加节流。

### 4.4 读取路径：注入新会话提示词

在 `buildSystemPrompt`（已因档案卡改为带 ctx）中：
1. `ListRecentTopicsByUser(ctx, user.ID, conversation.ID, N)`（N 建议 5）。
2. 聚合所有 topic 去重，作为"近期话题"放进 `MemorySection`。

> 注意：`buildSystemPrompt` 当前签名没有 `conversation`。需要把 `conversation.ID` 传入用于排除当前会话。改造签名为 `buildSystemPrompt(ctx, conversation, user, snapshot)`。

## 5. 提示词注入格式（MemorySection）

复用 `assistant.PromptOptions.MemorySection`（已存在但未被 `prompt_builder.go` 使用）。`BuildSystemPrompt` 已经会把非空 `MemorySection` 渲染成 `## Memory` 段落，无需改 assistant 包。

`prompt_builder.go` 新增组装函数 `buildMemorySection(profile, recentTopics)`，产出形如：

```markdown
### 用户档案卡
以下是关于当前用户的已保存信息，回答时请参考，但不要照搬复述：
```json
{ ...档案卡 JSON... }
```

### 近期聊过的话题
仅供参考，帮助你理解用户近期关注点；你没有这些对话的原文，如需细节请让用户补充：
- 为 go-agent 设计记忆系统
- 把系统资源迁移到 app_home
```

- 档案卡为空且无近期话题时，`MemorySection` 为空字符串，`BuildSystemPrompt` 自动跳过该段。

## 7. 数据流时序

### 写档案卡（会话内）
```
用户: "我是 Go 后端，喜欢简洁中文回答"
 → 模型调用 update_memory(profile={...})
 → executeToolCall 特判 → Store.UpsertUserProfile(user_id, json)
 → 返回 "档案卡已更新"
```

### 抽取话题（会话结束）
```
本轮对话结束 (finish_reason != tool_calls)
 → RespondToConversation 返回前
 → updateConversationTopics(history)
 → LLM 抽取 ["话题1","话题2",...]
 → Store.UpsertConversationTopics(conversation_id, json)   // 覆盖
```

### 注入（新/任意会话开始）
```
buildSystemPrompt(ctx, conversation, user, snapshot)
 ├─ GetUserProfile(user_id)                        → 档案卡 JSON
 ├─ ListRecentTopicsByUser(user_id, !conv_id, 5)   → 近期话题
 └─ MemorySection → "## Memory" 段落注入 system prompt
```

## 8. 与 ChatGPT 的对应关系小结

- **档案卡 = Saved memories**：显式工具写入、结构化、可覆盖、精确全量读取。
- **近期话题 = Chat history reference**：自动生成的轻量话题索引，跨会话静态注入，不提供原文。
- 二者都在系统提示词里以独立小节呈现，并明确告知模型"参考但不复述/无原文"。

---

## 9. 风险与权衡

| 风险 | 缓解 |
| --- | --- |
| 每轮结束抽取话题增加一次 LLM 调用、增加时延 | best-effort + 只喂文本（去 tool 噪音）；后续可加节流或异步 goroutine |
| 档案卡被模型写入垃圾/过大 | JSON 校验 + 注入上限截断 + 工具描述约束 |
| `buildSystemPrompt` 改签名波及调用点 | 调用点集中（仅 conversation_flow），编译期可发现 |
| 记忆读写失败影响主流程 | 全部 best-effort，失败降级为空记忆 + 日志 |
| 隐私合规 | 工具描述禁止存敏感信息；可后续加用户级"清空记忆"接口（本期不做） |

---

## 10. 本期不做（明确边界）
- 不做向量检索 / 语义召回（话题清单是静态注入，非检索）。
- 不做记忆的前端管理 UI（查看/编辑/删除档案卡）。
- 不做字段级 merge（采用整卡覆盖）。
- 不做跨用户共享记忆。
- 不做话题抽取的异步队列（初版同步 best-effort）。
