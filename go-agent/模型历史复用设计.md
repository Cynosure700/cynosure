# 模型历史复用（Model History Reuse）设计

## 背景

`go-agent` 每轮对话在调用 LLM 前，都会对历史做上下文压缩：`compressContextBeforeLLM`（`internal/web/runtime/context_compression.go`）克隆一份历史副本，跑过 5 层压缩管线（`internal/web/runtime/compression/`），得到"请求态历史" `requestHistory` 发给模型。

改造前，每轮压缩的输入基底都是**全量原始聊天记录** `state.History`（来源于 `conversations.history_json`）。这意味着：会话越长，每一轮都要对几乎相同的长前缀**重复跑一次压缩**——尤其是最后一层 `FullHistorySummarizationStrategy`，在 token 超预算时会调用 LLM 做全量摘要，既慢又贵，且因源历史 hash 每轮变化导致 `context_summaries` 缓存频繁未命中、反复摘要。

**核心目标**：让"上一轮已经压缩好的历史"在下一轮被直接复用，作为新一轮的历史起点，从而显著减少重复压缩。

## 与现有机制的边界

```text
展示历史 (state.History / conversations.history_json)
    = 逐字真实消息，全量原始，前端展示与持久化的源头

【新增】模型历史 (state.ModelHistory / conversation_model_histories 表)
    = 喂给压缩管线 / 模型的历史线，起点为上一轮压缩产物，随轮增长

三层长期记忆 (memories 表)         = 跨会话沉淀，注入 system prompt
会话记忆 (conversation_memories 表) = 当前会话主干信息，压缩管线替代品
全量摘要 (context_summaries 表)     = token 超限时的一次性 LLM 摘要缓存
```

关键约束（必须遵守）：

1. **展示历史不受影响**：`conversations.history_json` 永远保持全量原始消息，不含 summary 前导 / `<persisted-output>` 占位 / 被裁剪的中间消息。前端 `displayConversationMessages`（`internal/web/app/conversation_handlers.go`）读的仍是这份原始历史。
2. **系统提示词每轮重建**：system prompt 在循环外构造一次，不进模型历史。

## 设计方案：双历史线显式分离

在 `LoopState`（`internal/web/runtime/hooks/types.go`）中新增 `ModelHistory` 字段，与原有 `History` 并存，形成两条独立的历史线：

- **`History`（展示线）**：保持全量原始，照旧写入 `history_json`、供前端展示与记忆收尾使用。
- **`ModelHistory`（模型线）**：来自上一轮的压缩产物（从新表加载），作为压缩管线的输入基底，并随本轮对话同步增长。

### 数据流

```text
新一轮开始
  ├─ loadConversationMessages → History（全量原始，含 Redis 缓存）
  ├─ loadModelHistory         → ModelHistory（取自 conversation_model_histories；
  │                              无记录 / 解析失败 / 出错 → 回退为 History 的克隆）
  └─ appendUserMessageHook    → 本轮 user 同时 append 到 History 与 ModelHistory

每个 round
  ├─ compressContextBeforeLLM(基底 = ModelHistory) → requestHistory
  ├─ 调模型
  ├─ 带 tool_calls 的 assistant → 同时 append 到 History 与 ModelHistory
  └─ tool result               → 同时 append 到 History 与 ModelHistory

输出最终答案（finishReason != tool_calls）
  ├─ Stop hook：History + 最终 assistant → 写 history_json（展示，不变）
  └─ 异步收尾(scheduleMemoryWork)：
       finalModelHistory = 最后一次 requestHistory + 最终 assistant
       → UpsertConversationModelHistory（落库，供下一轮复用）
```

### 存表内容与时机

- **存什么**：最后一个 round 压缩后的 `requestHistory`，再追加本轮最终 assistant 答案（该 round 的 `requestHistory` 是答案的输入，本身不含答案那条消息，故需补上）。
- **何时存**：模型输出最终答案后，在异步收尾 `scheduleMemoryWork`（`internal/web/runtime/conversation_memory.go`）中、记忆相关 LLM 调用**之前**执行 upsert，确保即使后续超时也不丢压缩成果。复用已有的会话锁与异步框架，不阻塞用户响应。
- **摘要前导原样保留**：若某轮触发了全量摘要，存表的模型历史会带 `<conversation-summary>` 前导，下一轮在此基础上继续压缩。这是"直接复用上轮压缩产物"的自然结果（已知取舍：持续超预算时存在"摘要套摘要"的信息稀释）。

### 兜底

表中无记录 / JSON 解析失败 / 查询出错时，`loadModelHistory` 回退为 `History` 的克隆——行为与改造前完全一致，保证正确性。

## 数据结构

新增表 `conversation_model_histories`（`internal/web/storage/migrations.go` 中 `ensureConversationModelHistoryTable`）：

```sql
CREATE TABLE IF NOT EXISTS conversation_model_histories (
    conversation_id  VARCHAR(64) PRIMARY KEY,        -- 会话维度单行 upsert
    user_id          VARCHAR(64) NOT NULL,
    history_json     LONGTEXT NOT NULL,              -- 复用 EncodeConversationHistory
    estimated_tokens INT NOT NULL DEFAULT 0,
    created_at       DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    updated_at       DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6),
    KEY idx_cmh_user (user_id, updated_at),
    CONSTRAINT fk_cmh_conversation FOREIGN KEY (conversation_id) REFERENCES conversations(id) ON DELETE CASCADE,
    CONSTRAINT fk_cmh_user FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
```

- 主键 `conversation_id`，每会话一行，`ON DELETE CASCADE` 随会话删除自动级联清理。
- **不进 Redis 缓存**：每轮一次读写、单行主键查询、已被会话锁串行化，无需第二份缓存（与 `conversation-cache` 只缓存展示历史的语义互不冲突）。

repo（`internal/web/storage/conversation_model_histories_repo.go`）：

- `GetConversationModelHistory(ctx, conversationID) ([]Message, bool, error)`：无行 / 解析失败均返回 `(nil, false, nil)` 触发兜底。
- `UpsertConversationModelHistory(ctx, conversationID, userID, messages)`：`INSERT ... ON DUPLICATE KEY UPDATE`。

## 正确性

- **展示不受影响**：`history_json` 仍由 `state.History` 写入，全量原始、无压缩制品。
- **tool 配对安全**：模型线与展示线在三处 push 点（user / assistant / tool）同步累积；再压缩仍走原有 `repairToolCallBoundaries`，对 summary / 占位等无 tool 关联的消息无副作用。
- **压缩管线保留**：模型历史随轮增长仍可能再次超预算，需要继续压缩。
- **兜底**：表缺失 / 解析失败 / 出错 → 回退为展示历史克隆，等价改造前行为。
- **已知取舍**：持续超预算会出现"摘要套摘要"的信息稀释（按需求确认，原样存 `requestHistory`，不剥离摘要前导）。

## 验证

1. 构建 / 静态：`cd go-agent && go build ./... && go vet ./internal/web/...`。
2. 单元 / 集成（`internal/web/runtime`、`internal/web/storage`）：
   - `loadModelHistory`：有记录时复用存表模型历史；无记录 / 出错时回退展示历史。
   - 压缩不污染：`compressContextBeforeLLM` 不修改 `History` 与 `ModelHistory`，仅产出请求态副本。
   - 回归：`history_json` 不含 `<conversation-summary>`；`displayConversationMessages` 输出不变。
3. `cd go-agent && go test ./internal/web/...`。
4. 手动：长会话（>50 条）观察第二轮起 `logger.LogLLMRound` 的 reqBody 体积稳定；DB 校验 `conversations.history_json` 单调增长、`conversation_model_histories.history_json` 稳定；删除会话级联清理。
