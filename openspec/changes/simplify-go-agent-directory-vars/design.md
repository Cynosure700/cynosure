## Context

当前 go-agent 的目录变量主要围绕 `APP_HOME`、`WORKSPACE_ROOT`、`BUILTIN_SKILLS_DIR`、`COMMAND_BIN_DIR`、`COMMAND_SCRIPT_DIR` 展开，但这组变量的关系同时散落在配置解析、runtime 环境装配和 README 文档中。虽然现有行为已经稳定：workspace 根目录优先取 `output/workspace`，命令与技能目录都从该根目录派生，工具再基于这些值执行；但实现上仍存在“先各自解析、再在 runtime 层补默认值”的重复逻辑，阅读时不容易立刻看出哪一个才是主变量。

这次变更不打算改变任何默认路径、回退顺序、显式配置入口或边界校验，只聚焦于把目录变量收敛成更清晰的单一模型，并让 README 与代码表达一致。

## Goals / Non-Goals

**Goals:**
- 将目录配置收敛为“先解析 `APP_HOME` 与 `WORKSPACE_ROOT`，再统一派生运行时资产目录”的清晰模型。
- 消除配置层和 runtime 层对 `bin/cmd/skills` 目录的重复默认推导，保留现有兼容行为。
- 保持对显式环境变量 / `config.json` 配置的支持，同时继续保证目录不能偏离 workspace 根目录。
- 更新 `go-agent/README.md`，让使用者更容易理解哪些变量需要关心、哪些通常不需要单独配置。

**Non-Goals:**
- 不修改目录变量名称，不引入新的环境变量。
- 不改变 `WORKSPACE_ROOT` 的默认解析顺序，也不调整 `output/workspace` 与 `workspace` 的优先级。
- 不改变工具执行权限、技能目录切换逻辑或任何现有审计字段。
- 不重构与目录变量无关的配置项、数据库连接或前端行为。

## Decisions

### 1. 以 `WORKSPACE_ROOT` 作为运行时资产目录的唯一规范来源

**选择：** 继续保留 `BUILTIN_SKILLS_DIR`、`COMMAND_BIN_DIR`、`COMMAND_SCRIPT_DIR` 作为可显式配置字段，但实现上把它们视为 `WORKSPACE_ROOT` 下的规范派生目录；未显式配置时只在配置层推导一次，runtime 直接消费结果，不再自行补默认值。

**原因：** 现有规格已经约束运行时资产目录来自 workspace 根目录，代码中再做一层兜底只会制造“哪一层才是最终真相”的理解成本。把唯一派生点放在配置层，可以让配置对象本身成为完整、可直接消费的目录模型。

**备选方案：**
- 保持现状，在 runtime 层继续对空目录字段做补齐——兼容但重复，后续维护仍容易出现不一致。
- 完全移除三个显式目录变量——会压缩兼容面，也可能影响已有部署配置，不适合本次“只简化不破坏”的目标。

### 2. 保留显式目录配置，但继续限制为规范派生路径

**选择：** 保持现有校验语义：即使用户显式设置 `BUILTIN_SKILLS_DIR`、`COMMAND_BIN_DIR`、`COMMAND_SCRIPT_DIR`，它们也必须等于 `WORKSPACE_ROOT` 下的对应目录。

**原因：** 这能确保“可配置”与“单一目录模型”同时成立：外部配置仍可显式声明最终值，但不会把运行时资产拆到多个彼此独立的根路径下。这样也能避免 README 出现多种等价但难维护的配置方式。

**备选方案：**
- 放宽为“只要在 workspace 根目录下即可”——会再次引入多个变体路径，增加说明与测试复杂度。
- 彻底忽略显式配置并强制覆盖——对已有配置文件不够友好。

### 3. README 只突出主变量和默认推导规则

**选择：** 在文档中把 `APP_HOME`、`WORKSPACE_ROOT` 作为首先解释的主变量，把 `BUILTIN_SKILLS_DIR`、`COMMAND_BIN_DIR`、`COMMAND_SCRIPT_DIR` 明确标记为通常无需单独设置的派生目录，仅在需要显式声明规范路径时才配置。

**原因：** 用户真正需要理解的是“应用根目录”和“runtime workspace 根目录”的关系，而不是记住五个变量之间的交叉组合。文档跟随代码中的单一模型，才能真正降低理解成本。

**备选方案：**
- 仅改代码不改文档——会继续保留外部认知负担。
- 直接删掉派生目录变量的 README 说明——会让已有用户不知道这些变量仍然受支持。

## Risks / Trade-offs

- **[Risk] 精简 runtime 默认逻辑时遗漏某些空值兼容路径** → 通过配置与 runtime 测试覆盖默认解析、显式覆盖和回退场景，确保行为不变。
- **[Risk] README 简化后让用户误以为派生目录变量不再支持** → 在文档中明确“通常无需配置，但仍兼容显式声明”。
- **[Trade-off] 继续保留三个派生目录变量会让配置面看起来仍然偏多** → 先通过单一派生模型和文档收敛降低复杂度，避免一次性删除配置项带来的兼容风险。

## Migration Plan

1. 收敛 `internal/config` 中的目录解析逻辑，确保 `AppConfig` 输出的目录字段已经是最终规范值。
2. 移除 runtime 层对这些目录的重复默认推导，改为直接使用配置层给出的结果。
3. 更新 README，并通过配置 / runtime 回归测试确认默认行为没有变化。
4. 如出现回归，可回滚到当前多层默认推导实现；该变更不涉及数据迁移。

## Open Questions

- 暂无阻塞性开放问题；按“保留现有变量接口，仅统一其来源和说明”的方案推进。
