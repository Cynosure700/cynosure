## Context

当前项目已经具备多用户 Web 聊天、会话存储、技能管理与工具调用能力，但产品入口和默认定位仍然保留明显的 CLI 编码助手特征：`go-agent/main.go` 仍直接进入 REPL，CLI 提示词将角色定义为 coding agent，而 Web runtime 的系统提示词也延续了“web coding agent”的设定。这导致实现上已经具备聊天机器人基础，产品心智却仍围绕终端与编码任务展开。

本次变更需要把这些既有能力重新组织为一个服务化、浏览器优先、通用用途的 Agent 聊天产品，并明确遵循类似 ChatGPT 的网页形态：用户通过会话界面直接提问和获得回答，网页端不承担本地 CLI 职责，不执行 shell 命令，也不以“操作用户目录/工作区”为前提组织能力。

## Goals / Non-Goals

**Goals:**
- 让 Web 服务与浏览器聊天界面成为唯一正式的用户使用入口
- 将默认 assistant 角色调整为通用 Agent 聊天机器人，而非编码助手
- 让聊天界面优先展示自然对话，整体交互尽量贴近 ChatGPT 的 conversation-first 形态
- 明确网页端不提供 shell 执行、用户目录访问或本地工作区操作能力
- 将技能与受控工具降级为可选增强项，而不是围绕开发目录操作设计产品主流程
- 在尽量复用现有存储、鉴权、会话与 runtime 基础设施的前提下完成产品转向

**Non-Goals:**
- 不重写现有用户鉴权、会话持久化或技能 CRUD 基础设施
- 不在本次变更中新增复杂的多模型路由、插件市场或团队协作能力
- 不追求首版就覆盖 ChatGPT 的全部产品细节，例如多模态、语音或移动端适配
- 不要求彻底删除所有内部可复用的 CLI 相关代码，只要求它们不再构成正式产品入口
- 不为网页端设计“受控 shell”或“浏览器代理用户目录”之类的折中方案

## Decisions

### 1. 产品入口收敛为 Web 服务，CLI REPL 退出正式使用路径

**选择：** 将服务模式定义为唯一正式入口，根入口不再直接启动交互式 REPL；应用应以启动 Web API / Web Chat 服务为默认行为。

**备选：**
- 保留 CLI 与 Web 双入口，通过参数或环境变量切换
- 继续以 CLI 为默认入口，只在文案上强调 Web

**理由：** 用户要求已经明确要求完全舍弃 CLI 使用方式。如果继续保留双主入口，产品定位、测试路径、部署方式和默认提示词都会持续分裂，难以真正完成转向。

### 2. 统一系统提示词为“通用 Agent”，而不是“编码助手”

**选择：** 将运行时基线提示词改为通用对话助手，强调理解问题、直接回答、必要时再调用有限的受控能力；不得把 shell 执行、文件编辑、工作区操作或用户目录访问当作网页产品的默认能力前提。

**备选：**
- 保留 coding agent 提示词，只通过前端文案弱化技术感
- 增加“通用/编码”模式切换，让用户自行选择

**理由：** 当前问题并不只是界面文案，而是 runtime 的默认行为假设本身偏向编码任务。如果不从提示词与工具策略层一起收敛，产品会继续表现为代码助手。

### 3. Web 界面采用 ChatGPT 式 conversation-first 布局

**选择：** 主界面围绕会话列表、消息流、输入框和回答区域组织，尽量接近 ChatGPT 的低干扰聊天体验；技能管理退出主聊天流，工具运行细节不再作为主界面核心信息，必要时仅以轻量状态或次级面板呈现。

**备选：**
- 保持当前三栏/双栏信息密集布局
- 完全隐藏技能与工具事件，不再对用户可见

**理由：** 目标不是移除平台能力，而是让用户先感知“聊天机器人”，再按需接触增强能力。完全保留当前布局会强化开发者工具心智，不符合用户要求的 ChatGPT 形态。

### 4. 网页端明确不提供 shell 与用户目录操作能力

**选择：** 网页聊天产品不暴露 shell、bash、任意文件读写、目录浏览或任何依赖“替用户操作本地工作区”的能力；网页端仅保留不依赖用户本地目录的受控能力，例如技能加载、服务端持久化会话、平台内部状态读取等。

**备选：**
- 沿用当前 registry，把所有已注册工具直接暴露给聊天 runtime
- 为每个用户虚拟工作区或目录映射，以支持网页端继续调用 shell / 文件工具

**理由：** 用户已经明确指出网页端无法操作用户目录，因此 shell 与本地文件工具在产品模型上就是错误能力，而不是“高风险但可选”的能力。继续保留这类假设会让实现和交互都偏离目标产品。

### 5. 迁移策略以“保留可复用内核、替换产品外壳”为原则

**选择：** 尽量复用既有会话存储、技能加载、runtime loop 和 SSE 机制，只对入口、默认提示词、前端结构与工具能力边界做产品化重构，并从网页运行时中剔除依赖本地目录的工具假设。

**备选：**
- 从零重写一个新的聊天 runtime
- 继续复用所有 CLI 心智和结构，只做少量文案替换

**理由：** 当前仓库已经具备 Web Chat 所需的大部分骨架，最有效的路径是复用核心能力，同时移除 CLI 导向的默认假设。

## Risks / Trade-offs

- **[Risk] 仍有部分代码路径默认依赖 CLI 心智或目录操作能力** → 通过统一 system prompt、运行时工具注册表和前端文案集中治理，去掉“工作区/目录/命令执行”假设
- **[Risk] 将工具事件降级后，用户对 agent 行为的可解释性降低** → 保留轻量可查看的运行细节，但不让其占据主界面
- **[Risk] 原有偏开发者的使用场景会因为网页端不支持 shell / 文件工具而退化** → 接受该产品取舍，网页端聚焦 ChatGPT 式对话能力，不再承诺终端代理能力
- **[Trade-off] 完全弱化 CLI 会减少开发者本地调试便利性** → 接受这一代价，用内部调试入口或测试替代正式产品入口
- **[Trade-off] 保留技能管理但降低其主界面权重，会让高级能力入口更深** → 换取更清晰的首屏产品心智，符合聊天机器人优先目标

## Migration Plan

1. 调整应用启动入口，确保默认运行路径启动 Web 服务而不是 REPL
2. 抽取并统一运行时系统提示词构造逻辑，移除 coding-agent 基线设定
3. 从 Web runtime 中移除 shell、目录访问和文件工作区类能力，并补充“该能力网页端不支持”的兜底回答路径
4. 重构前端主界面，使其更贴近 ChatGPT 式聊天产品，保留会话能力但降低技能管理与工具事件的主流程权重
5. 运行现有后端与前端测试，并补充浏览器聊天主路径验证
6. 若需要回滚，可恢复旧入口与旧提示词构造，同时保留数据模型不变

## Open Questions

- 是否需要保留一个仅面向内部开发的隐藏调试入口？本次设计默认“不作为正式产品能力”，且不影响网页端产品定义
- 技能管理最终是放入独立页面、抽屉，还是个人设置区域？本次变更只要求其退出主聊天流程，不强制具体 UI 形态
