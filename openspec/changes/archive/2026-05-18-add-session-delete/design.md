## Context

当前会话相关链路只覆盖“创建、列表、查看、继续发送消息”，后端路由在 `go-agent/internal/web/app/server.go:289` 到 `go-agent/internal/web/app/server.go:363` 之间没有删除分支，存储层在 `go-agent/internal/web/storage/store.go:199` 到 `go-agent/internal/web/storage/store.go:309` 之间也只有创建、查询、缓存读写能力。前端会话列表渲染位于 `web/src/App.tsx:190` 到 `web/src/App.tsx:205`，每个会话只有切换入口，没有删除动作；API 层 `web/src/api.ts:77` 到 `web/src/api.ts:137` 也缺少删除接口封装。

本次变更跨越前端 UI、前端 API、服务端路由、存储删除与缓存失效，且删除操作涉及权限校验与关联数据清理，因此适合先用设计文档明确方案。

## Goals / Non-Goals

**Goals:**
- 为已认证用户提供删除自己聊天会话的端到端能力
- 确保删除只作用于会话拥有者，不能删除他人会话
- 删除会话时同步移除数据库中的 conversation 记录及其关联 messages/tool_calls，并清理 Redis 会话缓存
- 删除当前激活会话后，让前端自动切换到剩余会话或空状态，不留下失效选中项
- 为关键删除场景补充前后端测试覆盖

**Non-Goals:**
- 不新增“批量删除会话”“软删除/回收站”“二次确认弹窗历史恢复”等扩展能力
- 不修改会话标题生成、消息发送或会话排序规则
- 不调整认证模型，也不扩展到 `auth_sessions` 的管理或删除
- 不引入新的存储介质、消息队列或后台异步清理任务

## Decisions

### 1. 后端采用 `DELETE /api/conversations/{id}` 单会话删除接口

**选择：** 复用现有 `/api/conversations/{id}` 资源路由，在 `DELETE` 方法下执行删除，并保持与现有 skill 删除接口一致，返回 `200 {"ok": true}`。

**备选：**
- 增加 `/api/conversations/{id}/delete` 之类的动作式接口
- 使用 `POST` 携带删除动作，避免前端处理 `DELETE`

**理由：** 当前后端已经按 REST 资源路由组织 skill 与 conversation，继续沿用资源删除语义最简单，也能最少改动现有路由结构与前端请求封装。

### 2. 权限校验继续放在 handler 层，存储层负责按 ID 删除与缓存失效

**选择：** 服务端先像读取会话详情一样查询会话归属并校验 `conversation.UserID == user.ID`，确认归属后调用新的 store 删除方法。存储层不额外接收 userID 做授权判断，只负责删除 conversation、依赖数据库外键级联清理关联 records，并删除 Redis 缓存键。

**备选：**
- 把 userID 一并传入 store，在 SQL 层执行 `DELETE ... WHERE id = ? AND user_id = ?`
- 完全由 store 负责先查后删，handler 不感知权限判定细节

**理由：** 当前详情读取、消息流入口等所有会话归属校验都集中在 handler 层，沿用同一模式能减少重构范围，也更符合现有服务边界。数据库已有外键级联约束，删除主表即可同步清理消息和工具调用，无需重复手写多表删除语句。

### 3. Redis 会话缓存采用同步失效，失败时将请求视为错误

**选择：** 在数据库删除成功后立刻执行 `DEL conversation-cache:<id>`；如果 Redis 删除返回非空错误，则接口返回 500，并由测试覆盖该失败路径。

**备选：**
- 将缓存删除视为 best effort，只记录日志并继续返回成功
- 先删缓存再删数据库，以避免任何残留缓存

**理由：** 当前缓存是运行时直接读取的活跃上下文副本，删除接口如果已成功响应却留下旧缓存，会让后续排查更困难。同步失效最符合“删除成功即所有已知状态完成清理”的预期；即便数据库已删除，返回错误也能暴露环境问题，促使调用方重试或人工排查。

### 4. 前端在列表项内提供删除操作，并在本地立即修正选中状态

**选择：** 在会话列表每个条目上增加删除按钮；删除成功后直接从 `conversations` state 中移除该项。如果删除的是当前激活会话，则优先切换到剩余列表中的第一项；若已无剩余会话，则清空 `activeConversationId`、`messages` 与工具事件状态。

**备选：**
- 删除后统一调用 `refreshAll()` 再重新推导当前会话
- 只允许删除非激活会话，避免处理当前选中状态

**理由：** 会话列表数据量小，但删除后的即时状态变化非常明确，本地同步更新能减少一次额外列表闪烁，并确保被删除的会话不会继续在右侧消息面板中显示。

## Risks / Trade-offs

- **[Risk] 删除当前激活会话后，消息区仍残留旧内容** → 删除成功时同步清空 `messages`，并在存在剩余会话时触发对新激活会话的加载
- **[Risk] 误删后无法恢复** → 本次明确选择硬删除，先不实现回收站；如需降低风险，可在实现阶段增加轻量确认交互
- **[Risk] Redis 删除失败时数据库已删除，接口返回错误会产生“是否成功”的感知不一致** → 在错误文案与测试中明确该场景属于缓存失效异常，重试不会恢复已删会话，但可完成缓存清理
- **[Trade-off] handler 先查归属再删除会多一次数据库往返** → 换取与现有会话权限校验模式一致，降低改动面
- **[Trade-off] 返回 200 JSON 而不是 204** → 响应体略有冗余，但能复用现有前端请求与断言模式，减少实现分支

## Migration Plan

1. 在存储接口与实现中新增会话删除方法，并处理 Redis 缓存键删除
2. 在服务端会话详情路由中增加 `DELETE` 分支，复用已有归属校验逻辑
3. 在前端 API 层增加删除调用，并在会话列表中接入删除按钮与状态更新逻辑
4. 补充服务端 handler/store 测试与前端交互测试
5. 部署后无需数据迁移；若需回滚，只需移除删除入口与 API 分支，现有数据模型保持兼容

## Open Questions

- 是否需要在前端加入二次确认或“删除中”禁用态？当前设计默认可以先提供最小删除入口，交互细节由实现时按复杂度决定
- 删除失败时前端是否需要区分“权限错误”“缓存清理错误”“会话不存在”？当前设计允许先统一展示后端错误消息
